# Lounge Front-end 구축 가이드 브리핑

## 1. 브리핑 목적

Front-end 구축을 진행하기 전에 개발 기준과 구조를 가이드로 정리했습니다.

이번 브리핑은 완성된 시스템을 인계하거나 프로젝트 전체 기술을 확정하는 자리가 아닙니다. 현재 준비한 Front-end 가이드의 주요 내용과 앞으로 어떤 기준으로 구축할 것인지 공유하는 자리입니다.

가이드는 개발자나 AI에 따라 구현 방식이 달라지는 문제를 줄이고, 향후 운영 인력이 구조를 이해하여 기능을 수정·확장하기 쉬운 기반을 만드는 것을 목적으로 합니다.

## 2. 현재 준비한 범위

가이드에는 다음과 같은 Front-end 구축 기준을 정리했습니다.

- React, Next.js와 TypeScript를 사용하는 기본 개발 구조
- Figma, 디자인 토큰, Tailwind CSS와 shadcn/ui를 연결하는 UI 구현 기준
- React 지역 상태, TanStack Query, Zustand와 React Hook Form의 역할 구분
- WebView와 Native App 사이의 책임 및 Bridge 연동 원칙
- 접근성, 테스트, 코드 리뷰와 품질 확인 기준
- 느린 네트워크, 로딩, 오류와 Offline 상황에 대한 Front-end 대응 원칙
- 외부 입력, 개인정보, Client 저장소와 의존성 공급망을 포함한 보안 기준
- AI를 개발과 리뷰에 사용할 때의 작업 범위 및 검증 원칙

이 내용을 처음부터 모두 구현한다는 뜻은 아닙니다. 실제 기능과 사용처가 생길 때 필요한 기준을 선택하여 적용합니다.

## 3. 이렇게 구축할 예정입니다

### 역할이 다른 코드를 분리합니다

화면, 서버 데이터, Client 상태, Form과 Native App 통신의 책임을 구분합니다. 서버에서 조회한 데이터를 별도의 전역 상태에 다시 복제하거나, 화면 Component에 API·업무 규칙·Bridge 처리를 한꺼번에 넣지 않습니다.

### 공통화는 실제 반복을 확인한 뒤 진행합니다

처음부터 많은 Wrapper, 공통 Type과 추상화 계층을 만들지 않습니다. 기능 가까이에서 작게 시작하고, 동일한 형태와 변경 이유가 반복될 때 공통 Component나 공통 기능으로 분리합니다.

### UI는 일관되게 확장할 수 있도록 구성합니다

디자인 토큰과 프로젝트에 설치된 shadcn/ui Component를 우선 활용합니다. 화면마다 유사한 UI와 상태 표현을 새로 만들지 않고, 공통 기준을 유지하면서 필요한 부분을 프로젝트 코드로 수정합니다.

### 정상 화면 외의 상태도 함께 구현합니다

데이터가 정상적으로 도착한 화면만 만들지 않습니다. 최초 로딩, 갱신, 빈 데이터, 오류, 느린 응답과 연결 끊김을 실제 기능의 필요에 맞게 구분합니다.

### AI 결과도 같은 기준으로 검증합니다

AI가 만든 코드와 설명을 그대로 확정하지 않습니다. 관련 가이드, 실제 코드와 설정을 근거로 검토하고, 수행한 Test와 확인하지 못한 항목을 구분합니다.

## 4. 운영과 확장을 고려한 지점

가이드의 목적은 현재 화면을 만드는 데서 끝나지 않습니다. 이후 다른 인력이 기능을 추가하거나 문제를 확인할 때 기존 구조와 판단 이유를 파악할 수 있도록 기준을 남기는 데 의미가 있습니다.

- 새로운 화면은 기존 Layout, Component와 디자인 토큰을 확인한 뒤 추가합니다.
- 서버 데이터가 늘어나면 TanStack Query의 기능별 Query와 갱신 범위를 확장합니다.
- 여러 화면에서 공유해야 하는 Client 상태가 확인되면 Zustand 적용 범위를 검토합니다.
- API 계약이 확정된 뒤 지연·오류 상태를 반복 재현하기 어렵다면 MSW 같은 Front-end 테스트 도구를 선택적으로 검토할 수 있습니다.
- 성능 문제가 생기면 느낌으로 판단하지 않고 Browser 도구를 이용해 Network, Rendering과 사용자 체감 지표를 확인합니다.
- 기능과 외부 입력이 늘어나면 보안 경계, 개인정보 노출과 의존성 변경을 함께 검토합니다.
- WebView 기능이 늘어나면 승인된 Native App 계약을 기준으로 Bridge Adapter와 호출 범위를 확장합니다.

구체적인 운영 절차와 담당 체계는 아직 정하지 않습니다. 현재는 운영과 확장 과정에서 구조가 무너지지 않도록 기술적인 판단 기준을 준비한 상태입니다.

## 5. 현재 확정하지 않은 내용

이 저장소는 Front-end 가이드이므로 Front-end에서 독립적으로 결정할 수 없는 사항은 미리 확정하지 않았습니다.

- 화면 기획과 상세 업무 규칙
- API Endpoint, 요청·응답 형식과 오류 계약
- 인증, Cookie 또는 Token과 Session 처리 방식
- Backend가 제공할 개발·테스트 환경
- Flutter Native App과 Bridge의 실제 Method 및 메시지 형식
- 배포, 모니터링과 장애 대응 체계
- CSP, CORS, 허용 Origin과 개인정보 보존 정책
- 기능별 Timeout, Retry와 Offline 지원 범위

이 항목들은 관련 기획과 계약이 정해진 뒤 담당자와 협의하여 실제 코드와 가이드에 반영합니다. Swagger 또는 OpenAPI가 제공될 것이라고 미리 가정하지 않으며, Backend가 전달하고 승인한 계약 형식을 기준으로 작업합니다.

## 6. 가이드 활용 방식

- 구축할 기능과 관련된 사람용 가이드에서 상세 기준을 확인합니다.
- AI 작업에는 필요한 범위의 AI용 요약 문서를 제공합니다.
- 실제 구현이 시작되면 생성된 프로젝트와 설치된 Package를 우선 확인합니다.
- 가이드의 예시를 그대로 복사하지 않고 실제 구조에 필요한 부분만 적용합니다.
- 실제 코드와 확정된 프로젝트 계약을 최종 기준으로 사용합니다.
- 구현 결과와 반복되는 문제가 확인되면 그 근거로 가이드를 보완합니다.

## 7. 마무리

Front-end 구축 기준은 현재 어느 정도 준비됐으며, 앞으로 이 가이드를 기준으로 개발을 진행할 예정입니다.

목표는 처음부터 복잡한 구조를 만드는 것이 아니라, 현재 필요한 기능을 일관된 방식으로 구현하면서 이후 운영과 기능 확장에 대응할 수 있는 구조를 만드는 것입니다.

프로젝트 전체 협의가 필요한 내용은 임의로 정하지 않고, 진행 과정에서 확정되는 기획·Backend·Native App·배포 조건을 반영하여 구체화하겠습니다.

> Front-end를 어떤 기준으로 구축하고, 이후에도 이해하고 확장할 수 있는 구조를 어떻게 준비할 것인지 공유하는 것이 이번 브리핑의 핵심입니다.
