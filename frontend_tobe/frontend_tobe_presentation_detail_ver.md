# Front-End 전환 방향 및 구축 계획

## 1. 논의 목적

이번 논의에서는 현재 앱 구조의 불편을 짚고, 웹과 Native 영역을 분리한 하이브리드 앱으로의 전환 방향을 제안한다. 함께 정리할 내용은 다음과 같다.

- AS-IS 분석 결과와 TO-BE 방향
- 모바일 앱과 웹의 통신 브릿지 규격 초안
- Front-End 기술 스택과 선정 근거
- GitLab CI/CD 기반 배포 흐름

---

## 2. AS-IS 분석

현재 앱은 Android와 iOS가 각각 구현되어 있다. 플랫폼별로 기능을 따로 개발하고 빌드해야 하므로 같은 변경 사항을 중복 반영하는 일이 잦다. 작은 화면 수정이나 콘텐츠 변경에도 앱 빌드와 배포가 필요해 대응 속도가 느리고, 플랫폼 간 기능 차이가 생길 가능성도 크다.

### 주요 과제

| 구분 | 현재 상황 | 영향 |
|---|---|---|
| 개발 | Android와 iOS를 각각 구현 | 중복 개발 및 유지보수 비용 증가 |
| 배포 | 화면 변경에도 앱 빌드가 필요 | 긴급 수정과 서비스 개선 속도 저하 |
| 품질 | 플랫폼별 구현과 배포 시점이 다름 | 기능 및 사용자 경험의 편차 발생 |
| 운영 | 웹과 앱의 책임 범위가 불분명 | 장애 원인 파악과 담당 조직 간 협업이 어려움 |
| 확장 | 신규 기능마다 양쪽 앱을 함께 수정 | 일정 예측이 어렵고 회귀 테스트 범위가 커짐 |

---

## 3. TO-BE 방향

TO-BE는 서비스 화면을 웹으로 통합하고, 디바이스 기능은 Native가 맡는 하이브리드 앱 구조다.

- 웹 영역: 서비스 화면, 콘텐츠, 업무 규칙처럼 빠른 변경이 필요한 기능
- Native 영역: 푸시 알림, 위치 정보, 카메라, 생체 인증처럼 디바이스 권한과 기능이 필요한 영역
- 브릿지 영역: 웹과 Native가 정해진 메시지 형식으로 요청과 결과를 주고받는 통신 계층

웹 영역은 앱을 다시 빌드하지 않고 배포할 수 있다. Native 기능이 바뀔 때만 Android와 iOS 앱을 빌드한다. 이 구조를 적용하면 서비스 변경 속도를 높이면서도 디바이스 기능을 안정적으로 사용할 수 있다.

### 기대 효과

| 항목 | 기대 효과 |
|---|---|
| 개발 생산성 | 공통 화면을 한 번 구현해 Android와 iOS에서 사용 |
| 배포 속도 | 웹 변경은 앱 심사 없이 배포 가능 |
| 품질 관리 | 공통 UI와 업무 규칙을 한 코드베이스에서 관리 |
| 유지보수 | 웹, Native, 브릿지의 책임 범위를 명확히 구분 |
| 확장성 | 새로운 Native 기능은 브릿지 API를 추가하는 방식으로 확장 |

> 앱 심사 정책, 보안 정책 또는 Native 기능과 강하게 결합된 화면은 웹 즉시 배포 대상에서 제외한다.

## 4. 모바일 앱–웹 통신 브릿지 규격 초안

### 4.1 기본 원칙

1. 모든 메시지는 JSON 형식을 사용한다.
2. 웹은 Native에 등록된 메서드만 호출할 수 있다.
3. 요청마다 `requestId`를 부여해 응답과 연결한다.
4. 성공과 실패 응답은 같은 구조를 사용한다.
5. 브릿지 버전을 명시하고 하위 호환성을 유지한다.
6. 인증 토큰과 개인정보는 로그에 남기지 않는다.

### 4.2 통신 방향

| 방향 | 용도 | 예시 |
|---|---|---|
| Web → Native | 디바이스 기능 요청 | 위치 조회, 카메라 실행, 알림 설정 화면 이동 |
| Native → Web | 요청 결과 반환 | 위치 정보, 권한 상태, 촬영 결과 |
| Native → Web Event | 앱 상태나 외부 이벤트 전달 | 푸시 수신, 네트워크 변경, 앱 복귀 |

### 4.3 공통 요청 형식

```json
{
  "bridgeVersion": "1.0",
  "requestId": "req-20260722-0001",
  "method": "location.getCurrentPosition",
  "params": {
    "accuracy": "high",
    "timeoutMs": 5000
  }
}
```

| 필드 | 필수 | 설명 |
|---|---:|---|
| `bridgeVersion` | Y | 브릿지 규격 버전 |
| `requestId` | Y | 요청과 응답을 연결하는 고유 값 |
| `method` | Y | 호출할 Native 메서드명 |
| `params` | N | 메서드에 전달할 값 |

### 4.4 공통 응답 형식

성공 응답:

```json
{
  "bridgeVersion": "1.0",
  "requestId": "req-20260722-0001",
  "success": true,
  "data": {
    "latitude": 37.5665,
    "longitude": 126.9780
  }
}
```

실패 응답:

```json
{
  "bridgeVersion": "1.0",
  "requestId": "req-20260722-0001",
  "success": false,
  "error": {
    "code": "PERMISSION_DENIED",
    "message": "위치 권한이 허용되지 않았습니다."
  }
}
```

### 4.5 Native 이벤트 형식

```json
{
  "bridgeVersion": "1.0",
  "event": "push.received",
  "data": {
    "notificationId": "notice-1024",
    "type": "NOTICE"
  }
}
```

### 4.6 1차 지원 메서드

| 메서드 | 설명 | 주요 반환값 |
|---|---|---|
| `app.getInfo` | 앱 및 OS 정보 조회 | 앱 버전, OS, 브릿지 버전 |
| `auth.getAccessToken` | 인증 토큰 요청 | Access Token 또는 오류 코드 |
| `permission.getStatus` | 권한 상태 조회 | granted, denied, blocked |
| `permission.request` | 권한 요청 | 변경된 권한 상태 |
| `location.getCurrentPosition` | 현재 위치 조회 | 위도, 경도, 정확도 |
| `push.getToken` | 푸시 토큰 조회 | FCM 또는 APNs 토큰 |
| `camera.open` | 카메라 실행 | 파일 식별자 또는 취소 상태 |
| `browser.openExternal` | 외부 브라우저 실행 | 실행 성공 여부 |
| `app.openSettings` | 앱 설정 화면 이동 | 실행 성공 여부 |
| `navigation.closeWebView` | WebView 종료 | 처리 결과 |

### 4.7 표준 오류 코드

| 코드 | 의미 | 웹 처리 기준 |
|---|---|---|
| `INVALID_REQUEST` | 요청 형식 또는 필수 값 오류 | 사용자 입력 및 요청 값 확인 |
| `METHOD_NOT_FOUND` | 지원하지 않는 메서드 | 앱 최소 버전 안내 |
| `PERMISSION_DENIED` | 권한 거부 | 권한 필요 사유와 재요청 안내 |
| `USER_CANCELLED` | 사용자가 작업 취소 | 기존 화면 유지 |
| `TIMEOUT` | 제한 시간 초과 | 재시도 제공 |
| `NATIVE_ERROR` | Native 처리 중 오류 | 공통 오류 안내 및 로그 식별자 수집 |
| `UNSUPPORTED_VERSION` | 호환되지 않는 브릿지 버전 | 앱 업데이트 안내 |

### 4.8 보안 및 운영 기준

- 허용한 웹 도메인에서만 브릿지를 호출할 수 있도록 제한한다.
- `method`별 입력 스키마를 검사하고 허용되지 않은 호출은 차단한다.
- Access Token은 브릿지 응답 후 웹 저장소에 장기 보관하지 않는다.
- 개인정보, 인증 정보, 위치 좌표는 운영 로그에서 마스킹한다.
- 오류 로그에는 `requestId`, 앱 버전, OS, 메서드명만 남겨 추적성을 확보한다.
- 브릿지 변경은 Android, iOS, Web 담당자가 함께 리뷰한다.

### 4.9 버전 관리

- 형식: `major.minor`
- 기존 필드를 유지한 선택 필드 추가는 minor 버전을 올린다.
- 필드 삭제나 의미 변경처럼 호환성을 깨는 변경은 major 버전을 올린다.
- 웹은 현재 버전과 직전 major 버전을 지원하는 것을 기본 원칙으로 한다.
- 신규 메서드를 사용하기 전 `app.getInfo`로 지원 여부를 확인한다.

## 5. Front-End 기술 스택

| 구분 | 기술 |
|---|---|
| Framework | Next.js 16.x (App Router) |
| UI Library | React 19.x |
| Language | TypeScript 6.x |
| Styling | Tailwind CSS 4.x + SCSS |
| Server State | TanStack Query 5.x |
| Global UI State | Zustand |
| Form & Validation | React Hook Form 7.x |
| Component | shadcn/ui |

### 5.1 선정 근거와 고려 사항

#### Next.js 16.x (App Router)

라우팅, 레이아웃, 코드 분할과 서버 기능을 한 프레임워크에서 관리할 수 있다. App Router를 기준으로 화면 구조를 통일하면 서비스가 커져도 기능 단위로 나누기 쉽다.

- 장점: 파일 기반 라우팅, 공통 레이아웃, 빌드 최적화, 넓은 React 생태계
- 고려 사항: WebView 환경에서는 서버 렌더링이 꼭 필요한 화면과 정적 또는 클라이언트 렌더링 화면을 구분해야 한다.

#### React 19.x

컴포넌트 중심으로 화면을 나눠 공통 UI를 재사용하기 좋다. Next.js와 결합했을 때 개발 도구와 인력 수급 측면에서도 유리하다.

- 장점: 높은 재사용성, 큰 생태계, 검증된 개발 방식
- 고려 사항: 불필요한 상태 변경과 렌더링을 줄이기 위한 컴포넌트 설계 기준이 필요하다.

#### TypeScript 6.x

웹과 Native 사이의 메시지 형식, API 응답, 화면 속성을 타입으로 관리한다. 브릿지 규격을 타입으로 정의하면 플랫폼별 구현 차이를 개발 단계에서 발견하기 쉽다.

- 장점: 컴파일 단계 오류 탐지, 자동 완성, 안전한 구조 변경
- 고려 사항: 공통 타입의 소유 주체와 배포 방식을 정해야 한다.

#### Tailwind CSS 4.x + SCSS

일반 화면은 Tailwind CSS로 빠르고 일관되게 구성한다. 복잡한 스타일 규칙이나 기존 자산을 옮겨야 할 때는 SCSS를 보완적으로 사용한다.

- 장점: 빠른 UI 구현, 디자인 토큰 적용, 사용하지 않는 스타일 최소화
- 고려 사항: 같은 역할의 스타일을 Tailwind CSS와 SCSS에 중복 작성하지 않도록 기준을 둔다.

#### TanStack Query 5.x

서버에서 받은 데이터의 조회, 캐시, 재시도와 갱신 상태를 관리한다. API 데이터와 UI 상태를 분리해 화면 코드를 단순하게 유지할 수 있다.

- 장점: 캐시와 로딩·오류 상태 표준화, 중복 요청 감소
- 고려 사항: 데이터별 캐시 시간과 앱 복귀 시 재조회 정책을 정해야 한다.

#### Zustand

모달, 토스트, 임시 선택값처럼 여러 화면이 공유하는 UI 상태를 가볍게 관리한다. 서버 데이터는 TanStack Query가 맡고, Zustand에는 필요한 UI 상태만 둔다.

- 장점: 단순한 API, 적은 코드, 필요한 상태만 구독 가능
- 고려 사항: 모든 상태를 전역으로 올리지 않도록 사용 범위를 제한한다.

#### React Hook Form 7.x

입력 항목이 많은 화면에서도 불필요한 렌더링을 줄이면서 폼 상태를 관리한다. 검증 스키마와 연계하면 오류 메시지와 제출 조건을 일관되게 적용할 수 있다.

- 장점: 성능, 적은 코드, 유연한 검증 연계
- 고려 사항: 공통 입력 컴포넌트의 오류 표시와 접근성 규칙을 먼저 정한다.

#### shadcn/ui

컴포넌트 코드를 프로젝트가 직접 소유하므로 디자인 요구에 맞게 수정하기 쉽다. 외부 패키지의 고정된 스타일에 묶이지 않으면서 접근성 기반 컴포넌트를 출발점으로 삼을 수 있다.

- 장점: 높은 수정 자유도, 코드 소유권, Tailwind CSS와의 자연스러운 결합
- 고려 사항: 가져온 컴포넌트의 업데이트와 사내 디자인 시스템 반영은 프로젝트가 관리해야 한다.

## 6. GitLab CI/CD 배포 흐름

### 6.1 전체 흐름

```text
개발자 Push
  → Merge Request
  → 코드 품질 검사
  → 단위·통합 테스트
  → Web 빌드
  → Review 환경 배포
  → 코드 리뷰 및 승인
  → main 병합
  → Staging 배포·검증
  → Production 승인
  ├─ Web: 운영 환경 즉시 배포
  └─ Native 변경 시: Android/iOS 빌드 → 서명 → 배포 채널 업로드
```

### 6.2 권장 파이프라인 단계

| 단계 | 주요 작업 | 실패 시 처리 |
|---|---|---|
| `validate` | 패키지 잠금 파일, 환경 설정, 브릿지 스키마 검사 | 즉시 중단 |
| `quality` | Lint, TypeScript 타입 검사, 코드 규칙 검사 | Merge 차단 |
| `test` | 단위 테스트, API Mock 테스트, 브릿지 계약 테스트 | Merge 차단 |
| `build_web` | Next.js Web 산출물 생성 | 배포 중단 |
| `review` | Merge Request별 임시 환경 배포 | 리뷰어 확인 후 진행 |
| `deploy_staging` | Staging Web 배포 | 운영 배포 차단 |
| `e2e` | 핵심 사용자 흐름과 WebView 연동 검사 | 운영 배포 차단 |
| `deploy_production` | 승인 후 Web 운영 배포 | 직전 버전 유지 |
| `build_native` | 브릿지 또는 Native 변경 시 Android/iOS 빌드 | 해당 플랫폼 배포 중단 |
| `release_native` | 서명 후 내부 테스트 또는 Store 배포 | 기존 앱 버전 유지 |

### 6.3 변경 범위에 따른 배포 분기

#### Web만 변경된 경우

`web/` 또는 공통 UI 변경만 있으면 Web 파이프라인을 실행한다. 테스트와 승인 후 운영 서버에 배포하며 Android와 iOS 앱은 다시 빌드하지 않는다.

#### 브릿지 또는 Native가 변경된 경우

`android/`, `ios/`, 브릿지 스키마가 바뀌면 Web 테스트와 함께 플랫폼별 빌드를 실행한다. 브릿지 계약 테스트를 통과한 뒤 내부 배포 채널에서 호환성을 확인하고 Store 배포를 진행한다.

### 6.4 브랜치와 환경 운영안

| Git 기준 | 배포 환경 | 운영 방식 |
|---|---|---|
| Feature Branch | Review | Merge Request별 임시 URL 생성 |
| `develop` | Development | 개발자 통합 확인 |
| `main` | Staging | 운영 후보 버전 검증 |
| Version Tag | Production | 승인된 버전만 운영 배포 |

프로젝트가 trunk-based development를 채택하면 `develop` 없이 짧은 Feature Branch와 `main`만 운영할 수 있다. 어떤 방식을 쓰더라도 운영 배포는 보호된 브랜치·태그와 승인 절차를 적용한다.

### 6.5 품질 게이트

- Merge Request 승인 전 Lint, 타입 검사, 단위 테스트를 모두 통과해야 한다.
- 브릿지 변경에는 Android, iOS, Web 담당자 리뷰가 각각 필요하다.
- 운영 배포 전 Staging에서 로그인, 주요 화면, 푸시 이동, 위치 권한 흐름을 확인한다.
- Native 배포는 내부 테스트 채널 검증 후 Store 심사 단계로 넘긴다.
- 배포 후 모니터링 기준을 충족하지 못하면 직전 안정 버전으로 되돌린다.

### 6.6 버전과 롤백

- Web 산출물에는 Commit SHA와 배포 시간을 기록한다.
- Native 앱은 앱 버전, 빌드 번호, 지원 브릿지 버전을 함께 관리한다.
- Web은 직전 배포 산출물을 보관해 즉시 롤백할 수 있도록 한다.
- Native는 배포 후 바이너리를 되돌리기 어려우므로 기능 플래그와 서버 차단 장치를 준비한다.
- 새로운 브릿지 기능은 앱 보급률을 확인한 뒤 웹에서 활성화한다.

### 6.7 비밀정보 관리

- 서명 키, 배포 토큰, API 키는 GitLab의 Protected·Masked Variable로 관리한다.
- 운영 비밀정보는 보호된 브랜치와 Runner에서만 사용할 수 있도록 제한한다.
- 로그와 빌드 산출물에 비밀정보가 포함되지 않는지 자동 검사한다.
- Android와 iOS 서명 권한은 최소 인원에게만 부여하고 변경 이력을 남긴다.

## 9. 결론

공통 서비스 화면은 웹으로 통합하고 디바이스 기능은 Native에 남긴다. 두 영역은 버전이 명시된 브릿지 규격으로 연결한다. Web 변경은 빠르게 배포하고, Native 변경은 플랫폼별 검증과 Store 배포 절차를 거친다. 이 구조의 핵심은 단순히 WebView를 도입하는 데 있지 않다. 웹과 Native의 책임, 통신 규격, 배포 기준을 함께 정해야 운영 속도와 안정성을 모두 확보할 수 있다.
