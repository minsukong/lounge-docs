FRONT-END

Front-End AS-IS / TO-BE

1. AS-IS

현재 앱은 WebView 방식이며 Android와 iOS 소스가 별도로 관리되고 있습니다.

플랫폼별 소스가 분리되어 있어 앱 기능을 변경할 때 Android와 iOS를 각각 확인하고 빌드해야 합니다. 같은 기능이라도 플랫폼에 따라 구현 방식이나 적용 시점이 달라질 수 있어 개발과 운영에 부담이 생깁니다.

구분 현재 상황
앱 구조 WebView 방식으로 서비스하고 있습니다.
소스 관리 Android와 iOS 소스를 별도로 관리하고 있습니다.
개발 앱 기능 변경 시 두 플랫폼을 각각 확인해야 합니다.
빌드 Android와 iOS 빌드를 따로 진행해야 합니다.
운영 플랫폼별 기능 차이와 배포 시점 차이가 생길 수 있습니다.

2. TO-BE

서비스 화면은 웹으로 통합하고, 디바이스 기능은 Native가 담당하는 구조로 개선합니다.

  • 화면, 콘텐츠, 서비스 기능은 웹에서 제공합니다.
  • 푸시 알림, 위치 정보, 카메라 등은 Native가 담당합니다.
  • 웹과 Native는 정해진 브릿지 규격으로 정보를 주고받습니다.
  • 웹 변경은 앱 빌드 없이 배포합니다.
  • Native 또는 브릿지가 변경될 때만 Android와 iOS 앱을 빌드합니다.
구분 TO-BE 방향
서비스 화면 웹으로 통합해 Android와 iOS에서 함께 사용합니다.
디바이스 기능 Native 영역에서 안정적으로 제공합니다.
연동 방식 공통 브릿지 규격을 적용합니다.
웹 배포 앱 빌드 없이 빠르게 반영합니다.
앱 배포 Native 또는 브릿지 변경 시에만 진행합니다.

기대 효과

  • 같은 화면과 기능을 중복 개발하는 작업을 줄일 수 있습니다.
  • 서비스 변경 사항을 더 빠르게 반영할 수 있습니다.
  • Android와 iOS의 화면과 동작을 일관되게 유지할 수 있습니다.
  • 웹과 Native의 담당 범위가 분명해집니다.
  • 장애가 발생했을 때 원인을 더 빠르게 확인할 수 있습니다.

3. 웹–Native 브릿지

브릿지는 웹과 Native가 정보를 주고받기 위한 공통 규격입니다.

예를 들어 웹에서 위치 정보가 필요하면 Native에 요청합니다. Native는 사용자의 권한을 확인한 뒤 위치 정보를 웹에 전달합니다. 푸시 알림을 눌렀을 때 특정 웹 화면으로 이동하는 기능도 브릿지를 통해 처리합니다.

Next.js 통신 예시

Next.js 화면에서 위치 정보가 필요할 때 브릿지에 요청을 보냅니다. Native는 요청을 처리한 뒤 결과를 다시 웹에 전달합니다. 

Next.js 화면
  → Native에 위치 정보 요청
  → Android 또는 iOS에서 권한 확인
  → Native가 처리 결과 전달
  → Next.js 화면에 결과 반영

Next.js에서는 Android와 iOS의 차이를 공통 함수 안에서 처리합니다. 화면에서는 플랫폼을 구분하지 않고 같은 함수를 호출합니다. 

'use client';

function requestLocation() {
  const bridgeWindow = window as any;
  const message = JSON.stringify({
    requestId: crypto.randomUUID(),
    method: 'location.getCurrentPosition',
    params: {},
  });

  // Android WebView
  if (bridgeWindow.AppBridge) {
    bridgeWindow.AppBridge.postMessage(message);
    return;
  }

  // iOS WebView
  bridgeWindow.webkit?.messageHandlers?.AppBridge?.postMessage(message);
}

Native는 처리 결과를 Next.js에 등록된 이벤트로 전달합니다.

useEffect(() => {
  const handleNativeMessage = (event: Event) => {
    const result = (event as CustomEvent).detail;
    console.log('Native 응답:', result);
  };

  window.addEventListener('nativeMessage', handleNativeMessage);
  return () => window.removeEventListener('nativeMessage', handleNativeMessage);
}, []);

위 코드는 통신 방식에 대한 간단한 예시입니다. 실제 객체명, 메시지 형식, 응답 방식은 Android, iOS, 웹 담당자가 브릿지 규격을 확정한 뒤 적용합니다.

기본 원칙

  • 요청과 응답 형식을 통일합니다.
  • Android와 iOS에서 같은 기능명과 결과 형식을 사용합니다.
  • 성공과 오류에 대한 처리 기준을 함께 정의합니다.
  • 인증 정보와 개인정보는 안전하게 전달하고 기록에 남기지 않습니다.
  • 브릿지에 버전을 부여해 이전 앱과의 호환성을 관리합니다.

우선 정의할 기능

기능 설명
앱 정보 앱 버전과 운영체제 정보를 확인합니다.
인증 웹과 Native 사이에서 인증 정보를 전달합니다.
권한 위치, 알림, 카메라 권한을 확인하고 요청합니다.
위치 현재 위치 정보를 웹에 전달합니다.
푸시 알림 수신과 화면 이동을 연결합니다.
카메라 촬영 기능을 실행하고 결과를 전달합니다.

브릿지 규격은 Android, iOS, 웹 담당자가 함께 검토한 뒤 확정합니다.

4. 오프라인 대응

한 번 접속한 서비스 화면과 필요한 파일을 디바이스에 저장해 두면, 네트워크가 없는 상황에서도 일부 기능을 사용할 수 있습니다.

다만 모든 기능을 오프라인으로 제공할 수 있는 것은 아닙니다. 화면과 정적 콘텐츠처럼 서버 통신이 필요하지 않은 기능은 오프라인에서도 제공하고, 로그인이나 실시간 조회처럼 서버 확인이 필요한 기능은 실행을 제한합니다.

구분 오프라인 동작 예시
저장 가능한 기능 사용 가능 기본 화면, 안내 콘텐츠, 이미지, 최근 조회 정보
디바이스 기능 부분적 사용 가능 QR 코드 확인 및 디바이스에 저장된 정보 등은 사용 가능
서버 통신 기능 사용 불가 로그인, 실시간 조회, 데이터 등록·수정, 결제

동작 방식

  1. 온라인 상태에서 Next.js 화면과 필요한 파일을 디바이스에 저장합니다.
  2. 오프라인이 되면 저장된 화면과 데이터를 우선 보여줍니다.
  3. 화면 상단에 오프라인 상태임을 안내합니다.
  4. 서버 통신이 필요한 기능은 비활성화하고 온라인 연결이 필요하다는 메시지를 표시합니다.
  5. 네트워크가 복구되면 최신 화면과 데이터로 갱신합니다.

오프라인 상태입니다. 저장된 정보만 확인할 수 있으며, 로그인·조회·등록 기능은 네트워크 연결 후 이용할 수 있습니다.

구현 시 고려 사항

  • 오프라인 지원 화면과 필수 파일을 미리 정합니다.
  • Next.js의 정적 화면과 클라이언트에서 실행되는 기능을 중심으로 구성합니다.
  • 캐시된 화면과 데이터에 버전을 부여해 오래된 정보가 계속 노출되지 않도록 합니다.
  • 개인정보나 인증 정보는 오프라인 저장 대상에서 제외하거나 암호화합니다.
  • 웹과 Native가 같은 네트워크 상태를 사용하도록 브릿지에서 연결 상태를 전달합니다.
  • 서버 전송이 필요한 작업을 임시 저장할지는 서비스 정책에 따라 별도로 결정합니다.

5. Front-End 기술 구성

안정성, 개발 편의성, 유지보수성을 기준으로 기술을 선정했습니다.

역할 기술 선정 이유
웹 서비스 Next.js, React 공통 화면을 구성하고 기능별로 관리하기 좋습니다.
개발 언어 TypeScript 개발 과정에서 오류를 미리 확인할 수 있습니다.
화면 스타일 Tailwind CSS, SCSS 일관된 화면을 빠르게 만들고 관리할 수 있습니다.
서버 데이터 TanStack Query 데이터 조회, 갱신, 오류 상태를 관리하기 좋습니다.
화면 상태 Zustand 여러 화면에서 사용하는 상태를 간단하게 관리할 수 있습니다.
입력 화면 React Hook Form 입력값과 오류 메시지를 효율적으로 관리할 수 있습니다.
공통 컴포넌트 shadcn/ui 버튼과 입력창 같은 공통 요소를 서비스에 맞게 구성할 수 있습니다.

각 기술의 역할을 분명하게 나누고, 필요한 범위에서만 사용하겠습니다.

6. GitLab CI/CD 배포 흐름

개발자가 변경 내용을 등록하면 GitLab에서 검사, 테스트, 검토, 배포 과정을 순서대로 진행합니다. 

개발 내용 등록
  → 자동 품질 검사
  → 기능 테스트
  → 검토 환경 배포
  → 담당자 확인 및 승인
  → 운영 환경 배포

웹 변경

웹 화면이나 서비스 기능만 변경된 경우에는 자동 검사와 담당자 확인을 거쳐 웹에 배포합니다. Android와 iOS 앱은 다시 빌드하지 않습니다.

Native 또는 브릿지 변경

디바이스 기능이나 브릿지 규격이 변경된 경우에는 Android와 iOS 앱을 각각 빌드하고 테스트합니다. 내부 검증을 마친 뒤 앱 배포 절차를 진행합니다.

운영 기준

  • 모든 변경 사항은 자동 검사와 담당자 검토를 거칩니다.
  • 운영 배포 전에 주요 기능을 검증합니다.
  • 웹 배포에 문제가 발생하면 직전 버전으로 되돌립니다.
  • 앱 기능에는 비상 시 해당 기능을 중지할 수 있는 장치를 마련합니다.
  • 인증 정보와 배포 권한은 지정된 담당자만 관리합니다.

7. 진행 계획

단계 진행 내용
1 현재 Android, iOS, 웹 소스와 기능을 확인합니다.
2 웹과 Native가 담당할 범위를 정합니다.
3 브릿지 규격 초안을 작성합니다.
4 Android, iOS, 웹 담당자가 함께 규격을 검토합니다.
5 로그인, 위치, 푸시 기능으로 연동 방식을 검증합니다.
6 GitLab CI/CD 환경을 구성합니다.
7 검증된 기능부터 순서대로 적용합니다.

8. 협의가 필요한 사항

  • 웹으로 전환할 화면과 Native에 유지할 기능
  • 브릿지에서 우선 지원할 기능
  • 오프라인에서 제공할 화면과 데이터의 범위
  • Android와 iOS의 최소 지원 버전
  • 인증 정보와 개인정보 처리 방식
  • 개발, 검토, 운영 환경의 승인 담당자
  • 브릿지 규격서 초안 공유일, 리뷰일, 확정일

9. 정리

TO-BE의 핵심은 서비스 화면을 웹으로 통합하고 디바이스 기능은 Native에 두는 것입니다. 두 영역은 공통 브릿지 규격으로 연결합니다.

웹은 빠르게 변경하고 배포할 수 있도록 구성하고, Native는 디바이스 기능을 안정적으로 제공하는 데 집중합니다. 저장된 화면과 콘텐츠는 오프라인에서도 제공하되, 서버 통신이 필요한 기능은 상태를 명확히 안내하고 실행을 제한합니다. 이를 통해 플랫폼별 중복 작업을 줄이고 개발 속도와 운영 안정성을 함께 높이겠습니다.
