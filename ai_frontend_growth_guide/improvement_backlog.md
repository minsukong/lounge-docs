# AI 협업 기반 Front-End 성장 가이드 추후 보완 백로그

## 1. 문서 목적

이 문서는 `ai_frontend_growth_guide`를 추후 보완하기 위해 현재 확인된 문제와 검토 항목을 기록합니다.

현재 프로젝트는 기획 흐름, Backend API 계약, App Bridge 계약과 실제 운영 방식이 확정되지 않았으므로 구체적인 절차, 담당자, 산출물과 승인 기준을 지금 확정하지 않습니다. 프로젝트 기준이 정리된 뒤 이 문서의 항목을 하나씩 검토하여 `draft.md`와 HTML 교육 문서에 반영합니다.

이 문서에 적힌 내용은 확정된 프로젝트 규칙이 아닙니다. 실제 프로젝트 구조와 협업 방식이 결정되기 전까지는 보완 후보로만 사용합니다.

## 2. 현재 문서에 남아 있는 핵심 문제

### 2.1 대상 독자와 문서 역할이 좁음

현재 문서는 주로 한 명의 Front-end 개발자가 AI와 협업하며 성장하는 흐름을 설명합니다. 하지만 실제로 이 과정을 구축하고 운영하는 담당자, 검토자와 Front-end 책임자가 문서를 어떻게 사용해야 하는지는 설명하지 않습니다.

추후 다음 내용을 검토합니다.

- 학습자, 과정 운영자, 검토자와 Front-end 책임자의 역할
- 개발자가 스스로 사용하는 경우와 팀 교육에 사용하는 경우의 차이
- 신규 입사자, 프로젝트 투입 예정자와 기존 개발자의 사용 범위
- 단계 완료와 예외를 최종 판단하는 주체

### 2.2 구축과 운영 절차가 없음

현재 문서는 무엇을 학습하고 검토할지는 설명하지만 과정을 처음 준비하고 반복 운영하는 방법은 제공하지 않습니다.

추후 프로젝트 운영 방식이 정해지면 다음 항목을 보완합니다.

- 과정 최초 구축 순서
- 신규 개발자 온보딩 절차
- 실습 기능을 선택하는 기준
- 단계별 진행, 검토와 보완 흐름
- 질문, 결정과 미확정 항목을 기록하는 위치
- 과정 중단, 재학습과 단계 생략 기준
- 문서 개정, 검토와 폐기 절차

### 2.3 실습을 시작하기 위한 조건이 없음

각 단계에는 AI 요청과 완료 확인이 있지만 어떤 환경과 코드에서 실습하는지는 정해져 있지 않습니다. 프로젝트가 확정되지 않은 현재는 구체적인 저장소와 명령을 작성하지 않습니다.

실제 프로젝트가 준비되면 다음 내용을 확인합니다.

- 실습에 사용할 저장소, 작업 폴더와 브랜치 기준
- 필요한 Node.js와 package 상태
- 단계별 시작 파일과 수정 가능한 범위
- 실행할 Typecheck, Lint, Test와 Build 명령
- 실제 Backend 또는 App 환경이 필요한 단계
- 계약 미확정 상태에서도 진행할 수 있는 실습과 진행하면 안 되는 실습
- 실습 완료 후 남겨야 할 결과물

### 2.4 완료 기준을 동일하게 판단하기 어려움

현재 완료 기준은 대부분 개념을 설명하거나 위험을 발견할 수 있는지를 묻습니다. 이를 어떤 증거로 확인하고 누가 승인하는지는 정해져 있지 않습니다.

추후 다음 항목을 검토합니다.

- 단계별 필수 결과물과 선택 결과물
- 설명, 코드 변경, 테스트 결과와 실제 화면 확인 중 필요한 증거
- 통과, 보완과 재학습을 구분하는 기준
- 자기 점검과 리뷰어 점검의 차이
- 결과 기록 위치와 보관 기간
- 단계별 완료 예시와 미완료 예시

### 2.5 전체 가이드와의 연결이 부족함

현재 문서에는 일부 Front-end, TypeScript, 테스트, 보안과 공통 소스 가이드만 연결되어 있습니다. 실제 구축 흐름에서 사용하는 다른 가이드와 어떤 관계인지 한눈에 알기 어렵습니다.

추후 다음 흐름을 프로젝트 기준에 맞춰 연결합니다.

- Figma 설명과 구현 정보 확인
- AI를 활용한 화면과 컴포넌트 초안 작성
- 기존 컴포넌트와 디자인 토큰 조사
- Storybook에서 컴포넌트 작성과 상태 검증
- 프로젝트 기능에 컴포넌트 연결
- API와 App Bridge 계약 확인
- 테스트, 보안 검토와 병합
- 배포 이후 회귀 확인과 문서·컴포넌트 동기화

실제 프로젝트에서 AI가 읽어야 하는 `AGENTS.md`와 상세 가이드의 관계도 함께 설명해야 합니다.

### 2.6 병합 이후 운영 흐름이 없음

현재 과정은 기능 구현과 병합 전 검토에 집중합니다. 실제 서비스 운영에서 발생하는 변경과 장애를 성장 과정에 어떻게 반영할지는 설명하지 않습니다.

추후 다음 내용을 검토합니다.

- 배포 후 실제 동작과 오류 확인 범위
- 사용자 피드백과 운영 이슈의 재현 방법
- 회귀, Hotfix와 Rollback에서 Front-end가 확인할 항목
- 보안 공지와 의존성 업데이트 대응
- Figma, 코드, Storybook과 가이드의 동기화
- 운영 중 반복해서 발생한 문제를 교육 과정에 되돌리는 방법

Backend, Native App, 배포와 보안 담당의 업무를 Front-end 운영 절차로 확정하지 않습니다. Front-end가 확인하고 협업해야 하는 경계만 프로젝트 책임자와 합의한 뒤 작성합니다.

## 3. 내용 정확성과 문서 간 충돌

### 3.1 TypeScript의 누락 없는 분기 예시

`02-typescript-basics.html`은 `never`를 사용한 누락 없는 분기를 설명하지만 현재 예시는 마지막 상태를 기본 반환으로 처리합니다. 새 상태가 추가되어도 잘못된 표시로 흡수될 수 있으므로 설명과 예시를 일치시켜야 합니다.

추후 판별 가능한 Union, `switch`와 `never`가 실제로 연결되는 예시로 보완합니다.

### 3.2 빈 응답과 JSON 처리 예시

`08-api-contracts-and-errors.html`은 `204`, 빈 본문과 JSON이 아닌 응답을 구분하라고 설명하지만 현재 예시는 모든 성공 응답에 `response.json()`을 호출합니다.

Backend 계약과 공통 요청 계층이 확정된 뒤 실제 응답 처리 기준에 맞는 예시로 교체합니다. 계약이 정해지기 전에는 특정 공통 응답 형식을 가정하지 않습니다.

### 3.3 API 미확정 상태의 Parser와 Fixture 기준

`03-typescript-boundaries.html`은 계약이 미확정인 Parser와 Fixture를 임시 가정으로 표시할 수 있는 것처럼 설명하지만 `12-feature-integration-and-review.html`은 계약 확정 전 구현하지 않도록 안내합니다.

현재 프로젝트 기준은 기획 흐름과 Backend API 계약이 승인되기 전 Request, Response, Parser, Fixture와 Mock Handler를 구현하지 않는 것입니다. 추후 관련 교육 문서의 문장을 동일한 기준으로 맞춥니다.

### 3.4 Next.js 코드 예시의 파일 경계

`06-nextjs-app-router.html`은 Server Component와 Client Component를 하나의 코드 블록에 이어서 보여줍니다. 초급자가 한 파일로 복사하면 `use client` 지시문의 위치를 잘못 이해할 수 있습니다.

추후 파일별 코드 블록, 파일 이름과 각 파일의 실행 위치를 명확히 구분합니다.

### 3.5 Bridge Adapter 타입 예시

`10-webview-bridge-and-security.html`은 기능별 입력·응답 검증과 최소 노출을 강조하지만 예시의 `request`는 모든 기능을 `unknown` 입력과 출력으로 처리합니다.

App Bridge 계약이 확정된 뒤 capability별 입력, 성공 결과와 오류가 연결되는 예시를 작성합니다. 실제 Method, 전역 객체와 Payload는 App 담당자와 합의하기 전까지 확정하지 않습니다.

### 3.6 Markdown 초안과 HTML 내용 불일치

현재 `index.html`에는 `11. 순차 교육 과정`이 있지만 `draft.md`에는 동일한 내용이 없습니다. 이후 `draft.md`를 기준으로 HTML을 갱신하면 교육 과정 링크가 누락될 수 있습니다.

추후 문서별 원본, 배포본과 수정 순서를 정하고 `draft.md`와 HTML의 내용을 함께 관리합니다.

## 4. 부족한 세부 설명

### 4.1 용어 설명

현재 문서는 여러 기술 용어를 짧은 문장 안에서 사용하지만 처음 접하는 개발자가 실제 코드와 연결할 수 있을 정도로 설명하지 못하는 부분이 있습니다.

추후 다음 용어를 우선 검토합니다.

- JavaScript: Promise, Microtask, Closure, 참조, 얕은 복사, AbortSignal
- TypeScript: Literal Union, Narrowing, 판별 가능한 Union, `never`, `satisfies`, Generic, Type Guard
- React: Props, State, 파생 값, 제어 컴포넌트, Context, Effect, Cleanup, 오래된 Closure
- Next.js: Route, Layout, Server Component, Client Component, Hydration, SSR, SSG, ISR
- 상태 관리: Query Key, Cache, Mutation, 무효화, 낙관적 갱신, Persist
- API와 테스트: Runtime Parser, Fixture, Handler, Mock, Timeout, 취소, 멱등성
- 보안: XSS, CSP, CSRF, CORS, SameSite, Origin, 신뢰 경계와 공급망
- WebView: Bridge, Adapter, Capability, Method, Payload와 요청 식별자

용어를 단순 번역하는 데 그치지 않고 다음 내용을 함께 설명하는 방식을 검토합니다.

1. 한 문장 정의
2. 이 프로젝트에서 필요한 이유
3. 잘못 사용했을 때 생기는 문제
4. 실제 코드에서 확인할 위치
5. 짧은 올바른 예시와 잘못된 예시

### 4.2 코드 예시의 맥락

현재 코드 예시는 핵심 문법을 짧게 보여주지만 파일 위치, 입력 데이터, 실행 결과와 실패 상태가 충분히 설명되지 않습니다.

추후 각 예시에 필요한 범위에서 다음 정보를 추가합니다.

- 예시가 위치하는 파일과 실행 환경
- 생략된 Import와 타입의 출처
- 예시가 전제로 하는 확인된 계약
- 정상 입력과 오류 입력
- 화면 또는 반환값의 예상 결과
- 이 예시가 보장하지 않는 범위

예시를 완전한 애플리케이션처럼 과도하게 확장하지 않고 해당 단계의 핵심 판단을 검증할 수 있는 최소 단위로 유지합니다.

### 4.3 개념에서 실제 업무로 이어지는 설명

현재 문서는 개념과 체크리스트 사이의 연결이 짧습니다. 운영 담당자와 학습자가 동일한 의미로 이해하려면 하나의 기능이 여러 단계를 거치는 예시가 필요합니다.

추후 실제 프로젝트 기능이 정해지면 동일한 작은 기능을 사용해 다음 변화를 연결하는 방식을 검토합니다.

- 사용자 행동과 화면 상태 정의
- Props와 State 구분
- 타입과 외부 입력 검증
- Server·Client 경계
- 기존 UI와 토큰 사용
- API 또는 Bridge 계약 질문
- 로딩, 오류, 취소와 중복 실행 처리
- 테스트와 실제 화면 확인
- 보안과 개인정보 검토
- 병합과 운영 피드백

### 4.4 잘못된 코드와 판단 비교

현재는 권장 원칙이 많지만 개발자가 실제 리뷰에서 발견해야 할 잘못된 코드가 충분하지 않습니다.

추후 다음 형식의 짧은 비교를 검토합니다.

- 왜 문제가 되는가
- 어떤 조건에서 실제 버그가 발생하는가
- 더 단순하거나 안전한 대안은 무엇인가
- AI가 제안했을 때 개발자가 어떤 질문을 해야 하는가

## 5. AI 활용 운영 기준

현재 문서는 AI의 수정 범위와 추측을 통제하는 방법은 설명하지만 회사 환경에서 어떤 AI와 자료를 사용할 수 있는지는 정하지 않습니다.

추후 회사 정책과 도구가 확정되면 다음 내용을 보완합니다.

- 사용할 수 있는 로컬 AI와 외부 AI 도구
- 소스 코드, 기획 자료, 개인정보와 인증정보의 입력 가능 범위
- 회사 계정과 개인 계정 사용 기준
- AI 대화, 생성 코드와 검토 결과의 보관 기준
- 사람이 반드시 승인해야 하는 변경
- AI가 제안한 package의 필요성, License와 보안 검토
- Cline, Claude Code와 Codex 등 도구가 달라도 공통으로 적용할 프로젝트 지침

실제 프로젝트에서는 도구별 설정 파일보다 프로젝트의 `AGENTS.md`를 공통 기준으로 사용하고, 도구 전용 설정에는 해당 도구에서만 필요한 내용을 남기는 원칙을 유지합니다.
