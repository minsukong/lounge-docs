Front-End Monorepo 공통 기준

Front-end 프로젝트가 함께 사용하는 저장소 구조, 공통 코드와 계약, 의존성, CI/CD 및 배포 원칙을 정의합니다.

이 문서는 Front-end 저장소 구조의 단일 기준입니다. app/app.html과 frontend_guide/index.html은 영역별 상세 구현을 설명하며, 저장소 구조와 운영 기준이 충돌하면 이 문서를 우선합니다.

Draft · Version 0.1 · 2026-08-04

1. 적용 범위와 표기

웹사이트, Flutter 앱, 앱 내 WebView, 카드사 인앱 서비스와 백오피스 등 Front-end 프로젝트를 하나의 저장소에서 관리합니다. 실제 저장소 이름은 아직 정하지 않았으므로 이 문서에서는 <repository-root>로 표현합니다.

표시 의미 적용 방법
MUST 확정 원칙 구현, 검수와 배포에서 반드시 준수
TBD 결정 필요 담당자 합의와 승인 후 이 문서에 반영
EXAMPLE 참고 예시 프로젝트 조건에 맞게 변경 가능

2. 저장소 구조

<repository-root>/
├── apps/
│   ├── website/                 # 대외 웹사이트
│   ├── mobile/                  # Flutter Native 앱
│   ├── app-webview/             # Front-end · 앱 내 Next.js WebView
│   ├── card-inapp/              # 카드사 인앱 서비스
│   └── backoffice/              # 운영·관리자 백오피스
├── packages/
│   ├── ui/                      # 검증된 Web 공통 UI
│   ├── api-client/              # Web API Client와 생성 Type
│   ├── webview-bridge/          # WebView Bridge 호출 Adapter
│   ├── config/                  # Web 공통 개발 설정
│   ├── testing/                 # Web 공통 테스트 설정
│   └── utils/                   # Web 범용 유틸리티
├── contracts/
│   ├── api/                     # API Schema와 생성 기준
│   └── webview-bridge/          # 플랫폼 중립 Bridge 요청·응답 규격
├── tooling/                     # 저장소 운영 및 자동화 도구
└── README.md

애플리케이션 범위

Directory 역할 기술·분리 상태
apps/website 대외 웹사이트 Framework 및 배포 단위 TBD
apps/mobile Flutter Native 앱과 기기 기능 Flutter Toolchain
apps/app-webview 앱 내 Front-end 서비스 화면과 업무 흐름 Next.js·React·TypeScript
apps/card-inapp 카드사 인앱 서비스 제휴사별 분리 방식과 Framework TBD
apps/backoffice 운영·관리자 업무 Framework 및 배포 단위 TBD

카드사마다 독립 배포와 인증·보안 정책이 필요하면 apps/card-inapp/<partner>로 분리합니다. 동일 애플리케이션에서 설정만 구분할 수 있다면 하나의 프로젝트로 유지합니다. TBD

3. Directory 책임

영역 책임 금지 사항
apps 독립적으로 빌드·테스트·배포 가능한 애플리케이션 다른 앱의 내부 소스 경로를 직접 Import하지 않음
packages 둘 이상의 Web 애플리케이션에서 검증된 공통 구현 예상되는 재사용만으로 빈 패키지나 Wrapper를 만들지 않음
contracts 언어에 종속되지 않는 API·Bridge Schema와 Version 계약 특정 앱의 화면 상태나 구현 세부사항을 포함하지 않음
tooling 저장소 전체에서 사용하는 자동화와 운영 도구 애플리케이션 업무 로직을 포함하지 않음

4. 공통화와 계약 관리

  • 특정 기능이나 애플리케이션에서만 사용하는 코드는 해당 영역 가까이에 둡니다.
  • 둘 이상의 실제 사용처가 있고 의미와 변경 이유가 같을 때만 packages로 이동합니다.
  • Web 공통 UI는 packages/ui, WebView 전용 조합과 Wrapper는 apps/app-webview/src/components에서 관리합니다.
  • API와 Bridge의 플랫폼 중립 원본은 contracts에서 관리하고, TypeScript와 Dart Type 또는 Adapter는 각 Toolchain에서 별도로 생성하거나 구현합니다.
  • 생성된 Type과 Client를 수동으로 서로 다르게 수정하지 않으며 계약 변경과 생성 결과를 하나의 변경으로 검증합니다.
  • Native 앱과 WebView는 배포 시점이 다르므로 Bridge와 API 계약의 하위 호환성을 유지하고, Breaking Change는 Version을 올려 단계적으로 전환합니다.

5. Workspace와 의존성

  • Web 프로젝트는 하나의 Workspace에서 공통 작업과 의존성 정책을 관리합니다.
  • Flutter는 같은 저장소에 두되 Dart 의존성, Lock File과 빌드 도구를 Flutter Toolchain 기준으로 관리합니다.
  • Web Workspace와 Flutter 등 각 Toolchain의 Lock File을 변경 사항과 함께 검토하고 CI에서 고정 설치합니다.
  • Workspace, 패키지 관리자와 Task Runner 제품은 CI·배포 플랫폼을 확인한 뒤 확정합니다. TBD

6. CI/CD와 Release

  • 각 애플리케이션은 Pipeline, Artifact, 환경 설정, Version, 승인과 Rollback 단위를 분리하며 모노레포 전체를 항상 함께 배포하지 않습니다.
  • 변경 경로와 의존 관계를 기준으로 영향받는 애플리케이션과 패키지의 Lint·Test·Build를 수행합니다.
  • 공통 계약이나 패키지를 변경하면 이를 사용하는 모든 애플리케이션의 회귀 테스트를 수행합니다.
  • 운영 배포는 <app-name>/v<version> 형식의 앱별 Tag와 Release Note를 남기고 해당 Artifact와 연결합니다.
  • Flutter 앱은 Codemagic 기준을 적용하고, 웹 애플리케이션의 배포 플랫폼과 품질 Gate는 인프라 환경을 확인한 뒤 확정합니다. TBD

7. 환경과 Secret

  • dev·qa·prod 환경과 배포 권한은 애플리케이션별로 분리합니다.
  • API Endpoint, 인증 Client, Host, Cookie 범위, CORS·CSP, Redirect URI와 Origin Allowlist는 서비스·제휴사·환경별 승인 값으로 관리합니다.
  • 브라우저에 노출 가능한 공개 설정과 서버·CI에서만 사용하는 Secret을 구분합니다.
  • Signing Key, Token과 배포 자격 증명은 저장소, 앱 Bundle, Web JavaScript와 Build Log에 포함하지 않습니다. MUST

8. 변경 기준과 미확정 항목

구조 변경 기준

  • 새 애플리케이션을 추가할 때 Owner, 배포 단위, 환경, 권한과 Rollback 책임을 함께 정의합니다.
  • 새 공통 패키지를 추가할 때 실제 사용처, 공개 API, 의존 방향과 변경 책임을 확인합니다.
  • 계약을 변경할 때 영향을 받는 TypeScript·Dart 생성 결과, Adapter와 출시된 앱 Version을 함께 검토합니다.

우선 결정 항목

  • 실제 저장소 이름
  • Web Workspace, 패키지 관리자와 Task Runner 제품
  • 웹사이트, 카드사 인앱과 백오피스의 Framework 및 최종 분리 범위
  • 카드사별 단일 프로젝트 또는 독립 프로젝트 구성
  • 웹 애플리케이션별 배포 플랫폼과 CI/CD 품질 Gate
