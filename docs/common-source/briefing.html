FRONT-END · COMMON SOURCE BRIEFING

공통 소스 가이드 활용 브리핑

공통 소스 가이드로 시작할 수 있는 범위, 현재 한계와 실제 저장소 적용 순서를 설명합니다.

1. 종합 평가

이 문서 묶음은 Front-end 공통 소스를 안전하게 적용하기 위한 참고 기준입니다. 화면 기획과 제품 계약이 확정되지 않은 항목에는 구현 예시를 적용하지 않고 확인할 항목과 책임 경계만 파악합니다.

가이드의 예시를 한 번에 모두 복사하는 것이 목표는 아닙니다. 실제 앱의 기존 코드와 설치 package를 먼저 확인하고, 사용처가 확인된 항목만 비교·병합해 적용하는 것이 이 가이드의 사용 방식입니다.

모든 가이드는 docs/에 통합되어 있고 애플리케이션 source와 설정은 apps/app-webview/에서 관리합니다. 참고 구현은 실제 사용처, 설치 package와 기존 source를 확인해 선별 적용합니다.

2. 프로젝트 시작에 도움이 되는 부분

영역 가이드가 제공하는 것 실제 적용할 때 확인할 것
UI 설정 디자인 전에도 사용할 수 있는 의미 기반 토큰과 shadcn 설정 브랜드 값, 실제 shadcn 생성 결과와 디자인 기준
React QueryClient 생명주기와 반복되는 폼 동작 예시 서버 상태 사용 여부와 Query 정책, 실제 반복 사용처
TypeScript 공통 검사 강도와 외부 입력을 확인하는 함수 실제 API·Bridge 응답 형식과 기존 compiler 설정
API 요청 응답 본문·HTTP 오류·기능별 parser를 연결하는 경계 기본 URL, 인증 전달, timeout과 실제 오류 계약
세션 로그인 확인·비로그인·로그인 상태와 회원 정보의 분리 세션 응답, 만료·갱신과 로그아웃 뒤 이동
테스트 Client Component와 Query 컴포넌트를 검증하는 환경 설치 버전, 기존 테스트 도구와 실행 명령
API Mock 계약 확정 후에도 실제 환경에서 재현하기 어려운 상태의 선택 도구 Backend 환경 우선, Front-end 범위와 관리 책임
통합 사용 조회·검증·화면 상태·수정·테스트를 연결한 기능 예시 API 경로, 인증, 응답 형식, 문구와 route

Tailwind CSS와 UI 설정은 디자인 값이 바뀌어도 화면 코드의 역할 이름을 유지할 수 있게 합니다. React 공통 코드와 TypeScript 공통 설정과 검사 함수는 서버 상태와 외부 입력을 기능 코드에 연결하는 기준을 제공합니다. API 요청 기반 구현 예시와 세션과 회원 경계 구현 예시는 계약을 추측하지 않고 요청과 로그인 상태의 경계를 준비합니다. 테스트 공통 설정, API Mock 도입 판단 기준과 통합 사용 예시는 실제 요청 흐름을 검증할 범위와 적용 조건을 보여 줍니다.

3. 현재 범위가 적절한 이유

  • 디자인이 확정되지 않아도 중립 토큰으로 화면 구조와 상태 표현을 시작할 수 있습니다.
  • API가 확정되기 전에는 필요한 계약 질문과 응답 검증 지점만 파악하고 구현하지 않습니다.
  • Backend가 준비되지 않은 상태를 Front-end 단독 Mock 계약으로 대신하지 않습니다.
  • 로그인 확인 실패와 비로그인을 구분하고 세션과 회원 상세 데이터가 섞이지 않게 시작할 수 있습니다.
  • 공통 컴포넌트는 반복되는 동작만 담고 API, 화면 이동과 업무 문구를 포함하지 않습니다.
  • 사용처가 없는 Wrapper, 전역 type과 상태 저장 구조를 미리 만들지 않습니다.
  • 각 예시에는 적용 조건, 파일 위치, 사용처와 테스트가 함께 있습니다.

Front-end만 먼저 준비하는 현재 상황에서는 UI 기반과 확인 질문까지만 진행합니다. Backend, 인증과 WebView Bridge 계약은 추측하지 않으며 HTTP 요청, 세션, parser, fixture와 handler는 승인된 계약이 전달된 뒤 구현합니다. Swagger 또는 OpenAPI가 제공될 것이라고 미리 가정하지 않습니다.

4. 적용 순서

  1. Next.js가 생성한 tsconfig, PostCSS 설정과 설치 package를 가이드 예시와 비교합니다.
  2. 기존 설정을 교체하지 않고 Tailwind 토큰과 components.json의 필요한 부분만 병합합니다.
  3. 실제 테스트 실행 도구를 확인한 뒤 필요한 공통 setup만 연결합니다.
  4. 첫 서버 상태 기능이 생길 때 QueryClient와 Provider를 적용합니다.
  5. Backend가 승인한 계약과 개발 환경이 제공되면 공통 request와 기능별 parser를 첫 API에 연결합니다.
  6. 로그인이 필요한 첫 화면에서 세션 Query를 적용하고 회원 상세 데이터와 cache 범위를 분리합니다.
  7. 실제 환경에서 재현하기 어려운 상태가 확인되면 Front-end 책임자 또는 프로젝트 담당자가 Front-end 테스트 범위와 관리 책임을 정해 Mock 도구를 검토합니다. API 동작과 기준 데이터는 승인된 계약을 따릅니다.
  8. 동일한 폼 동작이 반복될 때 SubmitButton과 FormField의 공통 위치를 결정합니다.
  9. 실제 적용 결과에 맞춰 공통 소스 적용 항목의 경로, 교체 지점과 미확정 항목을 갱신합니다.

5. 평가의 한계

예시 코드의 실제 동작 여부는 apps/app-webview에 적용한 뒤 설치 버전에서 typecheck, test와 build로 확인합니다. 문서의 구조, 링크와 코드 표시 검증을 애플리케이션 동작 검증으로 간주하지 않습니다.

Next.js, shadcn과 설치 package의 실제 설정이 예시와 다를 수 있으므로 가이드 파일을 그대로 덮어쓰지 않습니다. 실제 source를 기준으로 삼고, 가이드와 차이가 생기면 적용 이유와 함께 문서를 갱신합니다.

6. 다음 검토 시점

현재 단계에서는 예시의 수를 더 늘리는 것보다 초기화된 앱과 첫 기능에서 기존 예시를 검증하는 것이 우선입니다. 첫 기능을 적용한 뒤 반복되는 코드, 맞지 않는 경로와 빠진 테스트가 확인되면 그 근거로 공통 소스와 가이드를 보완합니다.

따라서 이 가이드는 프로젝트를 시작하기에 충분한 준비 자료로 평가합니다. 다만 프로젝트의 최종 구조나 제품 계약을 대신하지 않으며, 실제 사용처와 검증 결과를 통해 완성해 가는 기준으로 사용합니다.
