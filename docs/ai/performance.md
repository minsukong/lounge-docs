# 네트워크 지연 대응과 성능 핵심 규칙

> 기준 원본: [성능 검증 가이드 초안](../guides/performance/draft.md), [Front-End 개발 가이드](../guides/frontend/index.html)
>
> 이 문서는 AI 코딩용 요약입니다. 충돌하거나 세부 판단이 필요하면 기준 원본을 확인합니다.

## 확인이 필요한 작업

다음 작업에서는 이 문서를 먼저 확인합니다.

- API 조회, 저장, 제출과 삭제
- TanStack Query 상태와 Cache 처리
- Loading, Skeleton, Spinner, Progress와 Toast UI
- Timeout, 재시도, 요청 취소와 중복 실행
- Offline, 연결 복구와 느린 네트워크 대응
- 이미지, 폰트, 외부 Script와 초기 전송 성능

## 필수 상태 구분

- 표시할 데이터가 없는 최초 로딩과 기존 데이터를 유지한 갱신을 구분합니다.
- Loading, Success, Empty, Timeout, Offline과 Error를 하나의 Boolean이나 같은 UI로 처리하지 않습니다.
- 변경 요청은 조회 중 상태와 분리하고 관련 영역에 진행 상태를 표시합니다.
- Cache가 사용 가능하면 재조회 중에도 기존 데이터를 유지하고 필요한 수준에서 갱신 상태를 알립니다.
- 네트워크 오류와 로딩 때문에 사용자 입력을 불필요하게 제거하지 않습니다.

## shadcn/ui 로딩 UI

- 실제 프로젝트의 `src/components/ui`와 설치된 shadcn/ui 소스를 먼저 확인합니다.
- 최종 콘텐츠 구조를 예측할 수 있는 최초 로딩에서 Skeleton을 사용합니다.
- 기존 데이터를 갱신할 때 화면 전체를 Skeleton으로 되돌리지 않습니다.
- 버튼이나 작은 영역의 진행 상태에는 Spinner와 작업 의미를 함께 표시합니다.
- 실제 진행률을 계산할 수 있는 작업에서만 Progress 백분율을 표시합니다.
- 사용자가 읽고 복구해야 하는 Timeout, Offline과 입력 오류를 사라지는 Toast에만 표시하지 않습니다.
- 설치된 shadcn/ui Motion과 프로젝트 토큰을 우선하고 같은 Animation을 다시 만들지 않습니다.
- Motion 감소 설정과 `role="status"`, `aria-live`, `aria-busy` 등 필요한 접근성 정보를 유지합니다.

## 요청 안전성

- 기획 흐름과 Backend API 계약이 확정되기 전에는 endpoint, method, status, 요청·응답 필드, parser, fixture, handler와 Mock을 만들지 않습니다. 확인 질문과 `TBD`만 남기고 승인된 계약이 전달된 뒤 구현합니다.
- Swagger 또는 OpenAPI 제공을 미리 가정하지 않고 실제로 전달된 승인 문서를 기준으로 사용합니다.
- 화면 이동, 검색어나 필터 변경으로 필요 없어진 요청은 `AbortSignal`을 실제 `fetch`까지 전달해 취소합니다.
- 검색어, 필터, 페이지와 사용자처럼 응답을 구분하는 값을 Query Key에 포함합니다.
- 늦게 도착한 이전 응답이 최신 조건의 화면을 덮어쓰지 않게 합니다.
- 저장과 제출 중에는 같은 동작의 연속 실행을 줄입니다.
- Client의 버튼 비활성화만으로 중복 처리가 보장된다고 가정하지 않고 Backend의 멱등성 또는 중복 처리 계약을 확인합니다.
- 서버 처리 결과가 불명확한 Timeout에서 변경 요청의 성공과 실패를 추측하지 않습니다.

## Timeout과 재시도

- 모든 API에 같은 Timeout 숫자를 임의로 적용하지 않습니다.
- Timeout과 사용자가 직접 취소한 요청을 구분합니다.
- 조회 요청은 제한된 재시도를 검토할 수 있지만 무한 재시도하지 않습니다.
- 저장, 결제, 예약과 이용권 사용 같은 변경 요청은 멱등성과 중복 처리 계약이 확인되지 않으면 자동 재시도하지 않습니다.
- API별 Timeout, 재시도 횟수와 간격은 실제 API 처리 시간과 제품 UX가 확정되기 전까지 `TBD`로 유지합니다.

## Offline과 복구

- 연결이 끊겨도 현재 화면과 작성 중인 입력을 가능한 범위에서 보존합니다.
- 서버 확인이 필요한 기능은 사용할 수 없는 이유와 복구 동작을 제공합니다.
- 승인된 Cache를 표시할 때 오래된 데이터일 수 있음을 구분합니다.
- 연결 복구 후 모든 요청을 동시에 실행하지 않고 현재 화면에 필요한 데이터부터 갱신합니다.
- Offline Mutation Queue는 중복, 순서, 보안과 충돌 해결 정책이 확정된 경우에만 도입합니다.

## 검증

- 정상 네트워크와 저속 Network Throttling에서 대표 화면을 확인합니다.
- Chrome 개발자 도구의 Network 탭에서 `Disable cache`와 팀이 선택한 저속 Profile을 적용한 뒤 최초 로딩과 갱신을 확인하고, `Offline` 전환 전·중·후의 화면 보존과 복구를 확인합니다.
- API 처리 지연과 오류 상태는 사용할 수 있는 Backend 개발·테스트 환경에서 먼저 확인하되 별도 재현 환경 제공을 전제로 두지 않습니다.
- 승인된 API 계약이 있고 실제 환경에서 필요한 상태를 반복 재현하기 어렵다면 MSW 같은 도구를 Front-end 테스트 범위에서 선택할 수 있습니다. Front-end 책임자 또는 프로젝트 담당자와 범위·관리 책임을 정하고 Backend에 공유합니다.
- Mock 결과만으로 실제 Backend 연동과 저속 네트워크 검증이 끝났다고 판단하지 않습니다.
- 요청 도중 Offline, 빠른 검색 조건 변경, 버튼 연속 실행과 이전 응답의 늦은 도착을 확인합니다.
- 변경 전후를 같은 기기, Build와 네트워크 조건에서 비교합니다.
- LCP, CLS, INP, 요청 수, 전송량과 Bundle을 확인하되 Lighthouse 종합 점수 하나만으로 합격 여부를 결정하지 않습니다.
- 대표 기기, 네트워크 Profile, 성능 Budget과 CI 실패 기준은 실제 운영 환경이 확인되기 전까지 `TBD`로 유지합니다.
