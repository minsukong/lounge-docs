더라운지 3.0
현재 기준 작업 가능한 내용

기획 확정 전 준비할 수 있는 소스 기반과 공통 UI, 구현 위치와 완료 조건

1. 지금 준비하려는 것과 판단 근거

기획 전체의 완료를 기다리지 않고, 화면 제작에 필요한 실행 환경과 UI 검수 기반부터 준비한다. 업무 규칙과 외부 계약에 의존하는 부분은 해당 합의가 이루어진 뒤 연결한다.

이번 문서의 목적

개발자·기획자·디자이너·리뷰어가 선행 개발의 범위와 이유를 함께 확인하는 것이다. 이 문서는 구현 제안이며, 코드 생성·패키지 설치·개별 작업의 Ready 판정을 수행한 결과가 아니다. 실제 착수 시 작은 작업 단위별로 위치·근거·완료 조건을 정한다.

확인한 현재 상태판단에 미치는 영향근거
lounge-docs는 문서와 참고 골격을 관리한다.제품 소스·빌드·배포는 별도 코드 저장소에 둔다. docs를 제품 번들에 포함하지 않는다.저장소 안내, 프로젝트 핵심 정보
front-end/webview에는 폴더와 .gitkeep만 있다.실행 가능한 앱·공통 컴포넌트·Storybook 설정·package.json이 갖추어졌다고 볼 수 없다. 별도 실제 소스 저장소의 존재와 위치도 아직 확인되지 않았다.WebView 참고 골격 안내 및 해당 폴더의 실제 파일 확인
IA는 화면군의 뼈대이며 확정 작업 목록은 아니다.공통 헤더·오류·로딩 등은 후보로 활용하되, 메뉴·정책·담당·최종 화면 수를 확정하지 않는다.진행 현황과 IA 후보, IA 기준
회원·결제·API·인증·Native Bridge 계약이 미정이다.실제 통신·세션·Bridge·업무 데이터 Mock은 계약 확인 후 구현한다.과업 범위와 미정 사항, 계약 검토

기술 기준은 기존 문서의 Next.js 16 App Router, React 19, TypeScript 6, Tailwind CSS 4, shadcn/ui base-nova를 참조한다. 실제 설치 버전·조합·실행 명령은 코드 저장소를 구성할 때 검증한다. 문서에 언급된 globals.css·components.json·Icon은 현재 참고 골격에서 구현 파일이 확인되지 않았다.

2. 현재 기준으로 나눈 작업 범위

공통 UI도 디자인 없이 완성할 수 있는 것은 아니다. 의미 있는 HTML, label 연결, disabled·focus 등의 기본 동작은 먼저 검토할 수 있지만, 브랜드 색상·크기·variant·문구·배치는 확인된 디자인을 기준으로 정한다.

선행 작업준비할 내용선행 확인 또는 보류 범위
FoundationApp Router 기본 실행, TypeScript·Lint 설정, 스타일 진입점, alias, 최소 README, 설치·빌드 재현실제 저장소 위치와 패키지 조합 확인. 인증 Provider나 환경변수 이름은 계약 없이 만들지 않는다.
Storybook전역 스타일, Components·Features·Screens 분류, 필요한 viewport, 정적 build첫 실제 UI와 함께 설정을 검증한다. 제품에 필요 없는 Provider·Props를 추가하지 않는다.
기본 UIButton·Input·Textarea·Checkbox·Radio·Badge·Skeleton 중 확인된 항목실제 디자인과 사용처에 맞는 항목부터 선정. 변형과 상태를 일괄 생성하지 않는다.
복합 UIDialog·BottomSheet·Select·Tabs·Toast 중 필요한 항목의 포커스·스크롤·키보드 동작닫기 정책, 선택 방식, 모바일 키보드, 디자인 확인 필요. Safari 15에서 핵심 동작 검증.
셸·공통 상태확인된 Header·Navigation, loading·empty·error의 표현 후보Native/WebView 담당, 메뉴 목적지·노출 조건·문구 확인. 업무별 오류 처리 규칙은 별도 합의.

근거: UI 구현 기준, Storybook 기준, 품질 기준. TanStack Query·Zustand·React Hook Form은 실제 데이터·공유 상태·폼 책임이 생기는 시점에 도입한다.

3. 실제 소스는 어디에 두고 왜 나누는가

현재 문서 저장소의 front-end는 참고 골격으로 유지한다. 새 코드 저장소가 필요하다면 Desktop/lounge/lounge-fe를 문서 저장소와 나란히 두는 구성을 제안한다. 이 경로와 저장소 이름은 아직 확정되지 않았으며, 기존 실제 저장소가 확인되면 그 구조를 먼저 따른다.

현재 확인된 참고 구조

lounge-docs/
├── docs/
│   ├── ai/
│   ├── guides/
│   └── workflow/
├── tokens/tokens.json
└── front-end/webview/
    ├── AGENTS.md · README.md
    ├── .storybook/       ← 설정 파일 없음
    └── src/
        ├── app/
        ├── components/ui/
        ├── features/
        ├── lib/
        └── test/
            ↑ 각 영역은 .gitkeep 골격

첫 구현 묶음의 권장 구조

lounge-fe/                ← 새 저장소 제안
├── README.md · AGENTS.md
└── webview/
    ├── package.json · 잠금 파일
    ├── tsconfig.json
    ├── Next · ESLint · PostCSS 설정
    ├── components.json   ← UI 도입 시
    ├── .storybook/
    │   ├── main.ts
    │   └── preview.ts
    └── src/
        ├── app/
        │   ├── layout.tsx
        │   ├── page.tsx
        │   └── globals.css
        └── components/ui/
            ├── button.tsx
            └── button.stories.tsx

위 오른쪽 구조는 생성 완료된 파일 목록이 아니다. Button은 최초 검수 대상의 예이며, 디자인과 사용처를 확인한 컴포넌트로 바꿀 수 있다. 잠금 파일은 선택한 패키지 관리 도구 하나만 사용한다. 설정 확장자와 세부 내용은 실제 버전에 맞춰 정한다.

위치만드는 이유추가하는 시점
src/app라우트·레이아웃·전역 스타일 진입점을 모은다. 업무 로직은 화면 파일에 모두 넣지 않는다.최초 앱 실행부터
src/components/ui여러 화면에서 같은 책임으로 사용하는 기본 UI를 관리한다.첫 공통 UI 구현부터
.storybook와 가까운 Story검수 환경 설정과 UI 소스를 구분하되, 컴포넌트 변경과 Story 변경은 함께 추적한다.첫 UI 구현과 같은 묶음
src/features/<기능>회원·사용처 등 실제 기능의 화면 조합과 상태를 가까이 관리한다.기능의 허용 범위가 정해진 뒤
src/lib, src/test실제 필요한 유틸리티와 테스트 공통 설정을 관리한다.cn 등의 소비자나 공통 테스트 설정이 필요할 때

반응형 홈페이지의 스택과 기능 공유 범위는 TBD다. 확인 전에는 별도 웹 앱·공통 package·전역 Store·Repository 계층을 미리 만들지 않는다.

4. 한 컴포넌트를 만드는 흐름과 검수 이유

대상 후보검수할 상태와 동작만드는 이유
Button확인된 variant, disabled, focus, 긴 문구. loading은 실제 요구가 있을 때.행동의 우선순위와 클릭 가능 상태를 여러 화면에서 일관되게 표현.
Input·Textarealabel·설명·오류 연결, disabled, 입력·키보드 동작. 길이와 검증 정책은 기능별 결정.회원·문의 등 반복 입력 UI의 의미와 접근성을 먼저 검수.
Checkbox·Radio선택·비선택, disabled, label 클릭, 그룹 이름과 키보드 조작.약관·선택 UI에 쓸 기본 조작을 검수. 약관 정책 자체는 별도.
Badge·Skeleton확인된 의미·텍스트·크기, 콘텐츠 대체 관계, 필요한 모션 제한.상태 표시와 로딩 표현을 재사용. 업무 상태 enum을 미리 만들지 않음.
Dialog·BottomSheet진입·닫기·포커스 복귀, 스크롤, 모바일 키보드, 접근 가능한 이름.복합 상호작용을 독립 검수해 실제 화면의 반복 문제를 줄임.

Story의 단순 문구와 UI 상태 예시는 검수에 필요한 최소 범위로 작성할 수 있다. 서버 응답·인증·결제 상태를 흉내 낸 fixture·handler는 승인된 계약 이후에만 작성한다. 모든 후보를 한 번에 만드는 대신 사용처가 확인된 소수부터 완성한다.

디자인 토큰은 Tokens Studio에서 생성·수정한다. 저장소의 생성 토큰을 직접 바꾸거나 미정 브랜드 색상을 임의로 정하지 않는다. 기존 토큰 파일이 있다는 사실만으로 내보내기·CSS 변환·앱 적용이 완료된 것으로 판단하지 않는다.

근거: 토큰 관리 기준, Story 대상과 작성 원칙, 접근성 기준.

5. 실행 순서와 각 묶음의 완료 조건

아래 순서는 의존성에 따른 제안이다. 기간과 담당자를 확정한 일정표가 아니며, 각 묶음은 필요한 작업 카드로 나누어 진행한다.

첫 묶음의 최종 산출물은 실행 가능한 기본 앱, 실제 UI와 가까운 Story, 빌드 결과와 재실행 안내다. API client·인증 Store·Bridge adapter·업무 Mock은 첫 묶음의 기본 산출물에 포함하지 않는다.

6. 빌드와 검수로 확인할 수 있는 것

검증확인하는 것별도로 확인할 것
Typecheck·Lint타입·import 경계, 정적 패턴과 기본 규칙.실제 동작·디자인 의도·화면 대비.
필요한 동작 테스트오류 영향이 큰 로직·폼·선택·열기/닫기 등 사용자 결과.단순 클래스 문자열이나 라이브러리 내부 동작을 반복 검사하지 않음.
Storybook 정적 build검수 대상 UI와 Story가 배포 가능한 형태로 묶이는지.Story 렌더링·상호작용·접근성 확인. build 성공만으로 UI 검수 완료를 판단하지 않음.
Next production build실제 앱의 모듈·라우트·렌더링 구성이 빌드되는지.실행 후 이동·입력·네트워크·WebView 사용자 흐름.
브라우저·실기기 검수핵심 정보·입력·이동, 포커스·스크롤·키보드와 필요한 safe-area.Safari 15는 프로젝트 지원 기준. Tailwind CSS 4의 기술 선택만으로 호환을 보증하지 않음.

실제 package.json에 정의된 명령만 사용한다. 기본 순서는 typecheck → lint → 필요한 test이며, Story 변경에는 Storybook 정적 build, 통합 영향에는 production build를 추가한다. 실행하지 못한 검사는 Not Run과 사유로 남긴다.

Safari 15에서는 핵심 흐름의 동작을 우선하고 호환 가능한 표현을 적용한다. 최소 지원 버전을 FE가 임의로 올리지 않으며, 지원 기기·검수 환경 확보는 TBD다.

근거: 검증 순서와 테스트 범위, Safari 15 지원 목적과 UI 기준.

7. 팀이 확인해야 할 결정과 연결 시점

확인할 결정협의 대상언제 필요한가
기존 실제 소스 유무·저장소 위치·패키지 관리 도구 TBDFE·저장소 관리 책임자Foundation 착수 전. lounge-fe/webview는 현재 제안.
공통 UI 디자인·토큰 출처·폰트·variant TBD디자인·FE각 UI의 시각 구현 전. 확정된 항목부터 착수 가능.
헤더·하단 탐색·뒤로가기의 Native/WebView 책임 TBD앱·FE·기획페이지 셸과 탐색 연결 전.
회원·결제 정책, API·인증·Bridge 계약 TBD기획·Backend·앱·FE해당 기능 통합 전. 독립적인 UI 준비와 구분.
홈페이지 스택·공유 범위, 판매채널·PO·OO 담당 TBD프로젝트·기획·각 개발 책임자해당 앱·영역 구성 전. WebView의 범위를 자동 확대하지 않음.

협의 대상은 역할 기준 제안이며 실제 담당자가 지정되었다는 의미는 아니다. 답변과 근거는 기존 결정 기록과 계약 검토에 연결하고, 착수 범위와 검사 결과는 작업 카드에 남긴다.

8. 착수할 때 사용할 공통 기준

  • 현재 문서와 참고 골격을 확인한 뒤 실제 코드 저장소의 지침·설정을 우선한다.
  • 첫 작업은 Foundation과 확인된 소수 UI·Storybook으로 범위를 고정한다.
  • 디자인 확인과 API·Native 계약 확인을 구분하고, 미정 부분은 영향받는 범위만 보류한다.
  • 완료 보고에는 변경 파일, Story 상태, 실제 검사 결과, 미검증 환경과 다음 행동을 함께 남긴다.
  • IA 후보 수나 UI 검수 완료를 전체 개발량·기능 통합 완료로 표시하지 않는다.

이 문서의 다음 행동은 팀의 범위 검토다. 구현이 승인되면 실제 저장소를 확인하고 첫 작업 묶음의 구체적인 파일·완료 조건을 정해 진행한다.
