기획 확정 전 준비할 수 있는 소스 기반과 공통 UI, 구현 위치와 완료 조건

1. 지금 준비하려는 것과 판단 근거

기획 전체가 확정되기를 기다리기보다, 화면을 만드는 데 필요한 실행 환경과 UI 검수 기반부터 먼저 준비할 수 있습니다. 업무 규칙이나 외부 계약에 의존하는 부분은 그 합의가 끝난 뒤 연결하면 됩니다.

이번 문서의 목적

개발자·기획자·디자이너·리뷰어가 선행 개발의 범위와 그 이유를 함께 확인하기 위한 자료입니다. 현재 WebView·홈페이지와 공통 UI 패키지에 실행·검수 기반이 있으며, 이 문서는 후속 선행 개발의 범위를 설명합니다. 기반 코드가 있다는 사실은 개별 업무 기능의 Ready나 Phase 0 전체 완료를 뜻하지 않습니다. 실제로 착수할 때는 작은 작업 단위로 나누어 위치·근거·완료 조건을 정합니다.

확인한 현재 상태판단에 미치는 영향근거
lounge-docs는 문서와 Front-end 소스를 함께 관리합니다.Front-end의 빌드·배포는 front-end/에서 진행하며, docs를 제품 번들에 넣지는 않습니다.저장소 안내, 프로젝트 핵심 정보
WebView·홈페이지·공통 UI 패키지의 실행 기반이 있습니다.front-end/webview/·website/와 packages/ui/의 기존 package·설정·공통 UI·Storybook을 확인해 이어서 구현합니다. 개발용 preview와 제품 배포 범위를 구분합니다.WebView 작업 위치 안내와 해당 폴더의 실제 파일 확인
IA는 화면군의 뼈대일 뿐이고, 확정된 작업 목록은 아닙니다.공통 헤더·오류·로딩 같은 항목은 후보로만 두고, 메뉴·정책·담당과 최종 화면 수는 확정하지 않습니다.진행 현황과 IA 후보, IA 기준
회원·결제·API·인증·Native Bridge 계약이 아직 정해지지 않았습니다.실제 통신·세션·Bridge와 업무 데이터 Mock은 계약이 확인된 뒤에 구현합니다.과업 범위와 미정 사항, 계약 검토

기술 기준은 기존 문서에 적힌 Next.js 16 App Router, React 19, TypeScript 6, Tailwind CSS 4, shadcn/ui base-nova를 참조합니다. 설치 버전·실행 명령은 front-end/의 workspace·공용 잠금 파일과 각 package에서, 구현 유무는 대상 앱·공통 패키지의 현재 소스에서 확인합니다. 앱·개발 화면·배포 경계 필수 기준과 현재 WebView 빌드 안내를 초기 구성·라우트·검수·빌드 설정 변경 전에 반드시 확인합니다.

2. 현재 기준으로 나눈 작업 범위

공통 UI라고 디자인 없이 완성할 수 있는 것은 아닙니다. 의미 있는 HTML, label 연결, disabled·focus 같은 기본 동작은 먼저 검토할 수 있지만, 브랜드 색상·크기·variant·문구·배치는 확인된 디자인을 기준으로 정해야 합니다.

선행 작업준비할 내용선행 확인 또는 보류 범위
Foundation기존 App Router·타입·린트·스타일·alias·설치·빌드 절차를 사용하고 변경 범위에 필요한 설정만 보완합니다.npm workspace와 기존 두 앱이 구성돼 있습니다. front-end/의 공용 잠금 파일·대상 package를 유지하고 필요한 변경만 적용합니다. 인증 Provider나 환경변수 이름은 계약 없이 만들지 않습니다.
Storybookpackages/ui/.storybook/의 공통 설정과 기존 Story를 사용하고 필요한 대상·상태·viewport를 갱신합니다.변경한 UI와 관련 Story를 함께 검증합니다. 제품에 필요하지 않은 Provider·Props는 추가하지 않습니다.
기본 UIButton·Input·Textarea·Checkbox·Radio·Badge·Skeleton 중 디자인과 사용처가 확인된 항목을 만듭니다.실제 디자인과 사용처에 맞는 항목부터 고릅니다. 변형과 상태를 한 번에 모두 만들지는 않습니다.
복합 UIDialog·BottomSheet·Select·Tabs·Toast 중 필요한 항목의 포커스·스크롤·키보드 동작을 다룹니다.닫기 정책, 선택 방식, 모바일 키보드와 디자인 확인이 필요합니다. Safari 15에서 핵심 동작을 확인합니다.
셸·공통 상태확인된 Header·Navigation과 loading·empty·error를 어떻게 표현할지 후보를 정리합니다.Native와 WebView의 담당, 메뉴 목적지·노출 조건·문구를 확인해야 합니다. 화면별 오류 처리 규칙은 별도로 합의합니다.

근거: UI 구현 기준, Storybook 기준, 품질 기준. React Hook Form·Zod는 공통 개발 폼 예제에 이미 사용합니다. 실제 업무별 규칙은 별도로 확인하며, TanStack Query·Zustand 기반은 승인 계약·조회·공유 상태 책임이 생기는 시점에 검토합니다.

3. 소스는 어디에 두고 무엇을 먼저 만드는가

Front-end 소스는 이 저장소 front-end/에서 관리합니다. Flutter 앱에서 WebView로 실행되는 화면은 front-end/webview/, FO 웹(PC WEB·반응형 홈페이지)과 PO(파트너오피스)·OO(현장운영시스템)은 front-end/ 아래 별도 영역으로 둡니다. APP IA의 업무 화면은 대부분 WebView이며, Native 잔여 항목은 현재 원본 View 대조를 따릅니다. 파일 제목만으로 APP 전체를 Native로 분류하지 않습니다. Flutter Native 앱만 별도 위치에 있으며, WebView 화면과는 합의된 Bridge 계약으로 연결합니다. front-end/webview/의 기존 앱과 검수 기반에서 시작하며, 실제 소스와 현재 설정을 문서의 초기 구성 예시보다 우선합니다.

웹 영역은 앱 WebView / FO 웹 / PO / OO로 구분합니다. FO 웹은 기존 더라운지 홈페이지를 AS-IS로 참고하는 사용자 웹이며, PO·OO와 서로 대체되는 명칭이 아닙니다. FO 웹은 front-end/website/에 있고 WebView와 같은 웹 스택·디자인 시스템을 사용하며 기본 UI·스타일은 front-end/packages/ui/에서 공유합니다. PO·OO의 구체적인 위치·스택·공유 범위·담당은 아직 정하지 않습니다. IA 영역별 근거를 확인한 뒤 필요한 구조를 정합니다.

현재 구현 위치

  • 실제 앱: webview/src/app/·website/src/app/
  • 공통 UI·스타일: packages/ui/src/components/·src/styles.css
  • Storybook: packages/ui/.storybook/와 구현 가까이의 Story
  • 공통 개발 예제: packages/ui/src/dev/
  • 앱별 검수 진입: 각 앱의 src/dev/·src/app/preview/

빌드·배포 기준

  • 운영 빌드에서 개발용 *.dev.* 라우트 제외
  • 개발 전용 import·스타일·Story·테스트 제외
  • front-end/에서 npm run build:webview·build:website 실행
  • 제품 배포 결과물은 각 앱의 dist/runtime/
  • 문서와 지침은 제품 배포에서 제외

위치는 front-end/ 기준이며 설치·공용 검증은 workspace 루트에서, 앱별 빌드·실행은 해당 package의 정의된 명령으로 수행합니다. 초기 구성 예시를 새로 생성하기보다 실제 파일을 확인하고, 변경할 때는 공용 배포 경계와 앱 안내를 함께 갱신합니다.

위치만드는 이유추가하는 시점
src/app라우트·레이아웃·전역 스타일의 진입점을 한 곳에 모읍니다. 업무 로직을 화면 파일에 모두 넣지는 않습니다.최초 앱 실행부터
packages/ui/src/components/여러 화면에서 같은 책임으로 쓰는 기본 UI를 관리합니다.첫 공통 UI를 구현할 때부터
packages/ui/.storybook/와 구현 가까이의 Story검수 환경 설정과 UI 소스는 나누어 두되, 컴포넌트 변경과 Story 변경은 함께 추적합니다.첫 UI 구현과 같은 묶음으로
src/features/<기능>회원·사용처처럼 실제 기능의 화면 조합과 상태를 가까이서 관리합니다.기능의 허용 범위가 정해진 뒤
src/lib, src/test실제로 필요한 유틸리티와 테스트 공통 설정을 관리합니다.cn 같은 소비자나 공통 테스트 설정이 필요할 때

FO 웹·WebView의 공통 UI·스타일·Storybook은 기존 packages/ui/를 사용합니다. 업무 기능의 공유·화면별 환경 차이와 PO·OO의 스택·담당은 TBD입니다. 기존 앱·공통 패키지를 중복 생성하지 않고, 새 Store나 계층은 실제 책임이 확인될 때 검토합니다.

4. 한 컴포넌트를 만드는 흐름과 검수 이유

대상 후보검수할 상태와 동작만드는 이유
Button확인된 variant, disabled, focus, 긴 문구를 봅니다. loading은 실제로 요구가 있을 때 추가합니다.행동의 우선순위와 클릭 가능 상태를 여러 화면에서 일관되게 표현하기 위한 것입니다.
Input·Textarealabel·설명·오류 연결, disabled, 입력·키보드 동작을 봅니다. 길이와 검증 정책은 기능별로 정합니다.회원·문의처럼 반복되는 입력 UI의 의미와 접근성을 먼저 검수하기 위한 것입니다.
Checkbox·Radio선택·비선택, disabled, label 클릭, 그룹 이름과 키보드 조작을 봅니다.약관·선택 UI에 쓸 기본 조작을 검수하기 위한 것이며, 약관 정책 자체는 별개로 둡니다.
Badge·Skeleton확인된 의미·텍스트·크기, 콘텐츠를 대체하는 관계, 필요한 모션 제한을 봅니다.상태 표시와 로딩 표현을 다시 쓰기 위한 것입니다. 업무 상태 enum을 미리 만들지는 않습니다.
Dialog·BottomSheet진입·닫기·포커스 복귀, 스크롤, 모바일 키보드, 접근 가능한 이름을 봅니다.복합 상호작용을 따로 검수해 실제 화면에서 같은 문제가 반복되는 것을 줄이기 위한 것입니다.

Story의 단순한 문구와 UI 상태 예시는 검수에 필요한 최소 범위로 작성할 수 있습니다. 서버 응답·인증·결제 상태를 흉내 낸 fixture·handler는 계약이 승인된 뒤에 만듭니다. 후보를 한 번에 모두 만들기보다, 사용처가 확인된 소수부터 완성합니다.

디자인 토큰은 Tokens Studio에서만 생성하고 수정합니다. 저장소에 생성된 토큰 파일을 직접 바꾸거나, 정해지지 않은 브랜드 색상을 임의로 정하지는 않습니다. 토큰 파일이 있다는 사실만으로 내보내기·CSS 변환·앱 적용까지 끝난 것으로 보지는 않습니다.

근거: 토큰 관리 기준, Story 대상과 작성 원칙, 접근성 기준.

5. 실행 순서와 각 묶음의 완료 조건

아래 순서는 작업 사이의 의존성을 기준으로 제안한 것입니다. 기간과 담당자를 확정한 일정표는 아니며, 각 묶음은 필요한 작업 카드로 나누어 진행합니다.

기본 앱·공통 UI·Story·빌드·재실행 절차는 후속 완료 카드에서 확인합니다. 남은 범위와 다음 행동은 Phase 0 카드와 진행 현황을 기준으로 정합니다. API client·인증 Store·Bridge adapter·업무 Mock은 첫 묶음의 결과에 포함하지 않습니다.

6. 빌드와 검수로 확인할 수 있는 것

검증확인하는 것별도로 확인할 것
Typecheck·Lint타입과 import 경계, 정적 패턴, 기본 규칙을 확인합니다.실제 동작, 디자인 의도, 화면 간 대비는 따로 봅니다.
필요한 동작 테스트오류의 영향이 큰 로직·폼·선택·열기/닫기처럼 사용자가 보는 결과를 확인합니다.단순한 클래스 문자열이나 라이브러리 내부 동작을 반복해서 검사하지는 않습니다.
Storybook 정적 build검수 대상 UI와 Story가 배포할 수 있는 형태로 묶이는지 확인합니다.Story의 렌더링·상호작용·접근성은 별도로 봅니다. build가 성공했다고 UI 검수가 끝나지는 않습니다.
Next production build실제 앱의 모듈·라우트·렌더링 구성이 빌드되는지 확인합니다.실행한 뒤의 이동·입력·네트워크와 WebView 사용자 흐름은 별도로 확인합니다.
브라우저·실기기 검수핵심 정보·입력·이동과 포커스·스크롤·키보드, 필요한 safe-area를 확인합니다.Safari 15는 프로젝트가 정한 지원 기준입니다. Tailwind CSS 4를 쓴다는 사실만으로 호환이 보증되지는 않습니다.

검증에는 실제 package.json에 정의된 명령만 사용합니다. 기본 순서는 typecheck → lint → 필요한 test이며, Story를 바꾼 경우에는 Storybook 정적 build, 통합에 영향이 있는 경우에는 production build를 추가합니다. 실행하지 못한 검사는 Not Run과 그 사유로 남깁니다.

Safari 15에서는 핵심 흐름이 동작하는 것을 먼저 생각하고, 필요하면 호환되는 표현으로 대체합니다. 최소 지원 버전은 Front-end가 임의로 올리지 않으며, 지원 기기와 검수 환경을 확보하는 일은 TBD입니다.

근거: 검증 순서와 테스트 범위, Safari 15 지원 목적과 UI 기준.

7. 팀이 확인해야 할 결정과 연결 시점

확인할 결정협의 대상언제 필요한가
패키지 관리 도구·설치 버전FEnpm workspace·공용 잠금 파일과 기존 package에서 확인합니다. 변경이 필요할 때 영향·호환성을 검토합니다.
공통 UI 디자인·토큰 출처·폰트·variant TBD디자인·FE각 UI의 시각적 구현 전에 필요합니다. 확정된 항목부터 시작할 수 있습니다.
헤더·하단 탐색·뒤로가기를 Native와 WebView 중 어디에서 책임지는가 TBD앱·FE·기획페이지 셸과 탐색을 연결하기 전에 필요합니다.
회원·결제 정책, API·인증·Bridge 계약 TBD기획·Backend·앱·FE해당 기능을 통합하기 전에 필요합니다. 독립적인 UI 준비와는 구분합니다.
업무 기능 공유·환경 차이, 판매채널·PO·OO 담당 TBD프로젝트·기획·각 개발 책임자홈페이지 스택·공통 UI 공유는 구성됐습니다. 새 업무 기능·별도 영역을 연결하기 전에 남은 범위·책임을 확인합니다.

협의 대상으로 적어 둔 내용은 역할 기준의 제안이며, 실제 담당자가 정해졌다는 뜻은 아닙니다. 답변과 근거는 기존 결정 기록과 계약 검토에 연결하고, 착수 범위와 검사 결과는 작업 카드에 남기면 됩니다.

8. 착수할 때 사용할 공통 기준

  • front-end/의 현재 파일과 그 근처의 지침을 문서 예시보다 우선합니다.
  • 기존 기반과 실제 카드의 미완료 항목을 확인해 다음 작업 범위를 정합니다.
  • 디자인 확인과 API·Native 계약 확인은 나누어 보고, 정해지지 않은 부분은 영향을 받는 범위만 보류합니다.
  • 완료 보고에는 변경한 파일, Story 상태, 실제 검사 결과, 검증하지 못한 환경과 다음 행동을 함께 적습니다.
  • IA 후보의 수나 UI 검수 완료를 전체 개발량이나 기능 통합 완료로 표시하지 않습니다.

다음 작업은 현재 카드의 남은 범위·담당·승인 근거를 확인하고, 기존 앱·공통 패키지의 사용처와 완료 조건을 정해 진행합니다. Phase 0 전체는 미완료이며 초안 검증을 실제 서비스·계약·실기기 검증으로 확대하지 않습니다.
