# Lounge Front-end 구축 가이드 브리핑

## 브리핑이 답해야 하는 질문

이 브리핑은 Front-end 기술을 요약하는 발표가 아닙니다. 구축 완료 후 운영할 실무자와 Front-end 구축 방식을 알아야 하는 관계자에게 다음 질문을 한 번에 설명합니다.

1. Front-end 구축 기준을 왜 여러 가이드와 계층으로 나눴는가
2. 가이드를 어떤 구조로 나눴고 각 문서는 왜 필요한가
3. 가이드와 AI를 연결해 실제 애플리케이션을 어떤 순서로 구축하는가
4. 구축이 끝난 뒤 실무자는 이 체계를 어떻게 이어서 운영하는가

발표에서는 문장보다 다이어그램을 중심으로 관계를 설명합니다. 폴더와 파일명은 실제 저장소 경로를 사용합니다.

---

## 1. 표지 — 사람의 판단과 AI의 실행을 하나의 구축 체계로 연결합니다

### 핵심 문구

> 사람의 판단과 AI의 실행을  
> 하나의 구축 체계로 연결합니다.

가이드는 Front-end의 구조·UI·상태·품질과 역할을 공통 기준으로 유지합니다. AI는 가이드와 실제 Source를 바탕으로 탐색·구현·검증을 돕고, 사람은 방향과 최종 품질을 결정합니다.

### 다이어그램

```text
사람의 방향과 판단
        ↓ 공통 기준으로 구조화
가이드 체계
        ↓ 작업에 필요한 Context 제공
AI의 탐색·구현·검증 지원
        ↓ 사람이 검토할 수 있는 결과
Source · Story · Test · 운영 문서
```

### 발표 포인트

가이드는 구축이 끝난 뒤 보관하는 설명서가 아닙니다. 사람의 판단을 구현 가능한 기준으로 바꾸고, AI의 결과를 같은 기준으로 검토하며, 구축 후 운영까지 이어주는 작업 체계입니다.

---

## 2. 구축 전략 — 사람은 결정하고, AI는 기준 안에서 실행합니다

### 핵심 문구

> 사람은 방향과 품질을 결정하고  
> AI는 기준 안에서 실행합니다.

### 다이어그램

```text
사람의 방향과 판단                           AI의 탐색과 실행
───────────────────────                    ───────────────────────
제품 방향과 사용자 흐름                      기존 Source와 Component 탐색
업무 규칙과 우선순위                         코드와 Story 초안
API·인증·Bridge 연동 방식                    상태·예외 누락 후보 확인
보안·운영 정책                               Typecheck·Lint·Test·Build
변경 승인과 최종 품질                        검증 결과와 변경 내용 정리
          │                                          ▲
          └────── 가이드로 작업 기준 제공 ───────────┘
                             │
                             ▼
                Source · Story · Test · 운영 Context
```

### 발표 포인트

가이드는 사람이 결정한 방향을 AI가 실행할 수 있는 구체적인 기준으로 바꿉니다. AI가 만든 결과는 다시 개발자와 관련 담당자가 구조, 업무 의도와 품질 기준에 맞는지 검토합니다.

---

## 3. 전체 저장소 — Source와 가이드를 한 저장소에서 연결합니다

### 핵심 문구

> 가이드는 별도 문서함이 아니라  
> 실제 Source를 구축하는 같은 저장소의 한 축입니다.

### 다이어그램

```text
lounge-docs/
├─ AGENTS.md                    AI 구현 작업의 최상위 기준
├─ apps/
│  ├─ mobile/                   Flutter Native App
│  └─ app-webview/
│     ├─ AGENTS.md              WebView 앱에 가까운 구현 지침
│     ├─ .storybook/            UI 독립 개발·검수 환경
│     └─ src/                   실제 Front-end 구축 결과
└─ docs/
   ├─ AGENTS.md                 문서 작성·검증 기준
   ├─ guides/                   사람이 읽는 상세 기준 원본
   ├─ ai/                       AI 작업별 핵심 요약
   ├─ common-source/            파일 단위 적용 조건과 구현 예시
   ├─ assets/                   문서 공통 자산
   ├─ search/                   많은 가이드의 탐색 진입점
   └─ templates/                문서 형식의 일관성
```

```text
docs의 기준 ── 작업 맥락 제공 ──▶ AI와 개발자 ── 구현·검증 ──▶ apps/app-webview
     ▲                                                              │
└──────── 구조·공개 API·연동 기준 변경 시 함께 갱신 ─────────────┘
```

### 발표 포인트

애플리케이션 Build 대상은 `apps/app-webview`입니다. `docs`는 제품 Bundle에 포함되지 않지만, 구현 판단과 검토 기준을 제공하고 Source 변경을 다시 반영받습니다.

---

## 4. docs 계층 — 같은 기준을 사용 목적에 맞는 깊이로 제공합니다

### 핵심 문구

> 내용이 많아진 이유는 중복하기 위해서가 아니라  
> 사람·AI·구현 단계가 필요한 깊이가 다르기 때문입니다.

### 다이어그램

```text
docs/guides/
사람용 상세 기준 원본
왜 필요한지 · 판단 기준 · 배경 · 검토 방법
        │ 핵심 결정만 압축
        ▼
docs/ai/
AI 작업별 Context Router
project · ui · figma · storybook · quality · performance · security
        │ 파일에 옮길 구체성이 필요할 때
        ▼
docs/common-source/
적용 조건 · 파일 경로 · 구현 예시 · 교체 지점
        │ 기존 Source와 비교·병합
        ▼
apps/app-webview/
실제 Package · 설정 · Source · Story · Test
```

보조 체계인 `docs/assets`, `docs/templates`, `docs/search`는 문서를 같은 형식으로 제공하고 많은 가이드를 찾을 수 있게 합니다.

### 각 계층을 분리한 이유

| 계층 | 왜 따로 두었는가 |
| --- | --- |
| `guides` | 관계자와 실무자가 결정의 배경과 전체 기준을 이해해야 하기 때문 |
| `ai` | AI에 긴 문서 전체가 아니라 현재 작업에 필요한 판단만 제공하기 위해 |
| `common-source` | 정책 설명과 실제 파일 단위 예시를 섞지 않고 적용 조건을 명확히 하기 위해 |
| `apps/app-webview` | 문서 예시가 아니라 설치 Package와 기존 Source를 최종 사실로 사용하기 위해 |

---

## 5. 상세 가이드 지도 — 구축의 결정 지점을 영역별로 나눴습니다

### 핵심 문구

> 가이드 하나는 구축 과정의  
> 하나의 결정 영역을 책임집니다.

### 다이어그램

```text
                              [Lounge Front-end 구축]
                                         │
          ┌──────────────────────────────┼──────────────────────────────┐
          ▼                              ▼                              ▼
  ① 기반과 경계                    ② UI와 상태                    ③ 검증과 운영 품질
  architecture                    frontend                       storybook
  저장소·책임·배포 단위             전체 구현 흐름                   독립 UI 개발·검수

  app / platform/webview          ui/react_code_exports          testing / lint
  Native·WebView 책임과 Bridge     Figma→React·기존 UI 재사용       동작·정적 품질 검증

  browser-support                ui/design_tokens               security
  지원 Browser·Viewport 기준       의미 기반 스타일 연결             신뢰 경계·개인정보

                                  ui/zustand                    performance
                                  공유 Client 상태 사용 조건        지연·오류·성능 검증

                                  typescript                   i18n
                                  타입·외부 입력 경계                번역·Locale·Layout
```

```text
보조 가이드
planning ─ 구축 범위와 일정 판단
learning/ai-frontend-growth ─ AI 결과를 검토할 수 있는 Front-end 역량 확보
```

### 발표 포인트

가이드가 많아진 것은 기술을 백과사전처럼 모았기 때문이 아닙니다. 구축 중 서로 다른 결정권자와 검증 시점을 가진 영역을 분리했기 때문입니다. 작업자는 전체를 읽지 않고 현재 결정에 필요한 가이드만 선택합니다.

---

## 6. AI 구축 흐름 — AI는 가이드를 읽고, Source를 확인하고, 근거를 남깁니다

### 핵심 문구

> 가이드는 AI의 입력이고  
> 실제 Source와 검증 결과가 출력입니다.

### 다이어그램

```text
[작업 요청·Figma]
        │ 범위 확인
        ▼
[Root AGENTS.md]
        │ 전체 원칙과 문서 선택
        ▼
[App AGENTS + Package + 기존 Source]
        │ 실제 상태 확인
        ▼
[docs/ai 작업별 요약]
        │ project / ui / figma / quality 등 필요한 것만
        ▼
┌──────────────── 세부 판단이 필요한가? ────────────────┐
│ 예                                                   │ 아니오
▼                                                      ▼
[docs/guides] 또는 [docs/common-source]              [구현]
│ 판단 배경 / 파일 단위 예시                            │
└──────────────────────┬───────────────────────────────┘
                       ▼
            [apps/app-webview에 구현]
                       │
                       ▼
        [Storybook · Typecheck · Lint · Test · Build]
                       │
                       ▼
[재사용·신규 구현·검증 결과·확인 사항 완료 보고]
```

```text
제품·업무 판단 필요 ──▶ 담당자에게 확인 ──▶ 결정 사항을 작업 기준에 반영
                                  └── AI 구현과 검증 흐름으로 복귀
```

### 발표 포인트

AI는 가이드만 보고 코드를 만들지 않습니다. 반드시 실제 Package와 기존 Source를 다시 확인합니다. 사람은 작업 범위, 기획과 최종 품질을 결정하고 AI는 탐색·초안·반복 검사를 수행합니다.

---

## 7. 구축 순서 — 가이드가 실제 구축 단계의 선행 조건이 됩니다

### 핵심 문구

> 가이드를 다 만든 뒤 개발하는 것이 아니라  
> 필요한 기준을 세우고 단계별로 Source에 적용합니다.

### 다이어그램

```text
1. 기반 고정
architecture · frontend · app · webview
저장소, 책임, 지원 환경과 적용 경계 설정
        │ 산출물: app-webview 골격 · AGENTS
        ▼
2. UI 개발 기반
design-tokens · react_code_exports · storybook
Token, 기존 Component 우선, Figma 연결, 독립 검수 방식 설정
        │ 산출물: globals.css · components/ui · Storybook
        ▼
3. 공통 실행 기반
common-source/tailwind · react · typescript · test
실제 사용처가 생길 때 필요한 설정과 공통 코드를 선별 적용
        │ 산출물: Provider · 공통 경계 · Test 환경
        ▼
4. 기능 단위 구축
기획·Figma + 확정된 API·Bridge 정의
기능 가까이에 구현하고 상태·예외·Story를 함께 작성
        │ 산출물: features/* · Story · 사용자 동작 Test
        ▼
5. 품질과 통합
testing · lint · security · performance · browser-support · i18n
지원 환경과 실제 사용자 흐름에서 완료 근거 확인
        │ 산출물: 검사 결과 · Build · 미검증 항목
        ▼
6. 운영 인계
Source, Story, 가이드, AI 요약과 담당자 결정 사항을 연결된 상태로 전달
```

### 발표 포인트

공통 폴더를 미리 모두 채우지 않습니다. 실제 기능과 반복 사용처가 생길 때 적용 조건을 확인해 선별 도입하고, 각 단계의 가이드와 검증 기준을 실제 Source에 연결합니다.

---

## 8. 역할과 의사결정 — AI가 만들 수 있어도 AI가 결정하지 않습니다

### 핵심 문구

> 자동화할 일과  
> 승인받아야 할 일을 분리합니다.

### 다이어그램

```text
기획·Backend·Flutter·보안·운영 담당
화면·업무 기획과 API·인증·Bridge·운영 기준 결정
                    │ 승인된 입력
                    ▼
Front-end 개발자 / Reviewer
구조·상태·UI·접근성·지원 환경·최종 품질 판단
                    │ 작업 범위와 검토
                    ▼
AI
기존 구현 탐색 · 코드와 Story 초안 · 누락 후보 · 반복 검사 · 결과 정리
                    │ 검토 가능한 산출물
                    └──────────────────────▶ Front-end 개발자 / Reviewer
```

### 발표 포인트

AI는 생산성과 일관성을 높이지만 기획을 결정하거나 제품 책임을 대신하지 않습니다. 사람의 판단 영역과 AI의 실행 영역을 가이드에 명시하고, 결과는 담당자가 다시 검토합니다.

---

## 9. 구축 후 운영 — Source와 가이드를 같은 변경 흐름에서 유지합니다

### 핵심 문구

> 구축이 끝나면 가이드는  
> 운영과 다음 변경의 출발점이 됩니다.

### 다이어그램

```text
[신규 기능·변경·장애]
        ▼
[운영 실무자: 관련 가이드와 기존 Source 탐색]
        ▼
[AI와 개발자: 영향 범위·Story·Test 후보 확인]
        ▼
[Source · 공개 API · 연동 기준 변경]
        ▼
┌──────────── 연결된 기준도 함께 갱신 ────────────┐
│ guides 원본 │ ai 요약 │ common-source │ Story·Test │
└──────────────────────┬─────────────────────────┘
                       ▼
             [다음 작업의 정확한 Context]
                       └───────────────↺
```

### 사용자별 진입점

| 사용자 | 시작 위치 | 얻는 것 |
| --- | --- | --- |
| 운영 실무자 | `docs/index.html`, 검색, 관련 상세 가이드 | 변경 위치·검토 기준·담당 경계 |
| Front-end 개발자 | Root·App `AGENTS.md`, 실제 Source | 구현 순서·재사용 대상·검증 기준 |
| AI | `AGENTS.md` → 작업별 `docs/ai` | 현재 작업에 필요한 제한과 판단 기준 |
| 관계자·Reviewer | 브리핑 → 관련 `docs/guides` | 구축 방식·책임 범위·결정이 필요한 항목 |

### 발표 포인트

운영 단계의 핵심은 문서를 보존하는 것이 아니라 다음 변경에서 다시 사용할 수 있는 정확한 Context를 유지하는 것입니다. 구조·공개 API·연동 기준이 바뀌면 관련 문서와 Story를 함께 갱신합니다.

---

## 10. 결론 — 가이드, AI와 Source를 하나의 구축 체계로 운영합니다

### 핵심 문구

> 가이드로 경계를 세우고  
> AI로 구축을 가속하며  
> Source와 검증 근거로 운영을 이어갑니다.

### 다이어그램

```text
             사람의 결정과 승인
                    ↓
가이드 기준 ──▶ AI 실행 ──▶ Source·Story·Test
    ▲                              │
    └────── 변경과 학습을 반영 ────┘
```

### 최종 메시지

- 사람의 판단을 가이드로 구조화해 일관된 기반을 구축합니다.
- 상세 원본, AI 요약과 구현 예시를 목적에 따라 분리합니다.
- AI는 가이드와 실제 Source를 함께 확인해 구현과 검증을 돕습니다.
- 구축 결과와 가이드를 연결한 상태로 운영 실무자에게 인계합니다.
