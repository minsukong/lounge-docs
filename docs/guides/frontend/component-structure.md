# TSX 가독성과 데이터·로직·UI 분리 기준

화면·Feature를 새로 만들거나 데이터·상태·주요 UI 영역을 확장할 때 반드시 적용합니다. 기존 파일 전체를 관성적으로 개편하지 않고 이번 작업에서 책임이 섞이거나 커지는 부분을 정리합니다. 단순한 컴포넌트는 한 파일로 시작하되, 변경이 누적되는 화면을 하나의 TSX에 계속 덧붙이지 않습니다.

## 1. 화면 파일에 남길 내용

화면 TSX에서는 주요 UI 영역의 구성, 화면 수준의 상태 연결과 로딩·오류·빈 상태 같은 전체 표시 흐름을 읽을 수 있어야 합니다. 세부 영역의 긴 JSX, 고정 데이터 목록, 복잡한 데이터 변환과 여러 독립 동작을 모두 화면 본문에 넣지 않습니다.

- 라우트 파일은 라우트에 필요한 서버 작업·메타데이터·진입 연결을 담당하고, 기능이 커지면 Feature 화면으로 연결합니다.
- 화면은 Header·Filter·List·Form 등 의미 있는 영역을 조합합니다. 한두 태그의 단순 묶음마다 컴포넌트를 만들지는 않습니다.
- 단순하고 화면에만 필요한 상태·이벤트는 화면에 유지할 수 있습니다. 여러 영역의 상태를 조율하는 책임도 화면에 남길 수 있습니다.
- 자식에 긴 설정·업무 로직을 그대로 넘겨 화면 줄 수만 줄이는 방식은 피합니다. 이동한 코드가 담당하는 책임을 설명할 수 있어야 합니다.

## 2. 분리 신호와 약 200줄 검토 기준

직접 작성하는 화면·Feature TSX가 약 200줄을 넘으면 같은 변경에서 구조를 검토합니다. 이 수치는 리뷰를 시작하는 신호이며 강제 상한이나 새로운 Lint 규칙이 아닙니다. 200줄 이하라도 다음 신호가 나타나면 분리를 검토합니다.

- 한 파일에서 데이터 조회·변환, 폼 처리, 모달 상태와 여러 화면 영역을 함께 수정해야 합니다.
- 긴 배열·설정 객체 또는 반복 JSX 때문에 화면 구조를 찾기 어렵습니다.
- 서로 다른 이유로 바뀌는 영역이 한 파일에 섞여 있고, 작업자가 관련 코드를 찾기 위해 계속 위아래로 이동해야 합니다.
- 독립적인 동작·조건 분기·상태가 있는 영역을 따로 검수하거나 수정하기 어렵습니다.
- 조건부 렌더링이 깊어져 로딩·오류·성공·빈 상태의 표시 우선순위를 읽기 어렵습니다.

검토 후 분리하거나, 같은 책임의 단순 표현이어서 유지하는 이유를 카드의 구조 기록에 짧게 남깁니다. 코드 압축, 여러 표현을 한 줄에 배치, 접기 주석만 추가하는 방식으로 기준을 피하지 않습니다. 생성 코드·shadcn/ui 원형·외부 예제는 줄 수만으로 개편하지 않고 실제 수정 책임과 영향으로 판단합니다.

## 3. 내용별 배치 기준

| 내용 | 분리할 때 | 배치와 유지 기준 |
| --- | --- | --- |
| 고정 표시 데이터·설정 | 긴 메뉴·옵션·표시 목록이 JSX를 가릴 때 | 기능 내부의 의미가 드러나는 *.data.ts·*.config.ts. 짧은 상수는 사용하는 파일에 유지 |
| API·서버 데이터 | 요청·응답·조회·갱신 책임이 UI와 섞일 때 | 기능 내부 API·Query 모듈. 실제 계약과 기존 서버·클라이언트 패턴을 적용 |
| 계산·변환·정렬 | 표시와 별개로 읽고 검증할 로직이 생길 때 | 기능 내부의 순수 함수 모듈. 동일 계산 결과를 중복 상태로 저장하지 않음 |
| 상태·이벤트·폼 | 관련 상태 전환과 처리 흐름이 복잡해질 때 | 해당 동작의 기능 전용 Hook 또는 폼 모듈. 단순 useState를 감싸는 Hook은 불필요 |
| 반복 UI | 카드·행·목록 항목의 표현과 동작이 반복될 때 | 기능 내부 컴포넌트. 실제 공유 의미가 확인되기 전에는 공통 UI로 이동하지 않음 |
| 큰 UI 영역 | 필터·목록·입력·상세 영역이 독립적인 책임을 가질 때 | 의미 있는 영역별 컴포넌트. 부모에서만 쓰더라도 충분한 분리 이유가 있으면 별도 파일 가능 |
| 타입·variant | 여러 파일이 사용하는 계약 또는 조합이 커질 때 | 기능 내부 타입·variant 파일. 작은 로컬 Props는 컴포넌트 가까이에 유지 |

고정 표시 데이터를 분리한다는 이유로 서버 응답을 흉내 낸 데이터, 업무 정책, API DTO와 fixture를 임의로 만들지 않습니다. 업무·API·Native 계약이 미정인 부분은 기존 승인 기준을 따릅니다. Tailwind 클래스도 줄 수를 줄이기 위해 무조건 설정 파일이나 거대한 스타일 객체로 옮기지 않습니다.

## 4. 상태 소유권과 의존 방향

- UI 한 영역에서만 쓰는 상태는 그 영역 가까이에 둡니다. 여러 영역이 함께 쓰면 가장 가까운 공통 부모에서 소유하고 필요한 값·이벤트를 전달합니다.
- 서버 데이터, 입력 중인 폼 값, 화면 선택·열림 상태를 구분합니다. 분리된 파일마다 같은 원본을 상태로 복제하거나 동기화 Effect를 추가하지 않습니다.
- 화면에서 필요한 컴포넌트·Hook·순수 함수를 가져옵니다. 자식 컴포넌트나 데이터 모듈이 부모 화면을 다시 가져오는 순환 import를 만들지 않습니다.
- Props는 해당 영역에 필요한 데이터와 이벤트로 제한합니다. 전역 Store로 옮기거나 모든 상태·setter를 담은 객체를 전달하여 Props 문제를 우회하지 않습니다.
- 기존 Server Component를 기본으로 유지합니다. 파일 분리를 위해 전체 화면에 use client를 추가하거나 서버 조회를 모두 클라이언트 Hook으로 이동하지 않습니다. 서버 전용 코드·비밀 값은 클라이언트 모듈에 연결하지 않습니다.
- 컴포넌트는 모듈 수준에 정의합니다. 렌더 함수 안에 새 컴포넌트 함수를 정의하거나 key를 바꿔 입력·포커스·상태가 재설정되는 분리를 피합니다.
- 분리 후에도 label·설명·오류 연결, 포커스 복귀, 폼 제출, 로딩·오류·빈 상태, 라우팅과 CSS 적용이 유지되어야 합니다.

## 5. 기능 가까이에서 찾을 수 있는 파일 구성

다음은 기능이 커졌을 때의 구성 예시입니다. 모든 화면에 같은 파일 세트를 생성하지 않습니다. 실제 기능 이름과 기존 저장소의 파일명 규칙을 우선합니다.

```text
src/features/ticket/
├── ticket-screen.tsx        # 주요 영역과 전체 표시 흐름
├── components/
│   ├── ticket-filters.tsx   # 필터 영역
│   ├── ticket-list.tsx      # 목록 영역
│   └── ticket-item.tsx      # 반복 항목
├── ticket-options.data.ts  # 길어진 고정 표시 목록이 있을 때
├── ticket-format.ts        # 독립적인 계산·변환이 있을 때
├── use-ticket-filter.ts    # 복잡한 클라이언트 필터 동작이 있을 때
└── ticket.types.ts         # 여러 모듈의 실제 공유 타입이 있을 때
```

승인된 API 연동이 생기면 필요한 API·Query 모듈을 해당 기능 가까이에 추가합니다. 실제 사용처가 없는 api/·hooks/·types/ 폴더와 배럴 파일을 미리 만들지 않습니다. 기능 안의 데이터·유틸리티·컴포넌트를 저장소 전체의 data/·utils/·components/로 무조건 모으지 않습니다.

한 파일 안에서 독립적인 컴포넌트 정의만으로 충분하면 그 방식도 가능합니다. 다만 큰 영역을 같은 파일 아래로 옮기는 것만으로 탐색·검수 문제가 해결됐다고 보지 않습니다. 공개 UI와 독립 검수 가치가 있는 영역의 Story는 실제 구현 가까이에 유지합니다.

## 6. 작성 중 적용하는 순서

- 구현 전 기존 Feature·컴포넌트와 실제 상태 소유자를 확인하고, 카드에 화면·데이터·동작의 담당 파일을 간단히 적습니다.
- 작성 중 긴 목록·반복 JSX·독립적인 처리 흐름이 생기면 그때 분리합니다. 큰 TSX를 끝까지 만든 뒤 후속 정리 작업으로 계속 미루지 않습니다.
- 의미 있는 UI 영역 하나 또는 처리 책임 하나씩 이동합니다. 같은 책임을 여러 작은 파일로 과도하게 쪼개거나 중간 전달 컴포넌트를 연속해서 만들지 않습니다.
- 이번 기능의 구조 변경을 먼저 끝냅니다. 별도 요청 없이 다른 화면 전체를 개편하거나 새로운 공통 계층·상태 관리 도구를 추가하지 않습니다.
- 분리 뒤 import·Props·상태 소유권·표시 흐름을 검토하고 실제 변경 영향에 맞는 검증을 수행합니다.

## 7. 카드·리뷰·재개 기록

화면·Feature 구현 카드에는 구조 계획과 결과를 짧게 남깁니다. 작은 문구·스타일 수정은 구조 기록을 생략하거나 N/A로 표시할 수 있습니다.

| 시점 | 남길 내용 |
| --- | --- |
| 착수 | 화면·UI 영역·고정 데이터·조회·변환·상태 처리의 담당 파일, 필요한 항목만 |
| 구현 중 | 새로 발견한 분리 신호와 실제로 분리한 책임 |
| 리뷰 | 약 200줄 초과 검토 결과, 한 파일 유지 이유, 순환 import·상태 중복·과도한 Props·서버/클라이언트 경계 확인 |
| 완료·재개 | 변경된 파일 역할, 수행한 검사와 미검증 항목, 남은 구조 문제와 다음 행동 |

줄 수만 줄었는지보다 화면 구성과 수정할 책임을 쉽게 찾을 수 있는지 확인합니다. 아직 정리되지 않은 구조 문제는 카드에 남기고 검토 완료로 숨기지 않습니다. AI가 생성한 코드와 로컬 LLM의 초안에도 같은 기준을 적용하며, 파일만 분리됐다는 이유로 완성 코드로 간주하지 않습니다.

## 8. 운영 코드와 개발 코드 경계

제품에서 사용하는 데이터·Hook·UI와 Story·검수용 예시·개발용 화면을 구분합니다. 제품 화면에 큰 예시 목록이나 검수 제어 상태를 넣지 않습니다. 분리한 제품 모듈은 개발 전용 코드·Story·테스트를 가져오지 않습니다.

개발용 preview도 같은 가독성 기준을 적용하되 개발 코드 위치를 유지합니다. 개발용 Foundation 화면에서 분리한 데이터나 컴포넌트를 제품 공통 코드로 자동 이동하지 않습니다. 구체적인 위치와 배포 제외 기준은 [앱·개발 화면·배포 경계](../architecture/build-boundary.md)를 따릅니다.

## 9. 기존 기준과 함께 적용

[Front-End 개발 가이드](index.html)의 파일 분리·공통화 원칙, [React Code Exports 가이드](../ui/react_code_exports.html)의 상태 소유권·재사용 기준과 함께 적용합니다. AI용 요약은 [UI 구현 규칙](../../ai/ui.md), 실제 실행·기록은 [업무 지침](../../workflow/AGENTS.md)과 [작업 카드 양식](../../workflow/task-card.md)에서 연결합니다.

이 문서는 구조 판단의 공용 원본입니다. 예시 파일명은 고정된 템플릿이 아니며, 실제 설정·기존 구현과 합의된 계약을 우선합니다. 새로운 파일 구조를 도입하면 같은 변경에서 관련 Story·검증·작업 기록도 갱신합니다.
