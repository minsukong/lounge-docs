Flutter 카드 스캔 기술 가이드

flutter_card_scanner_plus와 Riverpod으로 구현된 카드 스캔 기능의 동작, 플랫폼 설정, 민감정보 처리와 실제 기기 검증 기준입니다.

1. 목적과 적용 범위

이 문서는 Flutter 앱에서 카메라 OCR로 결제 카드의 번호, 유효기간과 카드 소유자명을 읽는 현재 임시 구현과 WebView 연동 목표를 설명합니다. 최종 흐름에서는 WebView의 요청으로 Native 스캐너를 열고, 스캔을 마치면 기존 WebView로 돌아가 카드정보를 전달합니다. 구현 근거는 실제 Flutter 프로젝트의 소스와 잠금 파일, 로컬에 설치된 flutter_card_scanner_plus 0.1.2 소스이며, 패키지 동작은 pub.dev 패키지 페이지와 공식 API 문서를 함께 확인했습니다.

이 기능은 OCR로 카드 표면의 문자열을 읽는 입력 보조 기능입니다. Luhn과 카드 브랜드 규칙을 통과하더라도 실제 발급 카드, 사용 가능한 카드 또는 결제 가능한 카드임을 보장하지 않습니다.

구분 현재 상태 근거 또는 경계
구현 완료 임시 화면에서 기본 스캐너 실행, 결과 저장, 마스킹 번호·유효기간·소유자명 표시 CardScanPage, cardScanProvider · 개발 확인용
패키지 제공 iOS Vision, Android ML Kit OCR, Luhn 검사, 브랜드·길이 판별 flutter_card_scanner_plus 0.1.2
현재 미구현 WebView 요청 수신·결과 반환, 화면 캡처 방지, 앱 전용 권한 복구 UI, 만료 카드 차단·경고 확인한 Flutter·Android·iOS 소스에 해당 처리가 없음
권장사항 오류 상태 구분, 민감정보 수명 최소화, 실제 기기 회귀 테스트 제품 보안·UX 정책 확정 후 별도 구현 필요

참고사항과 실제 코드가 다른 부분은 실제 코드를 기준으로 했습니다. 현재 /cardscan Route와 결과 표시 화면은 스캐너 동작을 확인하기 위한 임시 구현입니다. 최종 WebView Bridge의 Method, 요청 식별자, 결과 Payload, 성공·취소·오류 형식은 아직 코드에 없으므로 TBD로 구분합니다. 앱 Manifest에는 카메라 권한이 직접 선언되어 있지 않고 Android 플러그인의 Manifest가 병합될 때 선언됩니다.

3. 전체 동작 흐름

아래 흐름은 확정된 최종 방향입니다. WebView Bridge의 구체적인 이름과 Payload는 아직 구현되지 않았으며, 현재 임시 화면의 Provider 저장·결과 표시 흐름을 대체합니다.

ScanRequirements.standard는 카드 번호와 유효기간을 필수로, 카드 소유자명을 선호 필드로 처리합니다. 필수 필드가 안정화된 뒤 이름을 최대 12 OCR Frame 동안 더 기다리고, 이름이 없으면 번호와 유효기간만으로 완료할 수 있습니다. 사용자가 스캐너를 닫으면 null이 반환됩니다. 스캔 화면은 기존 WebView 위에 열리고 종료되므로 별도의 WebView를 새로 만들지 않습니다.

권한 거부나 카메라 오류는 사용자 취소와 같은 사건이 아닙니다. 패키지의 기본 스캐너 화면이 오류를 표시하며, 사용자가 그 화면을 닫은 뒤에야 호출부에는 null이 반환될 수 있습니다. 최종 연동에서는 취소와 오류를 WebView가 구분할 수 있어야 하며, 현재 앱 화면은 패키지 오류 코드를 별도 상태로 보관하지 않습니다.

4. 주요 클래스와 Riverpod 상태 관리

구성 요소 역할 현재 구현 특성
CardScanPage 스캔 버튼, 결과 영역과 스캐너 호출을 구성 현재 개발 확인용 임시 화면
_CardResultView 스캔 결과를 사용자에게 표시 전체 번호 대신 maskedNumber 사용
cardScanProvider 임시 화면의 CardScanResult? 보관 NotifierProvider.autoDispose · 최종 Bridge 흐름 사용 여부 재검토
CardScanNotifier 초기화, 결과 저장과 명시적 초기화 build()는 null, setResult()와 clear() 제공
CardScannerPage 패키지 기본 전체 화면 카메라 UI 완료 시 결과, 닫기 시 null 반환

Provider는 실제 코드에서 다음과 같이 구성되어 있습니다.

final cardScanProvider =
    NotifierProvider.autoDispose<CardScanNotifier, CardScanResult?>(
      CardScanNotifier.new,
    );

class CardScanNotifier extends Notifier<CardScanResult?> {
  @override
  CardScanResult? build() => null;

  void setResult(CardScanResult result) {
    state = result;
  }

  void clear() {
    state = null;
  }
}

화면이 ref.watch(cardScanProvider)로 구독하는 동안 결과는 메모리에 유지됩니다. Route에서 벗어나 구독이 사라지면 Auto Dispose가 상태를 폐기하므로 재진입 시 초기값 null부터 시작합니다. 앱은 이 결과를 영구 저장소에 복사하지 않습니다. 최종 WebView 흐름은 결과를 전달한 직후 Native 쪽 참조를 정리하는 것을 기본으로 하며, 임시 화면의 Provider를 그대로 유지할 필요는 없습니다.

5. 스캐너 실행과 결과 처리

현재 임시 화면의 핵심 실행 코드는 다음과 같습니다.

final result = await CardScannerPage.show(
  context,
  title: '카드 스캔',
  requirements: ScanRequirements.standard,
);

if (result == null || !context.mounted) {
  return;
}

ref.read(cardScanProvider.notifier).setResult(result);
  1. 현재는 임시 Flutter 화면의 버튼, 최종 구조에서는 WebView 요청으로 패키지 기본 카메라 화면을 엽니다.
  2. Native OCR이 카드 Frame 안의 문자를 단말 내부에서 분석합니다.
  3. 패키지의 Dart Parser가 후보 번호를 브랜드 길이와 Luhn으로 검증합니다.
  4. 여러 Frame의 결과가 일치하고 필수 필드가 충족되면 CardScanResult가 반환됩니다.
  5. 사용자 취소 또는 화면 닫기는 null을 반환하므로 Provider를 변경하지 않습니다.
  6. 현재는 결과를 Provider에 저장하지만 최종 구조에서는 요청을 보낸 기존 WebView에 결과를 반환합니다.
  7. WebView가 결과를 받은 뒤 카드 입력 UI를 갱신하고, Flutter는 전달이 끝난 결과를 불필요하게 보관하지 않습니다.

현재 호출부에는 CardScannerException을 구분하는 try/catch가 없습니다. 기본 스캐너가 내부 오류를 화면에 표시하지만, 앱 고유의 재시도·설정 이동·분석 Event가 필요하다면 별도 오류 설계가 필요합니다. WebView 요청 처리에서는 동시 실행 방지, 요청과 응답을 연결할 식별자, WebView 이탈·재생성 시 응답 폐기 기준도 함께 정의해야 합니다.

6. 임시 Route와 최종 WebView 연결

Route 상수는 RouterPath.cardscan = '/cardscan'이고, AppRouter가 이 경로를 CardScanPage에 연결합니다. 현재 Splash의 후속 이동도 context.go(RouterPath.cardscan)으로 설정되어 있습니다. 이 Route는 현재 스캐너를 단독 검증하기 위한 임시 진입점입니다. 

GoRoute(
  path: RouterPath.cardscan,
  builder: (context, state) {
    return const CardScanPage();
  },
),

최종 구조에서는 WebView 화면을 /cardscan으로 교체하지 않습니다. WebView에서 승인된 Bridge 요청이 들어오면 현재 WebView의 Flutter BuildContext에서 CardScannerPage.show()를 열고, Scanner가 닫히면 유지 중인 WebView에 결과를 응답합니다. Method 이름, 요청 ID, 중복 요청, 성공·취소·오류 Payload와 JavaScript Callback 방식은 TBD이며 실제 계약 없이 임의로 구현하지 않습니다.

7. Android 설정과 권한

항목 현재 설정 확인 사항
최소 SDK minSdk = 24 앱 설정과 패키지 최소 요구사항이 일치
OCR ML Kit Text Recognition 패키지가 Bundled Model 16.0.1을 포함하며 오프라인 실행

배포 전에 병합된 Manifest에서 카메라 권한을 확인합니다. 프로젝트에 설치된 permission_handler가 있더라도 현재 카드 스캔 화면은 이 패키지를 통해 별도 사전 권한을 요청하지 않습니다. 같은 권한을 두 계층에서 동시에 요청하지 않도록 소유 주체를 하나로 유지합니다.

9. 스캔 결과 필드

필드 형식과 의미 현재 화면 사용
number 공백 없는 전체 카드 번호 문자열. 인식 전에는 null 화면에 직접 표시하지 않음
maskedNumber 마지막 네 자리만 남긴 •••• 1234 형식 결과 화면의 번호 표시에 사용
last4 번호 마지막 네 자리 또는 null 현재 직접 사용하지 않음
brand visa, mastercard, amex 중 하나 현재 직접 표시하지 않음
expiryMonth 1부터 12까지의 월 또는 null formattedExpiry 계산에 사용
expiryYear 네 자리 연도 또는 null formattedExpiry 계산에 사용
formattedExpiry MM/YY 형식. 월·연도가 없으면 null 값이 있을 때 표시
cardholderName 카드에 인쇄된 대문자 이름. 인식되지 않으면 null 값이 있을 때 표시
isComplete 현재 요구한 필드가 여러 Frame에서 확인되어 완료됐는지 표시 현재 직접 사용하지 않음
isExpired() 호출 시점을 기준으로 유효기간이 지났는지 계산 현재 호출하지 않아 만료 카드를 차단·경고하지 않음

number는 패키지가 Luhn과 지원 브랜드의 BIN·길이 규칙을 통과한 경우에만 결과 후보가 됩니다. 그러나 이 검사는 번호 형식의 유효성을 확인할 뿐 발급 상태, 소유권이나 결제 가능 여부를 확인하지 않습니다.

WebView 반환 계약

최종 흐름에서는 WebView가 카드 입력을 이어갈 수 있도록 스캔 결과를 반환합니다. 전체 번호가 필요한지, 만료 월·연도를 숫자로 나눌지, 브랜드와 소유자명을 포함할지는 Web 담당자와 승인된 계약으로 확정합니다. 현재 코드에는 계약이 없으므로 필드 이름, JSON 구조와 Callback 이름은 TBD입니다.

응답 종류 전달 원칙
성공 승인된 최소 카드정보만 요청 ID와 연결해 한 번 반환
사용자 취소 카드정보 없이 취소 상태만 반환

10. 마스킹과 민감정보 처리

카드 번호가 Native에서 Dart 영역으로 전달된 순간부터 CardScanResult.number를 카드 소유자 데이터로 취급합니다. 화면에 마스킹했다고 해서 메모리의 전체 번호가 사라지는 것은 아닙니다.

항목 현재 구현 유지 기준
화면 표시 maskedNumber만 사용 number나 formattedNumber를 UI에 직접 표시하지 않음
로그 카드 스캔 기능에서 결과를 로그로 출력하지 않음 전체 번호, 결과 객체와 OCR 원문을 로그·Crash·Analytics에 전달하지 않음
저장소 Auto Dispose Provider 메모리에만 일시 보관 SharedPreferences, 일반 파일, Database와 Clipboard에 저장하지 않음
WebView 전달 최종 연동 목표이며 현재 미구현 허용된 WebView와 요청에만 최소 필드를 일회성 응답으로 전달하고 URL·Query·범용 Event에는 포함하지 않음
CVV 패키지의 인식 필드가 아니며 앱도 처리하지 않음 스캔, 저장, 로그와 전송 대상에 추가하지 않음
카메라 Frame 패키지가 Native 메모리에서 처리하고 저장·전송하지 않음 별도 사진 저장이나 Gallery 스캔을 추가할 때 다시 검토
화면 캡처 방지 현재 확인한 앱 코드에는 구현되어 있지 않음 제품 정책 확정 후 Android·iOS에서 별도 구현·검증

패키지의 toString()은 번호를 마스킹하지만 앱 정책은 더 엄격하게 유지합니다. 객체의 다른 필드와 이름·유효기간도 개인정보가 될 수 있으므로 결과 객체 자체를 일반 로그에 남기지 않습니다. 이 패키지를 사용하거나 Luhn 검사를 통과했다고 해서 PCI DSS 요구사항을 충족하거나 인증을 대신하는 것은 아닙니다.

전체 번호를 WebView에 반환하면 Native뿐 아니라 WebView JavaScript 영역도 카드정보 처리 범위에 포함됩니다. 허용 Origin, 요청 Method, 응답 대상 Frame, 페이지 이동·새로고침·중복 Callback 시 폐기 기준을 제한하고, Console, Analytics, Session Replay, URL, Browser Storage와 오류 수집 도구에 값이 노출되지 않는지 Web과 App 양쪽에서 검증합니다.

12. 실제 기기 테스트

카메라 초점, 반사광, OCR 엔진과 권한 설정은 플랫폼과 단말에 따라 달라지므로 Android와 iOS 실제 기기에서 각각 검증합니다. 운영 카드 번호나 실제 고객 데이터를 Test Artifact로 남기지 않고, 카드사·결제사가 제공한 공식 Test 번호를 사용해 제작한 명확한 Test Data임을 표시합니다.

  1. 깨끗한 설치 상태에서 앱을 실행하고 /cardscan 화면에 진입합니다.
  2. 최초 카메라 권한 Prompt에서 허용과 거부를 각각 검증합니다.
  3. 지원 브랜드별 Test Card를 Frame 안에 두고 결과 반환 시간을 확인합니다.
  4. 표시된 번호가 마지막 네 자리 외에는 가려졌는지 확인합니다.
  5. 유효기간과 이름의 값·누락 처리를 실제 Test Card와 대조합니다.
  6. 화면을 벗어났다가 다시 진입해 이전 결과가 남지 않는지 확인합니다.
  7. Device Log, Crash Report, Analytics와 저장소에 전체 번호가 남지 않는지 확인합니다.

14. 유지보수와 향후 개선

유지보수 시 주의사항

  • 패키지 Version 변경 전 pubspec.lock의 실제 해석 Version과 공식 Changelog를 확인합니다.
  • 지원 브랜드, BIN, 번호 길이와 Luhn 규칙을 앱 코드에 별도로 복제하지 않습니다.
  • ScanRequirements를 바꾸면 완료 조건과 이름 누락 UX, 실제 기기 Test를 함께 갱신합니다.
  • Provider를 Keep Alive 또는 영구 저장으로 바꾸면 전체 번호의 수명과 삭제 시점을 다시 설계합니다.
  • 로그·Crash·Analytics·Session Replay 도구를 추가할 때 카드 화면과 결과 객체의 수집 여부를 점검합니다.
  • WebView Bridge는 카드 스캔 전용 Method와 응답 경계만 제공하고 범용 JavaScript 실행 통로로 확장하지 않습니다.
  • WebView Navigation 또는 재생성 뒤 이전 요청의 결과가 다른 페이지에 전달되지 않도록 요청 수명을 관리합니다.
  • 화면에 브랜드나 마지막 네 자리를 추가해도 전체 번호를 다시 조립할 수 있는 Data를 노출하지 않습니다.
  • Android·iOS 권한 요청을 패키지와 앱 양쪽에서 중복 소유하지 않습니다.
  • 기능 완료 판단은 Emulator만으로 끝내지 않고 최소 지원 OS와 최신 OS의 실제 기기에서 수행합니다.
