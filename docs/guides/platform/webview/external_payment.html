WebView 외부 결제 Intent·Scheme 연동 가이드

Web에서 구성한 외부 결제의 Intent·Scheme 실행과 서비스 앱 복귀를 Android·iOS OS 연동으로 지원하기 위한 기준입니다.

1. 목적과 적용 범위

이 문서는 Flutter WebView에서 구성한 외부 결제가 결제 앱, 인증 앱 또는 시스템 브라우저로 이동할 때 발생하는 플랫폼별 문제를 줄이기 위한 구현·검토 기준입니다.

결제사 연동, 결제 요청과 Return URL은 Web에서 구성합니다. WebView가 받은 Intent·Scheme을 Flutter에 전달하면 Android Kotlin과 iOS Swift는 허용된 외부 앱을 여는 OS 연동만 담당합니다. 서비스 앱 복귀 Scheme은 Native 설정에 등록하고, 복귀 이후 화면과 결과 조회는 Web이 처리합니다.

  • Flutter와 Android·iOS Native 사이의 호출 경계
  • 외부 결제 앱 또는 브라우저 실행과 앱 복귀
  • 앱 종료·백그라운드 전환·중복 실행·사용자 취소 처리
  • 서버 조회를 통한 최종 결제 상태 확인
  • 보안, 로그, 테스트와 배포 전 점검 기준

결제 상품 정책, 금액 계산, 승인·취소·환불 업무 규칙, Backend API 규격, 결제사 선정과 SDK별 설치 방법은 이 문서에서 확정하지 않습니다.

판매 대상과 출시 국가에 따라 앱 마켓의 외부 결제 허용 범위가 달라질 수 있으므로 구현 전에 법무·사업·배포 담당자가 스토어별 현재 정책을 확인하고 승인해야 합니다.

2. Flutter 계층에서 외부 결제를 직접 처리할 때의 문제

Flutter에서 외부 결제를 처리할 수 없는 것은 아닙니다. 다만 Web 결제 중 발생하는 플랫폼 전용 URL과 앱 전환을 Dart 코드 또는 범용 플러그인만으로 처리하면 Android·iOS의 실제 동작 차이가 추상화에 가려져 장애 원인과 책임 경계를 찾기 어려워질 수 있습니다.

문제 영역발생 가능한 문제이 프로젝트의 대응
Android Intent 해석intent: URL의 Scheme, Package, Fallback URL과 Extra를 플러그인이 모두 지원하지 않거나 원문을 잘못 변환할 수 있음WebView가 감지한 값을 Kotlin에 전달하고 허용 범위를 검증해 Intent 실행
Android 앱 조회 제한Android 11 이상에서 PackageManager로 결제 앱을 사전 조회하면 Package Visibility에 따라 결과가 필터링될 수 있음사전 조회가 필요할 때만 Manifest에 Query 등록. 바로 startActivity()를 호출하는 방식은 ActivityNotFoundException 처리
iOS Scheme 조회 제한LSApplicationQueriesSchemes에 없는 Scheme은 canOpenURL 결과가 실제 설치 상태와 다를 수 있음Web과 합의한 Scheme 중 설치 확인이 필요한 값만 등록
외부 앱 전환Flutter의 inactive·paused만으로 취소, 성공과 앱 복귀를 구분할 수 없음Native는 외부 앱 실행과 복귀 Scheme 수신만 처리하고 WebView가 상태 복구
Cold Start·Engine 재생성복귀 시 Flutter Engine이나 WebView가 준비되지 않아 정보가 유실될 수 있음Native에서 앱 진입을 수신하고 준비 완료 후 기존 WebView 복원
플러그인별 구현 차이Android·iOS 구현 범위, 오류 코드, 업데이트 시점과 지원 OS가 다를 수 있음외부 앱 실행 경계를 Kotlin·Swift Adapter로 고정하고 실제 기기 검증
오류 정보 축약앱 미설치, 허용되지 않은 Scheme과 실행 실패가 하나의 예외로 반환될 수 있음플랫폼 원인을 공통 앱 오류로 변환하되 민감한 원문은 Web에 노출하지 않음
설정의 이중 소유결제사 URL·Scheme을 Web과 Flutter에서 각각 관리하면 변경 시 불일치 발생결제사 설정은 Web, App은 최소 허용 목록과 복귀 Scheme만 관리
WebView Callback 범위Android shouldOverrideUrlLoading은 모든 Navigation에서 호출되지 않으며 POST 요청에는 호출되지 않음결제사별 이동 방식과 Redirect를 실제 WebView에서 확인하고 Callback만으로 전체 흐름을 보장한다고 가정하지 않음

문제의 원인을 Flutter Framework 자체로 단정하지 않습니다. 실제 원인은 WebView Navigation 처리, 사용 중인 플러그인, Android Manifest, iOS URL Types, 앱 수명주기 또는 결제사 URL 규격 중 하나일 수 있으므로 계층별 로그와 실제 기기로 구분해 확인합니다.

Flutter 플러그인을 유지할 수 있는 조건

  • 지원하는 Intent·Scheme과 오류 상태가 결제사 요구사항을 모두 충족합니다.
  • Android·iOS 최소 지원 버전과 실제 결제 앱 조합에서 검증되었습니다.
  • 앱 복귀와 Cold Start가 유실되지 않으며 WebView 복원 책임이 명확합니다.
  • 플러그인 업데이트와 장애 대응 책임을 프로젝트에서 유지할 수 있습니다.

이 조건을 충족하지 못하거나 플랫폼별 수정이 반복되면 Flutter에서 결제사별 로직을 늘리는 대신 Kotlin·Swift OS 연동 Adapter로 분리합니다.

3. 적용 결정과 역할

외부 결제 설정과 흐름은 Web이 소유합니다. Native는 WebView가 가로채 전달한 Intent·Scheme을 검증해 OS에 전달하고 서비스 앱 복귀 Scheme을 등록합니다.

영역담당책임
WebView Front-endWebView결제사 설정과 결제 요청, 외부 이동 URL 감지, Intent·Scheme 전달, Return URL과 결과 화면 처리
앱 조정 계층FlutterWebView의 외부 이동 요청을 Native에 중계하고 앱 복귀 후 WebView 복원
Android OS 연동Kotlin허용된 Intent·Custom Scheme 분석과 외부 앱 실행, 서비스 앱 복귀 Scheme 등록
iOS OS 연동Swift허용된 Custom Scheme·HTTPS URL로 외부 앱 실행, 서비스 앱 복귀 Scheme 등록
결제 BackendBackend결제 요청 생성, 금액·주문 검증, 멱등성 보장, 결제사 Callback 처리, 최종 상태 제공
결제 사업자PG·간편결제승인 UI, 사용자 인증, 결제 처리와 서버 통지

외부 결제 설정과 결과 처리는 Web이 담당합니다. Native는 WebView에서 전달받은 Intent·Scheme으로 외부 앱을 열고 서비스 앱의 복귀 Scheme을 등록하는 OS 연동만 담당하며, 결제 성공 여부를 판단하거나 결제 상태를 관리하지 않습니다.

이 역할 분리는 APP 개발 표준의 “일반 웹 결제를 우선 적용하고 필요한 Native 연동만 Flutter에서 처리” 기준을 구체화합니다.

4. 권장 처리 흐름

Native의 외부 앱 실행 결과와 앱 복귀는 결제 결과가 아닙니다. Web은 복귀 또는 WebView 재활성화 후 동일한 결제 시도 식별자로 Backend 상태를 조회합니다.

5. 결제사·Web·Native 복귀 계약

외부 결제와 복귀 흐름은 Web이 결제사 규격에 맞춰 구성합니다. Native와 Web이 함께 맞출 항목은 Web이 전달할 외부 앱 Scheme 허용 범위와 서비스 앱을 다시 열 복귀 Scheme입니다.

담당확정·구현할 항목
결제 담당·결제사지원하는 외부 앱 Scheme과 Return·Redirect 방식, 성공·실패·취소 복귀 조건, 허용 URL 등록 위치
Web Front-end결제사 연동 설정, 결제 요청, Return URL, Intent·Custom Scheme 감지와 App 전달, 복귀 화면과 결제 상태 조회
Backend결제 시도 식별자 발급, Return URL 허용 목록, 결제사 서버 Callback 검증, Web이 조회할 결제 상태 API와 멱등성 보장
Android Native전달받은 Intent·Scheme의 허용 여부 확인과 외부 앱 실행, 서비스 앱 복귀 Scheme 등록
iOS Native전달받은 Scheme·URL의 허용 여부 확인과 외부 앱 실행, 서비스 앱 복귀 Scheme 등록
App·Web 공통외부 앱 Scheme 허용 목록, 서비스 앱 복귀 Scheme, 앱 미설치 오류와 WebView 복원 방식

결제사에 전달할 Return·Redirect URL과 결과 Parameter는 Web에서 관리합니다. 서비스 앱 Scheme이 필요한 경우 Web은 Native에 등록된 확정 Scheme을 사용해야 합니다.

Native는 결제사별 업무 설정을 갖지 않습니다. 다만 WebView가 전달한 임의 Intent를 그대로 실행하지 않도록 허용할 Scheme, Package와 Fallback URL 처리 기준은 Web과 합의합니다.

복귀 계약에서 확정할 항목

  • 결제사 관리자 설정과 결제 준비 요청 중 Return URL을 지정하는 위치
  • 환경별 개발·QA·운영 HTTPS Domain과 정확한 Path
  • Android Manifest와 iOS URL Types에 등록할 서비스 앱 복귀 Scheme
  • 결제 앱 설치·미설치와 Intent 실행 실패 시 Web 대체 화면
  • 성공·실패·취소·사용자 이탈 시 결제사가 호출하는 URL과 Parameter
  • 결제사 복귀 값과 내부 결제 시도 식별자를 안전하게 연결하는 방식
  • Callback 유실, 중복 Callback과 앱 재실행 시 Backend 상태 조회 조건
  • 구버전 앱이 새 Return URL 또는 계약 버전을 처리하지 못할 때의 호환 정책

Return URL, 결과 Parameter와 Backend 상태 조회는 Web이 처리합니다. Native는 외부 앱 실행과 서비스 앱 Scheme 수신 뒤 기존 WebView를 복원할 뿐 결제 결과 값을 해석하지 않습니다.

6. 결제 상태 모델

화면과 플랫폼 Callback을 단순 success·failure Boolean으로 연결하지 않습니다. 실제 상태 이름과 서버 값은 승인된 계약에 맞춰 확정합니다.

상태의미사용자 처리
준비 중서버에서 결제 시도를 생성하는 중중복 입력 차단과 진행 표시
외부 결제 진행 중Web이 구성한 요청에 따라 Native가 외부 앱을 열었음앱 복귀 안내와 중복 실행 차단
결과 확인 중앱 복귀 또는 재진입 후 서버 상태를 조회함결제 성공으로 미리 표시하지 않음
완료Backend가 최종 성공을 확인함예약·이용권 등 후속 결과 표시
실패Backend가 최종 실패를 확인함안전한 재시도 또는 결제수단 변경 제공
취소사용자가 결제 흐름을 명시적으로 취소함오류로 과장하지 않고 기존 화면 복귀
미확정복귀 유실, Timeout 또는 서버 처리 지연자동 재결제 금지, 동일 시도 상태 재조회

앱이 백그라운드로 이동한 것만으로 취소 처리하지 않습니다. 앱이 활성화되어도 Web Return URL 처리가 완료되지 않았을 수 있으므로 WebView가 서버 상태를 조회해 미확정 상태를 해소합니다.

7. Flutter와 Native 경계

Flutter는 결제사별 세부사항을 포함하지 않고 WebView가 전달한 외부 이동 URL을 Native에 중계합니다. 실제 앱의 WebView Navigation Delegate와 Platform Channel 구성을 기준으로 확정합니다.

  • 사용자의 명시적인 결제 동작에서 한 번만 시작합니다.
  • 동시에 하나의 결제 시도만 활성화하고 빠른 중복 Tap을 차단합니다.
  • Flutter 화면이나 Activity·ViewController가 다시 만들어져도 진행 중 식별자를 복구합니다.
  • 중복 Callback은 같은 결제 시도의 상태 조회로 수렴시킵니다.
  • Flutter Engine이 없는 상태에서 들어온 복귀 이벤트는 안전하게 보관한 뒤 전달합니다.
  • 채널 연결 해제, 앱 종료와 Timeout이 발생해도 결제를 자동으로 다시 실행하지 않습니다.

호출 계약에서 확정할 항목

TBD Platform Channel과 Method 이름, WebView가 전달할 URL 형식, 허용 Scheme·Host·Package, 앱 미설치 오류와 서비스 앱 복귀 후 WebView 복원 방식을 Web과 App이 확정합니다.

WebView가 외부 앱 실행을 요청하려면 intent: URL 또는 Custom Scheme URL을 Flutter·Native에 전달할 수 있습니다. 이 URL은 허용 Scheme·Host·Package와 Fallback 범위를 검증하고 필요한 경우 민감한 Query를 제거한 뒤 실행합니다. 카드번호, CVC, 인증번호, 세션 Token과 결제사 Secret은 URL, Flutter 채널 또는 WebView Bridge로 전달하지 않습니다.

8. Android Kotlin 구현 기준

  • WebView가 전달한 intent: URL 또는 Custom Scheme을 검증하고 OS Intent로 외부 결제 앱을 엽니다.
  • 실행 가능한 Scheme·Host·Package를 허용 목록으로 관리합니다.
  • 암시적 Intent에 신뢰하지 않은 URL이나 임의 Extra를 그대로 전달하지 않습니다.
  • 설치 여부 조회에는 Android Package Visibility 정책에 맞는 최소 범위만 선언합니다.
  • 서비스 앱 복귀 Scheme은 Web과 합의한 값만 Manifest의 Intent Filter에 등록합니다.
  • onNewIntent, 새 Activity와 프로세스 재생성 진입이 같은 복귀 처리기로 수렴해야 합니다.

shouldOverrideUrlLoading은 모든 Navigation을 전달하지 않으며 POST 요청에는 호출되지 않습니다. 결제사 페이지가 JavaScript 이동, Redirect, iframe 또는 POST를 어떻게 사용하는지 실제 WebView에서 확인하고, 이 Callback 하나로 모든 외부 결제 이동을 탐지한다고 가정하지 않습니다.

외부 Activity 실행 성공은 결제 성공이 아닙니다. 구체적인 Intent 파싱, Package Query와 Manifest 코드는 Web 결제사가 전달하는 URL 형식과 지원 결제 앱 목록이 확정된 뒤 작성합니다.

9. iOS Swift 구현 기준

  • WebView가 전달한 Custom Scheme 또는 HTTPS URL을 검증하고 UIApplication URL 열기 API로 외부 앱을 엽니다.
  • 실행 가능한 Scheme·Host를 허용 목록으로 관리합니다.
  • canOpenURL로 조회할 Scheme만 LSApplicationQueriesSchemes에 최소로 선언합니다.
  • 서비스 앱 복귀 Scheme은 Web과 합의한 값만 URL Types에 등록합니다.
  • AppDelegate와 SceneDelegate의 실제 복귀 경로가 같은 처리기로 수렴해야 합니다.
  • 실행 중·백그라운드·종료 상태의 복귀를 각각 검증합니다.

외부 앱 열기 완료 Callback은 URL 전달 성공만 의미합니다. Return URL과 결제 상태 조회는 WebView가 처리합니다.

10. 복귀 URL과 입력 검증

  • 허용된 HTTPS Scheme 또는 승인된 Custom Scheme인지 확인합니다.
  • Scheme, Host, Port와 Path를 정확히 비교하고 부분 문자열 비교를 사용하지 않습니다.
  • 예상하지 않은 Redirect URL, 중첩 URL과 임의 Query를 거부합니다.
  • 요청 연결값이 현재 진행 중 결제와 일치하는지 확인합니다.
  • 동일 복귀 이벤트가 여러 번 들어와도 결제 실행과 후속 처리를 중복 수행하지 않습니다.
  • 민감값과 전체 URL을 로그·분석 도구·Crash Report에 기록하지 않습니다.
  • 복귀 값만으로 금액, 상품, 사용자와 성공 여부를 확정하지 않습니다.

TBD 외부 앱 Scheme 허용 목록과 서비스 앱 복귀 Scheme은 Web·App·보안 담당자가 함께 승인합니다. Redirect 경로와 결제 결과 Parameter는 Web·Backend·결제 담당자가 확정합니다.

11. 실패와 복구 기준

상황처리 기준
결제 앱 미설치승인된 스토어 또는 웹 결제 경로 안내
외부 앱 실행 실패결제를 재생성하지 않고 같은 시도의 서버 상태부터 확인
사용자가 뒤로 가기취소 Callback이 명확할 때만 취소, 그 외에는 상태 확인
복귀 Callback 유실앱 활성화 또는 결제 화면 재진입 시 같은 시도 상태 조회
앱 프로세스 종료WebView가 서버 상태로 복구하며 외부 앱을 자동 재실행하지 않음
네트워크 단절미확정 상태 유지 후 연결 복구 시 상태 조회
Backend Callback 지연제한된 간격으로 조회하고 확인 필요 상태 제공
중복 Tap·Callback서버 멱등성 Key와 앱의 단일 진행 상태로 수렴
앱 버전 불일치실행을 차단하고 업데이트 또는 승인된 대체 흐름 안내

재시도는 새 결제 생성과 기존 결제 상태 재조회를 구분합니다. 미확정 결제를 새로 실행하지 않고 기존 상태부터 확인합니다.

12. 보안과 개인정보

  • 주문 금액, 할인, 사용자 자격과 결제 가능 여부는 Backend가 다시 검증합니다.
  • 결제 요청 생성과 승인·취소 API는 서버에서 멱등성을 보장합니다.
  • 결제사 Secret, 서명 Key와 관리자 자격 증명은 앱에 포함하지 않습니다.
  • 카드정보와 인증정보는 결제사 SDK 또는 승인된 결제 화면에서만 취급합니다.
  • Bridge와 Platform Channel에는 필요한 최소 식별값만 전달합니다.
  • 운영 로그에 URL Query, 결제 Token, 사용자 식별정보와 결제사 원문 오류를 남기지 않습니다.
  • 결제사 SDK의 공식 배포 경로, 무결성, 라이선스, 개인정보와 업데이트 영향을 검토합니다.

16. 적용 순서와 완료 조건

  1. 결제사별 Android·iOS 공식 연동 규격과 Backend 계약을 승인합니다.
  2. 앱 복귀 도메인·Scheme, 상태 모델과 멱등성 기준을 확정합니다.
  3. Flutter–Native 계약을 버전이 있는 최소 규격으로 정의합니다.
  4. Kotlin·Swift 결제 Adapter와 모든 앱 복귀 진입점을 구현합니다.
  5. Flutter 조정 계층과 WebView 처리 중·확인 중·복구 UI를 연결합니다.
  6. WebView의 Backend 상태 조회와 중복 방지 시나리오를 통합 검증합니다.
  7. 실제 기기·결제사 Sandbox에서 플랫폼별 회귀 테스트를 수행합니다.
  8. 로그 마스킹, 장애 지표, 배포·Rollback과 고객지원 절차를 확인합니다.

완료 조건

  • Android와 iOS에서 외부 결제 실행·복귀·Cold Start 복구가 동작합니다.
  • Native 복귀 신호와 Flutter 전달 이후 WebView가 Backend 상태를 조회하고 검증된 결과를 표시합니다.
  • 중복 Tap, 중복 Callback, 앱 종료와 네트워크 단절이 중복 결제를 만들지 않습니다.
  • 허용되지 않은 URL과 변조된 복귀 값이 차단됩니다.
  • 운영 로그와 분석 Event에서 민감정보가 제거됩니다.
  • 최소 지원 OS와 대표 결제 앱 조합의 실제 기기 결과가 기록됩니다.
