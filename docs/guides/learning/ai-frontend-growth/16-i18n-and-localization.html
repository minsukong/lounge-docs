16. 다국어와 번역 경계

UI 문구, 서버 콘텐츠, 사용자 작성 콘텐츠를 구분하고, 언어 선택과 fallback, 번역 생성이 어디까지 각자의 책임인지 학습합니다.

1. 학습 목표

교육 과정 · 다국어 및 로컬 LLM 번역 가이드

고급 트랙입니다. 13단계 핵심 과정을 완료한 뒤, 화면을 여러 언어로 제공해야 할 때 학습합니다. 상세 기준은 다국어 및 로컬 LLM 번역 가이드가 소유하며, 이 단위는 그 가이드를 적용할 수 있게 익히는 경로입니다.

  • UI 문구, 서버 콘텐츠, 사용자 작성 콘텐츠 세 종류를 구분합니다.
  • 실행 언어 선택의 우선순위와 fallback 체인을 설명합니다.
  • 로컬 LLM 번역의 개발 시 역할과 실행 중 경계를 구분합니다.

2. 꼭 알아야 할 내용

한국어 원문을 코드에 작성하고, 번역 키는 도구가 만듭니다

개발자는 번역 키를 먼저 만들지 않고 한국어 문구를 코드에 직접 작성합니다. 추출 도구가 소스를 검색해 자동 ID와 언어별 카탈로그를 생성·병합하고, 카탈로그는 소스와 함께 검토해 저장소에 반영합니다. 생성된 실행 카탈로그는 사람이 직접 수정하지 않습니다.

정적 표현만 추출됩니다

추출 도구가 JSX에서 정적으로 확인할 수 있는 메시지 번역 대상입니다. 동적 값은 메시지 안의 변수로 전달하고, 같은 한국어가 문맥에 따라 다르게 번역되어야 하면 context로 구분합니다. 변수에 저장한 일반 문자열을 나중에 번역 함수에 넘기는 패턴은 추출되지 않습니다.

세 종류 콘텐츠는 소유자가 다릅니다

UI 문구는 Lingui 카탈로그로 관리합니다. 서버가 주는 상품명과 API 오류 문구는 서버 콘텐츠이며 다국어 계약이 UI 카탈로그와 별도로 정의됩니다. 사용자가 작성한 리뷰·댓글·게시글은 카탈로그에 넣지 않고, 사용자가 요청한 경우에만 기기에서 번역합니다. 사용자명, 브랜드명, 코드 같은 고유 식별값은 번역하지 않습니다.

언어 선택에는 우선순위와 fallback 체인이 있습니다

실행 언어는 앱 설정에서 사용자가 직접 선택한 언어, Flutter가 WebView 초기 요청에 전달한 값, Accept-Language, 브라우저 언어 순으로 결정하고 마지막에 영어를 기본으로 둡니다. 받은 언어 코드는 BCP 47 기준으로 정규화해 지원 언어(ko, zh-CN, ja, en)에 매핑하고, 번역이 누락되면 영어를, 영어도 없으면 한국어 원문을 사용합니다. 첫 화면이 fallback 언어로 잠깐 보였다가 바뀌지 않도록 최초 문서 요청 전에 언어를 결정합니다.

로컬 LLM은 개발 중 도구입니다

로컬 LLM은 비어 있거나 원문이 변경된 항목만 번역해 개발 중 카탈로그 후보를 만드는 데 사용합니다. 실행 중에는 준비된 카탈로그만 읽으며 사용자 요청 경로에서 LLM을 호출하지 않습니다. 자동 번역 결과는 후보이며 결제·환불·개인정보·약관처럼 의미 오류의 영향이 큰 문구는 담당자 검토 없이 확정 문구로 쓰지 않습니다.

기기 번역은 capability 계약입니다

기기 번역 지원 여부는 WebView의 User-Agent나 OS 버전 문자열 추측이 아니라 Flutter Bridge가 전달하는 capability로 판단합니다. 지원되지 않거나 번역이 실패하면 기능만 비활성화하고 원문을 표시하며, 번역되지 않은 문장을 빈 문자열로 숨기지 않습니다.

3. 코드 읽기

첫 번째는 추출되는 메시지입니다. 한국어 원문이 정적으로 작성되어 있고, 이름은 메시지 안의 변수로 전달됩니다.

import { Trans } from '@lingui/react/macro';

interface WelcomeMessageProps {
  name: string;
}

export function WelcomeMessage({ name }: WelcomeMessageProps) {
  return <p><Trans>{name}님, 환영합니다</Trans></p>;
}

두 번째는 추출되지 않습니다. 추출기가 label의 실제 값을 확인할 수 없어 카탈로그에 들어가지 못하고, 실행 중에 번역되지 않은 채 남습니다.

// 추출기가 label의 실제 값을 확인할 수 없습니다.
const label = getLoginLabel();
return <button>{label}</button>;

4. AI와 함께 연습

  1. AI에게 화면의 문구를 UI 문구·서버 콘텐츠·사용자 작성 콘텐츠로 분류하게 한 뒤, 분류 기준이 다국어 가이드와 일치하는지 대조합니다.
  2. 변수에 저장한 문자열, 조합되는 문장처럼 정적으로 추출되지 않는 메시지를 찾게 합니다.
  3. 언어 선택 우선순위와 fallback 체인을 표로 만들게 하고, 가이드의 기준과 다른 지점을 지적하게 합니다.
  4. Bridge 계약, 카탈로그 경로, 검토 담당자처럼 아직 확정되지 않은 항목과 지금 구현할 수 있는 항목을 분리하게 합니다.

5. 완료 확인

  • UI 문구, 서버 콘텐츠, 사용자 콘텐츠를 구분하고 각각의 관리 방법을 설명할 수 있습니다.
  • 언어 선택 우선순위, 정규화와 fallback 체인을 설명할 수 있습니다.
  • 로컬 LLM 번역의 개발 중 역할과 실행 중 경계를 구분할 수 있습니다.
  • 도구와 계약이 미확정일 때 검증 절차와 TBD를 분리해 관리할 수 있습니다.

6. 레이아웃과 품질 게이트 심화

긴 문구 레이아웃

같은 메시지도 언어마다 길이가 다릅니다. 고정 너비, 절대 위치와 버튼 너비를 전제한 배치는 문구가 긴 언어에서 깨집니다. 핵심 화면은 길이가 긴 후보 문구로 레이아웃을 확인하고, 텍스트가 잘리지 않고 컨테이너가 늘어나는 방향으로 설계·검증합니다.

자리표시자 보존은 코드로 검증합니다

변수, ICU 문법과 요소 자리표시자는 번역 전후에 유지되어야 합니다. 원본 변수와 태그가 프롬프트 지시만으로 보존되었다고 판단하지 않고, 키·변수·태그·JSON 구조를 코드로 검사합니다.

누락 번역을 품질 게이트로 두는 시점

누락 번역을 CI 오류로 처리할 시점과 배포 품질 Gate는 아직 확정되지 않았습니다(TBD). 확정 전에는 누락 항목을 반복 확인 가능한 절차로 관리하고, 임의로 Build를 막지 않습니다.

7. 마스터 실습과 증거

UI 문구, 상품명과 사용자 리뷰가 섞인 화면에서 세 종류 콘텐츠 분류표를 작성합니다. UI 문구는 추출 가능한 메시지로 작성하고, 언어 선택 우선순위와 fallback 표, 추출 불가능 메시지 목록, 확정이 필요한 TBD 목록(Bridge 계약, 카탈로그 경로, 검토 담당자)을 함께 제출합니다.

통과 기준: 세 종류 콘텐츠의 경계와 언어 선택·fallback 규칙을 다국어 가이드 기준으로 설명하고, 지금 구현할 수 있는 것과 계약 확정을 기다리는 것을 분리할 수 있어야 합니다. 실행 중에 번역 LLM을 호출하지 않고, 사용자 콘텐츠를 UI 카탈로그에 넣지 않아야 합니다.
