PROJECT STATUS BRIEFING

더라운지 3.0 프로젝트 현황 및 정상화 필요사항

현재 확인 가능한 자료의 상태와 한계를 구분하고, 실행 가능한 범위와 일정을 다시 수립하기 위해 필요한 조치를 정리합니다.

1. 결론

현재 확인한 IA, WBS, 기획, 디자인과 인터페이스 자료에는 최종 승인된 개발 기준임을 확인할 근거가 부족합니다. 기존 자료의 숫자, 일정과 목록은 담당 파트의 검증과 확정 전까지 참고 정보로 구분해야 합니다.

지금 필요한 것은 기존 일정의 날짜를 수정하는 작업이 아니라, 범위와 상태를 검증하고 파트 간 선후행 관계를 연결해 WBS를 다시 수립하는 것입니다.

확인 항목 내용
목적 현재 상태, 미확정 사항, 일정 영향과 정상화 조치를 공통 기준으로 공유
범위 IA, 기획, 디자인, API, WebView·Native, 일정과 QA
제외 특정 개인이나 조직의 책임 및 역량 평가
문서 한계 최종 IA, 화면별 기획서, 디자인 원본, Backend API 명세와 Native 연동 명세를 대신하지 않음

2. 현재 상태

영역 현재 확인 결과 판단
IA Page, Layer, Tab, Link와 Content 상태의 집계 기준 및 누락 범위 확인 필요 검증 필요
WBS 검증된 범위, 선행조건, 확인 대기와 통합 검증 기간의 연결이 부족함 재수립 필요
기획 화면별 업무 규칙, 상태, 예외 흐름과 데이터 출처의 확정 여부 확인 필요 확정 필요
디자인 시각 구성과 실제 데이터·상태·이동 규칙이 연결되지 않은 항목이 존재함 협의 필요
인터페이스 v0.8.1 내부 확인용. Endpoint 목록과 일부 형식은 있으나 상세 요청·응답 및 인증 기준이 부족함 기준 명세 아님
통합 검증 QA·UAT, 실제 기기, 환경과 파트별 완료 기준의 연결 필요 계획 필요

현재 문제는 자료가 전혀 없다는 의미가 아닙니다. 자료에 포함된 값과 분류가 공식 개발 범위와 일정의 기준선으로 검증·확정된 상태가 아니라는 점이 핵심입니다.

3. 활용 가능한 자료와 한계

3.1 Front-end 구현 및 품질 기준

  • Front-end 개발 가이드와 저장소 구조 기준
  • 디자인 토큰과 Figma 연계 기준
  • Storybook을 이용한 UI 상태 검수 기준
  • TypeScript, 상태 관리, 네트워크와 세션 처리 기준
  • 테스트, 접근성, 보안, 성능과 브라우저 지원 기준
  • WebView 환경과 Native 기능 연동 시 확인할 책임 경계

위 자료는 개발과 검토의 공통 기준으로 활용할 수 있습니다. 그러나 실제 업무 규칙이나 승인된 API 명세가 없는 상태에서 기능 요구사항을 대신 확정하지는 않습니다.

3.2 일정 산정 자료

일정 산정 자료는 당시 IA에 분류된 값을 바탕으로 역할 구분 방식, 특정 인력 구성의 예상 기간과 일정 전제조건을 검토한 참고 자료입니다.

  • 당시 화면 수는 최종 범위가 아니며 실제 신규 화면 수와 동일하게 해석할 수 없습니다.
  • 특정 인력 구성과 기간은 당시 범위와 선행조건을 가정한 산정 시나리오입니다.
  • Web, WebView와 Native의 역할 분류 방식은 참고할 수 있지만 실제 기능, 화면과 수량은 다시 확인해야 합니다.

3.3 인터페이스 자료

현재 확인한 자료는 v0.8.1 내부 확인용입니다. API 영역, Endpoint 목록, 일부 응답 형식과 오류 코드를 파악하는 참고 자료로는 사용할 수 있지만 최종 구현 기준은 아닙니다.

확인된 내용 아직 필요한 내용
API 영역과 Endpoint 목록 기능별 상세 요청·응답과 필수 Field
일부 응답 형식과 오류 코드 화면 상태와 연결되는 전체 오류 처리 기준
개발·운영 Host 일부 환경별 적용 대상과 QA 데이터
IN-APP API 66건의 Endpoint 목록 66건의 상세 요청·응답 명세
서명과 Token 방식에 대한 설명 생성 주체, 수명, 갱신과 만료 처리 기준

5. 파트 간 주요 의존관계

작업 영역 필요한 선행조건 주요 협의 파트 미확정 시 영향

API 연동 요청·응답, 인증과 오류 규칙 Front-end·Backend·기획 Type, 상태 처리와 테스트 재작업
WebView 연동 시작 주소, 세션과 Bridge 규격 Front-end·Flutter·Backend 로그인, 이동과 기기 기능 검증 지연

모든 선행조건이 완성될 때까지 전체 개발을 중단한다는 의미는 아닙니다. 기능별로 협의된 범위부터 진행하고, 협의되지 않은 기능은 대기 사유와 일정 영향을 구분해 관리해야 합니다.

6. IA와 WBS 재수립

현재 기재된 화면 수, 작업 기간과 완료일을 확정 범위 또는 공식 일정으로 해석하기 어렵습니다. 기존 날짜를 수정하기 전에 범위 집계 기준과 선후행 관계부터 다시 세워야 합니다.

6.1 WBS에 포함할 항목

  • 작업 범위와 완료 결과물
  • 선행 작업과 입력 자료
  • 담당 파트와 확인 또는 결정 담당
  • 착수 가능 조건과 예상 작업 기간
  • 파트 간 검토 및 수정 기간
  • 통합 테스트, QA와 UAT 기간
  • 미확정 사항과 결정 목표일
  • 일정 변경 시 영향을 받는 후속 작업

6.2 다시 수립하는 순서

  1. IA의 화면·상태 분류 기준과 누락 범위를 정비하고 검증합니다.
  2. 검증된 최종 범위와 화면 목록을 기준선으로 고정합니다.
  3. 기능별 미확정 사항과 관련 파트를 연결합니다.
  4. 기획, 디자인, Backend와 Native의 제공 일정을 확인합니다.
  5. 제공 순서에 따라 개발 가능한 기능 묶음을 구성합니다.
  6. 실제 투입 인력과 검토 가능 시간을 반영합니다.
  7. 통합, QA, UAT와 안정화 기간을 포함합니다.
  8. 위험이 현실화되면 완료일 또는 범위를 함께 조정합니다.

인력 보강은 병렬 구현에는 도움이 되지만, 기획·디자인·API와 Native 연동의 확인 대기나 의사결정 지연을 직접 줄이지는 못합니다.

번호 리스크 예상 영향 대응 방향

R5 Web-Native 협의 지연 로그인, 외부 이동과 기기 기능 통합 지연 Bridge, 세션과 앱 복귀 규격 우선 협의

R7 FE 인력 대비 범위 과다 구현, 협의, 리뷰와 통합이 한 역할에 집중 역할 분담과 실제 가동률을 반영해 일정 재산정
R8 미확정 항목의 개발자 판단 파트마다 다른 규칙을 구현 결정 주체와 목표일을 지정하고 결과 기록
R9 QA 환경과 실제 기기 제공 지연 개발 완료 후 검증 및 배포 대기 환경과 기기 제공 일정을 WBS에 포함

8. 정상화 단계

단계 완료 기준
1. 자료 상태 구분 확정, 검토 중, 참고와 미작성 자료를 구분
2. IA·범위 검증 분류 기준, 누락 상태와 최종 화면 목록 확인
3. 파트별 협의 기획·디자인·API·Native 미확정 항목의 담당과 목표일 지정
4. WBS 재수립 선행조건, 제공 일정, 실제 인력과 통합 검증 기간 반영
5. 기능별 실행 협의된 기능부터 구현하고 대기 항목의 일정 영향을 관리
6. 통합 검증 QA·UAT, 실제 기기, 배포와 운영 기준 확인

세부 책임은 조직의 공식 역할 정의와 파트 간 협의 결과를 우선합니다. Front-end 문서군이 존재한다는 사실만으로 각 파트의 최종 결정과 산출물이 완료된 것은 아닙니다.

10. 기능별 착수 및 완료 기준

10.1 착수 기준

  • 구현할 화면과 사용자 흐름
  • 주요 정상 및 예외 상태
  • 최종 또는 개발 가능한 수준의 디자인
  • 필요한 데이터와 제공 주체
  • API 또는 Native 연동 여부
  • 관련 파트의 협의 결과
  • 기능 완료를 판단할 검증 기준

일부 항목이 미확정이어도 독립적으로 진행 가능한 작업은 분리할 수 있습니다. 이 경우 확정 범위와 미확정 범위를 작업 항목에 함께 기록합니다.

10.2 완료 기준

  • 합의된 IA와 화면 상태가 구현되어 있습니다.
  • 승인된 데이터와 API 기준으로 정상 및 주요 오류 흐름이 동작합니다.
  • WebView와 Native 연동 기능이 실제 앱 환경에서 검증됐습니다.
  • 결제, 인증과 권한의 성공·실패·취소·재시도가 확인됐습니다.
  • 주요 반응형 해상도와 지원 브라우저에서 동작합니다.
  • 로딩, 데이터 없음, 오류와 접근 제한 상태가 확인됐습니다.
  • 주요 기능의 테스트와 회귀 확인이 완료됐습니다.
  • QA 및 UAT의 주요 결함이 해결됐습니다.
  • 배포 및 운영에 필요한 환경과 책임자가 확인됐습니다.

11. 최종 정리

현재 Front-end 구현과 품질을 위한 기준 자료는 개발 방향을 통일하고 필요한 협의사항을 식별하는 데 활용할 수 있습니다. 그러나 이 자료가 IA, 기획, 디자인, API와 Native의 최종 확정을 대신하지는 않습니다.

프로젝트 일정의 신뢰성을 확보하려면 IA와 기획 범위를 먼저 검증하고, 파트별 협의 결과와 실제 투입 인력을 새 WBS에 연결해야 합니다. 개발 가능한 기능은 순차적으로 진행하고, 협의가 필요한 기능은 대기 사유와 일정 영향을 투명하게 관리해야 합니다.
