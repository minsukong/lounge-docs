# shadcn·Tailwind CSS 기반 공통 UI 디자인 협의안

## 1. 이번 협의에서 정할 범위

현재 전달된 색상 팔레트를 기준으로, **각 색상과 디자인 수치를 어떤 역할에 사용하고 공통 컴포넌트에 어떻게 적용할지** 결정한다.

개발은 기존 shadcn 컴포넌트를 활용해 디자인을 구현한다. shadcn의 기본 외형을 그대로 사용하는 것이 아니라, 접근성·키보드·포커스 등의 기본 동작을 유지하면서 합의된 색상·크기·모양을 적용한다.

디자인팀은 화면에서의 역할과 시각적 기준을 정하고, 개발팀은 이를 Tokens Studio의 토큰 구조, CSS 변수, Tailwind 유틸리티와 컴포넌트 코드에 연결한다. 디자인팀이 개발 변수 이름까지 직접 정할 필요는 없다.

**이번 협의의 결과물**

- 역할별 색상 대응표
- 공통 타이포그래피·간격·크기·라운드 기준
- 주요 컴포넌트의 종류와 상태별 디자인
- 모바일·PC의 공통점과 차이
- 대표 UI 검수 결과와 미정 항목 목록

현재 light·dark의 색상값이 같다는 결정은 유지한다. Dark 전용 색상 설계는 이후 작업으로 둔다.

## 2. 색상: 팔레트에서 실제 역할로 연결

색상이 존재하는 것과 사용 규칙이 정해진 것은 구분한다. 예를 들어 Blue 500·Blue 600 중 어떤 것을 주요 버튼에 쓰는지, 본문 링크에도 같은 색을 쓰는지 결정해야 한다.

### 역할별로 결정할 항목

| 역할           | 디자인팀과 확인할 내용                                                       | 개발 연결                            |
| -------------- | ---------------------------------------------------------------------------- | ------------------------------------ |
| 화면 기본 배경 | 흰색인가, 옅은 회색인가. 카드가 있는 화면과 일반 화면이 같은가               | `background`                         |
| 기본 본문      | 제목과 본문에 같은 색을 쓰는가. 강조는 색상·굵기 중 무엇으로 구분하는가      | `foreground`                         |
| 카드 배경·본문 | 화면 배경과 어떻게 구분하는가. 테두리나 그림자가 필요한가                    | `card` / `card-foreground`           |
| 팝업·선택 목록 | 카드와 같은 배경을 쓰는가. 떠 있는 영역의 구분 방식은 무엇인가               | `popover` / `popover-foreground`     |
| 주요 행동      | 주요 버튼에 사용할 브랜드 색상과 그 위의 글자·아이콘 색상                    | `primary` / `primary-foreground`     |
| 보조 행동      | 주요 버튼과 나란히 있을 때 사용할 배경·글자색                                | `secondary` / `secondary-foreground` |
| 약한 배경      | 구획·비활성에 가까운 영역·보조 정보의 배경을 같은 색으로 처리하는가          | `muted`                              |
| 보조 문구      | 설명·도움말·시간·메타 정보의 글자색. Placeholder와 구분하는가                | `muted-foreground` 또는 별도 역할    |
| 상호작용 강조  | 메뉴 항목·선택 가능한 행의 hover 배경과 글자색                               | `accent` / `accent-foreground`       |
| 위험 행동·오류 | 삭제 버튼과 입력 오류에 같은 색을 쓰는가. 배경·글자·테두리를 어떻게 나누는가 | `destructive` 및 필요한 오류 역할    |
| 구분선         | 카드 테두리·목록 구분선·영역 경계에 같은 색을 쓰는가                         | `border`                             |
| 입력창 테두리  | 일반 구분선보다 강하게 보여야 하는가                                         | `input`                              |
| 키보드 포커스  | 포커스 표시의 색상·두께·간격. 오류 상태에서도 식별되는가                     | `ring` 및 포커스 스타일              |
| 성공·경고·안내 | 각 상태의 글자·아이콘·옅은 배경·테두리 조합                                  | 사용처에 맞는 상태 토큰              |
| 배경 가림      | Dialog·Sheet의 Dim과 Toast의 배경을 어디에 적용하는가                        | 오버레이·알림 역할                   |

### 먼저 결정할 구체적인 질문

- 주요 버튼은 **Blue 500 `#566CC2`와 Blue 600 `#435CBC` 중 어떤 색**을 사용하는가?
- 주요 버튼의 글자·아이콘은 항상 흰색인가?
- 본문 링크는 주요 버튼과 같은 색인가?
- 카드와 화면 배경은 어떤 조합으로 구분하는가?
- Placeholder와 보조 설명은 같은 회색인가?
- 오류·경고·성공 색상을 작은 글자에 직접 사용해도 읽기 쉬운가?
- 선택 상태와 hover 상태는 같은 배경인가, 다른 배경인가?
- 비활성 상태는 전체 투명도를 낮출지, 별도 색상 조합을 사용할지?

각 조합은 실제 크기의 글자·입력창·버튼에 적용해 가독성을 확인한다. 특정 조합의 대비가 부족하면 원본 팔레트를 임의로 바꾸지 않고, 역할 연결이나 표현 방식을 함께 조정한다.

## 3. 버튼: 종류·크기·상태를 함께 결정

현재 구현된 버튼 종류를 기준으로 사용 목적을 정한다. 종류 이름 자체보다 **사용자가 어떤 행동을 하는 버튼인지**를 먼저 합의한다.

### 버튼 종류

| 종류                    | 합의할 사용 목적                          | 디자인 결정                               |
| ----------------------- | ----------------------------------------- | ----------------------------------------- |
| 기본형 `default`        | 화면에서 가장 중요한 행동                 | 채운 배경, 글자·아이콘 색, 강조 수준      |
| 보조형 `secondary`      | 기본 행동과 함께 제공하는 보조 행동       | 배경·글자색과 기본형과의 구분             |
| 테두리형 `outline`      | 테두리로 구분하는 독립 행동               | 배경 유무, 테두리 색·두께, hover          |
| 약한 버튼 `ghost`       | 도구·목록·헤더 등에 배치하는 행동         | 기본 배경 유무, hover 영역, 클릭 범위     |
| 위험 행동 `destructive` | 삭제 등 결과에 주의가 필요한 행동         | 채움형·테두리형 중 표현, 오류색 사용 방식 |
| 링크형 `link`           | 문장이나 콘텐츠 안에서 제공하는 이동·행동 | 글자색, 밑줄, hover·포커스                |

모든 종류를 반드시 사용할 필요는 없다. 디자인에서 구분할 이유가 없는 종류는 사용하지 않아도 된다.

### 크기와 배치

- 기본·작은·큰 버튼 각각의 높이
- 최소 너비와 좌우 여백
- 글자 크기·굵기·행간
- 아이콘 크기와 글자 사이 간격
- 아이콘 전용 버튼의 외형과 클릭 영역
- 라운드와 테두리 두께
- 전체 너비 버튼을 사용하는 위치
- 버튼이 두 개일 때의 순서·간격·너비 비율
- 긴 문구에서 줄바꿈을 허용할지 여부
- 모바일 하단 고정 버튼에서의 여백과 안전 영역

시각적으로 작은 버튼도 터치·클릭 영역을 충분히 확보할 수 있도록 외형과 조작 영역을 함께 확인한다.

### 상태

기본·hover·누름·키보드 포커스·비활성·로딩 상태를 확인한다.

특히 로딩 버튼은 다음을 정한다.

- 기존 문구를 유지할지, 다른 문구로 바꿀지
- Spinner를 아이콘 위치에 표시할지
- 로딩 중 버튼 너비가 변하지 않게 할지
- 비활성 버튼과 로딩 버튼을 시각적으로 어떻게 구분할지

## 4. 입력·선택 컴포넌트

### Input·Textarea

| 항목             | 결정할 내용                                    |
| ---------------- | ---------------------------------------------- |
| 기본 외형        | 높이, 배경, 테두리, 라운드, 내부 여백          |
| 입력 글자        | 글자 크기·굵기·행간·색상                       |
| Placeholder      | 색상, 예시 문구 방식, 긴 문구 처리             |
| Label            | 크기·굵기, 필수 표시, 입력창과의 간격          |
| 도움말           | Label 아래 또는 입력창 아래 중 위치, 크기·색상 |
| 오류             | 테두리·아이콘·문구 중 사용할 표시와 배치       |
| 포커스           | 테두리 변화와 포커스 링의 표현                 |
| 비활성·읽기 전용 | 두 상태를 어떻게 구분할지                      |
| 아이콘·부가 행동 | 앞뒤 아이콘, 지우기, 비밀번호 표시 등의 위치   |
| Textarea         | 최소 높이, 여러 줄 입력과 크기 변경 허용 여부  |

입력 오류는 색상만으로 전달하지 않고 문구와 연결한다. 오류 문구가 추가됐을 때 아래 요소가 어떻게 이동하는지도 확인한다.

### Checkbox와 선택 UI

- 기본·선택·비활성·오류 상태의 모양
- 체크 영역과 Label의 간격
- Label이 여러 줄일 때 체크박스의 정렬
- Label 전체를 누를 수 있는 영역
- 그룹 제목·설명·그룹 오류의 배치

Radio·Switch·Select·Tabs 등 추가 컴포넌트는 **실제 사용할 화면이 확인된 항목부터** 같은 기준으로 정리한다.

## 5. Card·Badge·Dialog·Sheet

### Card

- 기본 화면 배경과의 구분 방식
- 테두리·그림자·라운드
- 내부 여백과 제목·설명·본문·행동 영역 간격
- 카드 전체가 클릭되는 경우와 내부 버튼만 클릭되는 경우의 구분
- 이미지나 긴 콘텐츠가 있을 때의 처리

### Badge

- 단순 정보·업무 상태·오류 등 사용 목적
- 채움형·테두리형·약한 배경형의 구분
- 글자 크기·굵기·여백·라운드
- 아이콘 포함 여부
- 긴 상태명과 줄바꿈 처리

업무 상태의 의미가 확정되지 않았다면 색상만으로 상태 체계를 미리 만들지 않는다.

### Dialog·Sheet

- 기본 폭과 최대 폭, 모바일에서의 좌우 여백
- 라운드·테두리·그림자·Dim
- 제목·설명·본문·버튼 영역의 배치와 간격
- 닫기 버튼의 위치와 크기
- 내용이 길 때 스크롤되는 영역
- 모바일 키보드가 열렸을 때 유지할 정보와 버튼 위치
- 배경 클릭·Escape·뒤로가기의 닫기 허용 여부
- 닫힌 뒤 포커스가 돌아갈 위치

일반 안내·입력·위험 행동 확인처럼 목적이 다른 팝업은 필요한 경우 동작을 구분한다. shadcn 기반 컴포넌트의 포커스·키보드 동작을 디자인 변경 과정에서도 유지한다.

## 6. 공통 수치: Tailwind에 연결할 기준

| 분류      | 함께 정할 값                                                          |
| --------- | --------------------------------------------------------------------- |
| 폰트      | 기본 서체, 사용 굵기, 숫자·영문 표현, 사용할 수 없는 환경의 대체 서체 |
| 글자 체계 | 화면 제목·영역 제목·본문·보조 문구·Label·버튼의 크기·굵기·행간        |
| 간격      | 화면 좌우 여백, 큰 영역 간격, 항목 간격, 컴포넌트 내부 여백           |
| 크기      | 버튼·입력창 높이, 아이콘 크기, 팝업 폭, 콘텐츠 최대 폭                |
| 라운드    | 버튼·입력창·카드·팝업·Badge의 모서리 단계                             |
| 테두리    | 기본·강조·입력 오류·포커스의 두께와 표현                              |
| 그림자    | 카드·떠 있는 메뉴·Dialog 등에 필요한 그림자                           |
| 움직임    | 필요한 열기·닫기·로딩 효과와 움직임을 줄이는 환경에서의 표현          |

디자인 수치는 가능한 한 반복되는 단계로 정리한다. 화면마다 비슷한 값을 조금씩 다르게 두기보다, 공통 기준으로 묶을 수 있는지 확인한다.

다만 모든 숫자를 토큰으로 만들지는 않는다. 실제로 반복되거나 함께 변경할 값은 공통 기준으로 관리하고, 특정 화면에만 필요한 배치는 해당 화면에서 처리한다.

개발에서는 합의된 값을 Tailwind 기본 체계와 비교해 연결한다. 기본 체계로 표현하기 어려운 프로젝트 고유 값은 CSS 변수와 테마 항목으로 관리한다.

## 7. 모바일·PC와 상태 화면

### 모바일·PC

- 같은 컴포넌트에서 달라지는 크기·여백·배치
- 콘텐츠 최대 폭과 화면 좌우 여백
- 버튼의 가로 배치·세로 배치 전환
- Dialog를 유지할지 Sheet로 바꿀지
- 긴 문구·큰 글자·좁은 화면에서의 처리

화면 너비별 차이는 대표 화면에서 확인하고, 개발에서 임의의 반응형 동작을 추가하지 않는다.

### 로딩·빈 화면·에러·오프라인

현재 구현된 상태 표현을 기준으로 다음을 확정한다.

- 전체 화면·영역 내부·카드 내부 중 표시 범위
- Skeleton·Spinner·안내 문구 중 사용할 표현
- 제목·설명·아이콘의 크기와 간격
- 다시 시도·이전·홈 이동 등 필요한 행동과 배치
- 기존 내용이 있는 갱신 상태의 표현
- 오류·오프라인 안내가 입력 내용이나 기존 콘텐츠를 가리지 않게 할 방법

이번에는 디자인 기준을 합의한다. 실제 API 오류 분기·재시도·인증·Native 연동 구현은 이후 작업 범위에서 다룬다.

## 8. 토큰과 코드에 반영하는 방식

합의된 값은 다음 관계로 관리한다.

**원시 색상·수치 → 의미 있는 역할 → 컴포넌트 적용**

예를 들어 주요 행동 색상을 정하면 다음이 함께 연결된다.

| 구분          | 연결 예시                   |
| ------------- | --------------------------- |
| 원시 색상     | 선택한 브랜드 Blue 단계     |
| 의미 역할     | 주요 행동 배경              |
| shadcn 변수   | `primary`                   |
| CSS 변수      | `--primary`                 |
| Tailwind 사용 | `bg-primary`                |
| 실제 적용     | 기본 버튼, 합의된 강조 요소 |

디자이너는 “주요 행동 배경”처럼 역할로 검토하고, 개발은 구현 변수와 대응표를 관리한다.

색상·폰트·간격·라운드 같은 **값은 변환해 코드에 연결**한다. 버튼 종류·상태 전환·반응형 배치·닫기 동작 같은 **규칙은 컴포넌트 코드에 반영**한다.

Tokens Studio에 넣는다고 모든 컴포넌트가 자동 생성되는 것은 아니다. 공통 토큰과 컴포넌트가 같은 결정을 사용하도록 관리하는 것이 목적이다.

## 9. 검수와 합의 기록

처음에는 다음 표본을 Figma와 Storybook에서 나란히 확인한다.

1. 주요·보조·테두리·위험 버튼과 상태
2. 기본·포커스·오류·비활성 입력창
3. Checkbox와 여러 줄 Label
4. Card·Badge
5. Dialog·Sheet
6. 로딩·빈 화면·에러·오프라인

각 표본은 모바일·PC와 긴 문구에서도 확인한다.

합의 결과는 아래 형태로 남긴다.

| 대상           | 결정 내용                | 적용 범위                  | 상태           | 확인 담당   |
| -------------- | ------------------------ | -------------------------- | -------------- | ----------- |
| 주요 행동 색상 | 선택한 팔레트와 글자색   | 기본 버튼·합의된 강조 요소 | 확정 / 검토 중 | 디자인·개발 |
| 입력 오류      | 테두리·문구·아이콘 표현  | Input·Textarea·선택 UI     | 확정 / 검토 중 | 디자인·개발 |
| 공통 크기      | 높이·여백·라운드·글자    | 해당 컴포넌트              | 확정 / 검토 중 | 디자인·개발 |
| 예외           | 공통 기준과 다른 이유·값 | 지정 화면·상태             | 확정 / 검토 중 | 디자인·개발 |

첫 협의에서는 **주요 색상 역할 → 글자·간격·라운드 → 버튼·입력창 → 팝업·상태 화면** 순서로 결정한다.

개발에서 토큰·컴포넌트에 반영한 뒤 실제 결과를 디자인팀이 확인하고, 미정인 항목은 별도 목록으로 유지한다. 이 표본 검수가 끝나면 이후 화면이 공통으로 사용할 첫 디자인 기준으로 삼는다.
