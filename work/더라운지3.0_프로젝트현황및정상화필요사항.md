# 더라운지 3.0 프로젝트 현황 및 정상화 필요사항

## 1. 작성 목적

이 문서는 더라운지 3.0 프로젝트의 현재 상태를 관련 자료와 실무 진행 상황을 기준으로 정리하고, 개발 일정과 완료 기준을 현실적으로 수립하기 위해 필요한 선행조건과 조치사항을 공유하는 데 목적이 있다.

특정 개인이나 조직의 책임을 평가하기보다 다음 내용을 명확히 하는 데 초점을 둔다.

- 현재 확인할 수 있는 기준과 산출물
- 아직 협의 또는 확정이 필요한 사항
- 파트 간 의존관계가 일정에 미치는 영향
- 현재 진행 방식에서 예상되는 주요 위험
- 프로젝트를 정상적으로 진행하기 위해 필요한 조치

이 문서는 최종 IA, 화면별 기획서, 디자인 원본, Backend API 명세 또는 Native 연동 명세를 대신하지 않는다. 각 파트의 최종 산출물과 협의 결과가 변경되면 이 문서의 판단도 함께 갱신해야 한다.

## 2. 핵심 요약

현재 프로젝트에는 Front-end 구현 기준, 기술 구조, 일정 산정 전제와 품질 기준을 정리한 문서가 존재한다. 그러나 실제 기능 개발을 안정적으로 진행하려면 화면별 업무 규칙, 상태 정의, 디자인, Backend API, Native 연동과 운영 정책이 기능 단위로 연결되어야 한다.

현재 확인된 주요 문제는 다음과 같다.

- 기획, 디자인, Backend, Native 등 여러 파트의 협의가 필요한 항목이 다수 남아 있다.
- 현재 확인한 IA, WBS, 기획, 디자인과 인터페이스 자료에는 최종 승인된 개발 기준임을 확인할 근거가 부족하다. 개별 자료의 숫자, 일정과 목록은 담당 파트의 검증과 확정 전까지 참고 정보로 구분해야 한다.
- 현재 IA와 WBS는 범위 집계 기준, 누락 여부와 파트 간 선후행 관계를 확인하기 어려워 공식 범위와 일정의 기준선으로 사용하기 어렵다.
- 기능별 착수 조건과 완료 기준이 공통 기준으로 관리되지 않으면 각 파트가 서로 다른 전제로 작업할 가능성이 있다.
- 미확정 사항을 개발 단계에서 개별적으로 판단하면 재작업과 일정 지연이 커질 수 있다.
- 개발 인력 보강만으로는 기획, 디자인, API와 Native 연동의 확인 대기를 해소하기 어렵다.

따라서 현재 일정의 날짜를 수정하는 방식이 아니라, 검증된 범위, 선행조건, 담당 파트, 결정 시점과 완료 기준을 함께 반영한 WBS 재수립이 필요하다.

## 3. 현재 활용 가능한 참고 자료와 한계

현재 `lounge-docs`에는 다음 범주의 자료가 마련되어 있다.

### 3.1 Front-end 구현 및 품질 기준

- Front-end 개발 가이드와 저장소 구조 기준
- 디자인 토큰과 Figma 연계 기준
- Storybook을 이용한 UI 상태 검수 기준
- TypeScript, 상태 관리, 네트워크와 세션 처리 기준
- 테스트, 접근성, 보안, 성능과 브라우저 지원 기준
- WebView 환경과 Native 기능 연동 시 확인할 책임 경계

이 자료는 개발자가 공통 기준에 따라 구현하고 검토할 수 있도록 돕는다. 다만 실제 업무 규칙이나 승인된 API 명세가 없는 상태에서 기능 요구사항을 대신 확정하는 자료는 아니다.

### 3.2 일정 산정 자료

Front-end 일정 산정 자료에서는 당시 제공된 IA에 분류된 값을 바탕으로 반응형 웹, 앱 WebView와 Native의 역할 구분 방식을 검토하고, 특정 인력 구성에서의 예상 기간과 일정이 성립하기 위한 전제조건을 정리했다.

다만 해당 자료에 사용된 화면 수는 최종 확정 범위가 아니다. 당시 IA의 화면 ID와 상태를 기준으로 집계한 값이며, Page 외에 Layer, Tab, Link와 Content 상태가 포함되어 있어 실제 신규 화면 수와 동일하게 해석할 수 없다. 현재 프로젝트의 전체 기능과 화면 범위도 당시 자료보다 확대됐거나 추가 확인이 필요한 상태이므로, 기존 수치를 공식 범위나 확정된 개발 물량으로 사용해서는 안 된다.

일정 산정 자료는 다음 내용을 확인하기 위한 참고 자료로 활용한다.

- Web, WebView와 Native의 역할 분류 방식과 통합 지점을 검토한다. 각 분류에 포함되는 실제 기능, 화면과 수량은 최신 자료를 기준으로 다시 확인한다.
- 화면 수만으로 공수를 계산하지 않고 업무 규칙, 상태 조합, API, Native 연동과 검증 난이도를 함께 고려한다.
- 특정 인력 구성과 기간은 당시 범위와 선행조건을 가정한 산정 시나리오이며, 현재 확정 일정이나 투입 계획을 의미하지 않는다.
- 기획, 디자인, Backend API와 Native 연동 사항이 기능 개발 순서에 맞춰 협의되고 제공돼야 해당 일정 가정이 성립한다.

따라서 IA와 기획 범위의 누락 및 분류 기준을 먼저 정비하고 검증한 뒤 Page, Layer, Tab, Link, Content와 주요 상태의 집계 기준을 통일해야 한다. 이후 검증된 범위, 실제 투입 인력과 파트별 제공 일정을 반영해 기간을 다시 산정해야 한다.

### 3.3 WebView 및 외부 결제 기준

WebView 관련 자료에서는 Web, Flutter, Android·iOS Native와 Backend의 역할을 구분하고 있다.

- Web은 서비스 화면과 사용자 업무 흐름을 담당한다.
- Flutter는 WebView 컨테이너, 화면 이동과 Web-Native 연동을 조정한다.
- Android·iOS Native는 운영체제 권한, 외부 앱 실행과 앱 복귀 같은 플랫폼 기능을 담당한다.
- Backend는 인증, 권한, 결제 결과와 업무 데이터의 최종 판단을 담당한다.

외부 결제의 경우 앱이 다시 활성화됐다는 사실만으로 결제 성공을 판단할 수 없다. 성공, 실패, 취소와 미확정 상태를 판단하는 방식은 Web, Backend, 결제 담당과 Native 파트의 협의가 필요하다.

### 3.4 현재 자료의 활용 가치와 한계

현재 문서군은 다음 용도로 활용할 수 있다.

- 파트별 역할과 기술적 책임 경계 검토
- 실제 구현 범위를 확인하기 위한 협의사항 식별
- 개발 일정 산정의 전제조건 확인
- 미확정 사항과 필요한 협의 대상 식별
- 개발 및 검수 시 공통 품질 기준 적용
- 신규 투입 인력의 프로젝트 구조 이해
- 기능별 완료 기준과 위험 검토

다만 다음 사항은 별도 산출물이나 담당 파트의 확정이 필요하다.

- 최종 IA와 화면 목록
- 화면별 업무 규칙과 사용자 흐름
- 정상, 로딩, 데이터 없음, 실패와 권한 상태 정의
- 최종 디자인과 문구
- Backend API 요청·응답, 인증과 오류 규칙
- WebView Bridge 요청·응답과 버전 처리 방식
- 결제, 세션, 운영 콘텐츠와 배포 정책

## 4. 현재 주요 확인 필요사항

### 4.1 기획 및 IA

개발 가능한 기준의 기획 완료 여부는 문서 작성 여부만으로 판단하기 어렵다. 기능별로 다음 항목이 확인되어야 한다.

- 화면의 목적과 진입 조건
- 사용자 행동에 따른 화면 이동
- 업무 규칙과 예외 조건
- 표시할 데이터와 데이터 출처
- 정상 이외의 상태와 사용자 안내
- 권한에 따른 노출 및 사용 가능 범위
- 완료, 취소, 재시도와 중복 요청 처리

기획 완료 목표일이 공유되어 있더라도, 위 항목의 범위와 담당 파트별 검토 일정이 함께 확인되지 않으면 실제 개발 착수일과 완료일을 산정하기 어렵다.

### 4.2 디자인

디자인 승인은 화면의 시각적 구성을 확정하는 단계와 기능 개발이 가능한 상태를 구분해야 한다.

예를 들어 메인 시안에는 카드, 여정, 라운지 추천과 eSIM 정보가 함께 표시되지만 다음 내용은 별도 확인이 필요하다.

- 값의 출처와 갱신 시점
- 등록 전후 및 여러 데이터가 존재할 때의 상태
- 로딩, 데이터 없음과 실패 상태
- 버튼과 카드 선택 시 이동 위치
- 운영 문구와 프로모션 정보의 관리 방식
- 서버 또는 화면에서 계산할 항목

시각 디자인이 승인됐더라도 데이터와 상태가 확정되지 않았다면 개발 범위까지 승인된 것으로 해석하지 않는 것이 필요하다.

### 4.3 Backend API

현재 확인한 인터페이스 자료는 `v0.8.1 내부 확인용` 문서다. API 영역, Endpoint 목록, 일부 응답 형식과 오류 코드를 파악하는 참고 자료로는 사용할 수 있지만, 담당 파트의 최종 확인과 승인을 받은 구현 기준은 아니다.

Front-end 요약 자료 기준으로 IN-APP API 66건은 Endpoint 목록만 있고 상세 요청·응답 명세가 기재되지 않았다. 인증 또는 서명 생성 주체, Token 수명과 갱신, 일부 오류 처리와 환경별 적용 기준도 확정되지 않았다. 따라서 현재 인터페이스 자료를 기능 구현, 연동 완료 판단 또는 일정 산정의 기준 명세로 사용할 수 없다.

기능 개발 전에 최소한 다음 내용을 관련 파트가 협의해야 한다.

- 호출 대상과 환경별 주소
- 요청 Method와 Parameter
- 응답 Field와 필수 여부
- 인증 또는 서명 처리 주체
- 오류 코드와 화면 처리 기준
- Token 발급, 만료와 갱신 방식
- 중복 요청과 재시도 처리
- 개발 및 QA 환경에서 사용할 데이터

Endpoint 목록을 파악한 상태와 담당 파트의 확인을 거쳐 실제 연동 개발이 가능한 상태는 구분해야 한다.

### 4.4 Native 및 WebView 연동

WebView 기능은 Web과 Flutter가 각각 구현한 뒤 마지막에 연결하는 방식만으로 완료하기 어렵다. 다음 항목을 기능 착수 전에 협의해야 한다.

- WebView 시작 주소와 허용 Origin
- 로그인 및 세션 전달 방식
- Bridge 호출 이름, 요청·응답과 오류 형식
- 외부 앱 실행과 서비스 앱 복귀 방식
- 앱이 종료된 상태에서의 복구 경로
- 구버전 앱과 새 Web 기능의 호환 정책
- 실제 기기 검증 범위

Native 연동이 필요한 기능은 Web 단독 구현만으로 완료 처리할 수 없다.

### 4.5 QA 및 운영

완료된 기능을 실제 운영 가능한 상태로 판단하려면 개발자 확인 외에 QA와 운영 검증이 필요하다.

- QA 및 UAT 담당과 검증 시점
- Android·iOS 실제 기기 및 지원 버전
- 개발, QA와 운영 환경의 차이
- 운영 콘텐츠와 프로모션 변경 주체
- 장애 발생 시 확인할 파트와 로그 범위
- 배포 순서와 이전 버전 호환 여부

이 항목이 일정 후반에 결정되면 개발 완료 후에도 검증 대기가 발생할 수 있다.

## 5. 파트 간 주요 의존관계

| 작업 영역 | 필요한 선행조건 | 주요 협의 파트 | 미확정 시 영향 |
| --- | --- | --- | --- |
| 화면 구현 | IA, 화면 상태, 디자인과 문구 | 기획·디자인·Front-end | 구현 대기 또는 화면 재작업 |
| API 연동 | 요청·응답, 인증과 오류 규칙 | Front-end·Backend·기획 | Type, 상태 처리와 테스트 재작업 |
| WebView 연동 | 시작 주소, 세션과 Bridge 규격 | Front-end·Flutter·Backend | 로그인, 이동과 기기 기능 검증 지연 |
| 외부 결제 | 결제 흐름, 복귀와 결과 확인 방식 | 기획·운영·결제·Front-end·Backend·Native | 중복 결제, 결과 불일치와 통합 지연 |
| 디자인 시스템 | 최종 토큰, 컴포넌트와 반응형 기준 | 디자인·Front-end·퍼블리싱 | 공통 UI 수정과 화면 회귀 발생 |
| 통합 QA | 검증 환경, 데이터, 기기와 완료 기준 | QA·운영·전체 개발 파트 | 완료 판단 및 배포 지연 |

각 행의 선행조건이 모두 완성될 때까지 전체 개발을 중단한다는 의미는 아니다. 기능별로 필요한 항목이 협의된 순서에 따라 개발을 진행하고, 협의되지 않은 기능은 일정상 대기 또는 미확정 상태로 구분하는 방식이 필요하다.

## 6. IA 및 WBS 재수립 필요사항

현재 공유된 IA와 WBS는 화면과 상태의 분류 기준이 일관되지 않고, 누락 범위와 파트 간 선후행 관계를 추적하기 어려운 상태다. 따라서 현재 기재된 화면 수, 작업 기간과 완료일을 확정 범위 또는 공식 일정으로 해석하기 어렵다.

WBS는 파트별 작업 목록과 날짜를 취합하는 것만으로는 실제 선후행 관계를 표현하기 어렵다. 최소한 다음 항목이 기능 또는 작업 묶음 단위로 포함되어야 한다.

- 작업 범위와 완료 결과물
- 선행 작업과 입력 자료
- 담당 파트와 확인 또는 결정 담당
- 착수 가능 조건
- 예상 작업 기간
- 파트 간 검토 및 수정 기간
- 통합 테스트와 QA 기간
- 미확정 사항과 결정 목표일
- 일정 변경 시 영향을 받는 후속 작업

현재 일정은 다음 순서로 다시 수립하는 것이 필요하다.

1. IA의 화면·상태 분류 기준과 누락 범위를 정비하고 검증한다.
2. 검증된 최종 범위와 화면 목록을 기준선으로 고정한다.
3. 기능별 미확정 사항과 관련 파트를 연결한다.
4. 기획, 디자인, Backend와 Native의 제공 일정을 확인한다.
5. 제공 순서에 따라 개발 가능한 기능 묶음을 구성한다.
6. 실제 투입 인력과 검토 가능 시간을 반영한다.
7. 통합, QA, UAT와 안정화 기간을 포함한다.
8. 위험이 현실화되면 완료일 또는 범위를 함께 조정한다.

개발 인원이 늘어나더라도 공통 구조, 주요 업무 규칙과 파트 간 협의는 선행되어야 한다. 인력 보강은 병렬 구현에는 도움이 되지만 확인 대기나 의사결정 지연을 직접 줄이지는 못한다.

## 7. 주요 프로젝트 위험

| 위험 | 예상 영향 | 확인 또는 대응 방향 |
| --- | --- | --- |
| 검증되지 않은 IA·WBS를 공식 기준으로 사용 | 범위 누락, 잘못된 완료일과 반복적인 일정 수정 | 분류 기준과 누락 범위를 검증한 뒤 새 기준선 지정 |

| 완료 기준 부재 | 파트별 완료 판단 차이와 QA 후 재작업 | 기능별 개발·연동·검증 완료 기준 정의 |

| 미확정 항목의 개발자 판단 | 파트마다 다른 규칙을 구현 | 결정 주체와 목표일을 지정하고 결과 기록 |
| QA 환경 및 실제 기기 제공 지연 | 개발 완료 후 검증 대기 | 환경과 기기 제공 일정을 WBS에 포함 |

## 8. 정상화를 위해 필요한 조치

### 8.1 즉시 필요한 조치

1. 현재 IA의 화면·상태 분류 기준과 누락 범위를 정비하고 검증한 뒤 기준 버전을 지정한다.
2. 기능별 기획·디자인 완료 여부와 미확정 사항을 함께 표시한다.
3. 미확정 사항마다 필요한 협의 파트, 확인 담당과 목표일을 지정한다.
4. Front-end, Backend와 Native의 연동 우선순위를 정한다.
5. 검증된 범위와 파트 간 의존관계 및 통합 검증 기준을 바탕으로 WBS를 재수립한다.
6. 현재 인력과 실제 역할 분담을 반영해 일정을 다시 산정한다.
7. QA, UAT, 실제 기기와 환경 제공 일정을 포함한다.

### 8.2 기능별 착수 기준

모든 기능에 동일한 수준의 문서가 필요한 것은 아니지만, 최소한 다음 항목은 확인되어야 한다.

- 구현할 화면과 사용자 흐름
- 주요 정상 및 예외 상태
- 최종 또는 개발 가능한 수준의 디자인
- 필요한 데이터와 제공 주체
- API 또는 Native 연동 여부
- 관련 파트의 협의 결과
- 기능 완료를 판단할 검증 기준

일부 항목이 미확정이어도 독립적으로 진행 가능한 작업은 분리해 착수할 수 있다. 이 경우 확정 범위와 미확정 범위를 작업 항목에 명시해야 한다.

### 8.3 결정 및 변경 기록

구두 협의만으로 기준이 변경되지 않도록 다음 항목을 간단한 결정 기록으로 남기는 것이 필요하다.

| 항목 | 기록 내용 |
| --- | --- |
| 대상 | 기능, 화면 또는 공통 정책 |
| 결정 내용 | 확정된 업무 규칙과 적용 범위 |
| 참여 파트 | 협의에 참여한 담당 파트 |
| 결정일 | 적용 기준이 확정된 날짜 |
| 적용 시점 | 개발 및 배포에 반영할 시점 |
| 미확정 항목 | 추가 확인이 필요한 내용과 담당 |
| 영향 범위 | 기획, 디자인, 개발, 테스트와 일정 영향 |

## 9. 역할과 책임 범위

현재 Front-end 문서군은 구현 기준, 기술적 책임 경계, 일정 산정 전제, 품질 기준과 파트 간 주요 협의사항을 정리한 자료다. 이 자료가 존재한다는 사실만으로 각 파트의 최종 결정과 산출물이 완료된 것은 아니다.

- 기획은 화면 목적, 사용자 흐름과 업무 규칙을 확정한다.
- 디자인은 필요한 상태를 포함한 화면과 상호작용을 정의한다.
- Front-end는 확정된 기준에 따라 Web 및 WebView 화면과 상태를 구현하고 검증한다.
- Backend는 데이터, 인증, 권한, 오류와 주요 업무 결과의 판단 기준을 제공한다.
- Native는 앱 수명주기, 운영체제 기능, WebView 컨테이너와 플랫폼 연동을 담당한다.
- QA와 운영은 실제 사용 조건과 완료 기준에 따라 결과를 검증한다.
- PM은 범위, 담당, 선후행 관계, 결정 일정과 전체 완료 기준을 통합 관리한다.

각 파트의 세부 책임은 조직의 공식 역할 정의와 협의 결과를 우선한다.

## 10. 제안하는 완료 기준

프로젝트 또는 주요 기능 묶음을 완료로 판단하려면 다음 항목이 확인되어야 한다.

- 합의된 IA와 화면 상태가 구현되어 있다.
- 승인된 데이터 및 API 기준으로 정상과 주요 오류 흐름이 동작한다.
- WebView와 Native 연동 기능이 실제 앱 환경에서 검증됐다.
- 결제, 인증과 권한처럼 영향이 큰 흐름의 성공·실패·취소·재시도가 확인됐다.
- 주요 반응형 해상도와 지원 브라우저에서 화면이 정상적으로 동작한다.
- 로딩, 데이터 없음, 오류와 접근 제한 상태가 확인됐다.
- 주요 기능의 테스트와 회귀 확인이 완료됐다.
- QA 및 UAT에서 확인된 주요 결함이 해결됐다.
- 배포 및 운영에 필요한 환경과 책임자가 확인됐다.

## 11. 결론

현재 프로젝트에는 Front-end 구현과 품질을 위한 상당한 기준 자료가 마련되어 있다. 이 자료는 개발 방향을 통일하고 파트 간 확인사항을 식별하는 데 활용할 수 있다.

다만 프로젝트 일정의 신뢰성을 확보하려면 문서의 존재만으로 준비 완료를 판단하지 않아야 한다. IA와 기획 범위를 먼저 정비·검증하고, 기능별 기획·디자인·Backend·Native 협의 결과와 실제 투입 인력을 새 기준 WBS에 연결해야 한다. 특히 미확정 사항의 담당과 결정 시점, 통합 검증 기간 및 완료 기준이 함께 관리되어야 한다.

현재 필요한 것은 개별 파트가 독립적으로 날짜를 수정하는 작업보다, 전체 범위와 의존관계를 기준으로 실행 가능한 순서를 다시 구성하는 것이다. 이를 통해 개발 가능한 기능은 순차적으로 진행하고, 협의가 필요한 기능은 대기 사유와 일정 영향을 투명하게 관리할 수 있다.
