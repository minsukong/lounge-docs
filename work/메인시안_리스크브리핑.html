1. 결론

시안은 "화면이 어떤 모습인가"만 답합니다. "값은 어디서 오고, 실패하면 어떻게 보이고, 어떤 상태가 더 있는가"에는 답이 없습니다.

화면 디자인만 통과하면 미결정 항목(4·5절)이 전부 개발 판단으로 넘어갑니다. 통과 결정 시 미결정 목록을 결정문에 함께 기록해야 합니다.

확인 항목 내용
대상 Figma 메인 화면 흐름도(다이나믹 존 및 상품영역) 섹션
근거 이 문서의 모든 근거는 시안에 실제로 적혀 있는 내용입니다

2. 시안에 있는 것

  • 로그인 후 화면 2장: #로그인후-미등록, #로그인후-제휴카드만 등록
  • eSIM 카드 변형 2종: 이용권 보유, 사용량 소진 임박
  • 나머지는 빈 박스 또는 한 줄 텍스트 자리입니다

2.1 다이나믹 존 (화면 맨 위 카드 2장)

카드 미등록 제휴카드만 등록
My card "10명 중 9명, 이미 무료 이용권을 받았어요" + 등록 버튼 카드 목록(옆으로 넘김). 예시: "공항 라운지: 통합 연 4회 제공 (본인 + 동반 1인)", "+ 혜택 5건", "무료 혜택" 표시 바
내여정 "여정 한번만 등록해두면, 다음부터는 공항에 맞는 라운지·이용권·혼잡도까지 자동으로 떠요" + 등록 버튼 미등록 카드와 동일. 등록 완료 상태가 없습니다.

2.2 상품 영역

  • 미등록: 빈 박스 → 한 줄짜리 박스 → 빈 박스. 내용이 없습니다.
  • 등록: "라운지 추천"(라운지명, 위치, 평점, 버튼) / "더라운지에서 소개하는 이용권"(eSIM 이용권, "런칭 기념 특별할인 최대 28%까지", 카테고리 3장)

2.3 eSIM 사용량 카드

"0.5GB 남음/5GB", "D-120만료", "15분 전 확인 기준"과 갱신 버튼이 있습니다.

2.4 주석으로만 있는 판정 규칙

"1GB 이하인 경우 소진임박 판정, '소진임박' 배지 자체도 캐시 스냅샷 기준 판정, 이미 충전을 마친 유저라면 '갱신'을 누르는 순간 배지가 바로 사라짐"

데이터 계약으로 정리된 곳은 없고, 이 메모 한 줄이 전부입니다.

3. 상태 목록: 있는 것과 없는 것

구분 시안에 있음 시안에 없음
제휴카드 미등록, 다수 등록 1장만 등록, 카드 해지, 혜택 소진
여정 미등록 등록 완료, 여정 여러 개, 지난 날짜 여정
eSIM 미보유, 정상, 소진 임박 0GB, 만료, 충전 중, 여러 개
서버 데이터 정상만 불러오는 중, 실패, 데이터 없음 — 전부 없음

조합하면 화면 12가지가 가능한데 시안은 2개입니다. 나머지는 TBD이고 개발이 정하게 됩니다. 카드 여러 장이 함께 뜨면 위쪽 자리에 무엇을 넣을지도 정해져 있지 않습니다.

4. 문제 항목

# 시안의 값 문제
1 "10명 중 9명" 계산 값인지 승인 문구인지 출처 미정. 계산 값이면 통계 필요, 문구면 기간 필요
2 "자동으로 떠요" 문구 ① 여정 등록 완료 상태 없음 ② "인천공항 • Terminal 2"가 여정에 따라 바뀌는 값인지 예시 고정 값인지 불분명 ③ "혼잡도"는 문구에만 있고 표시할 자리 없음
3 카드 혜택 문장("연 4회 제공") 카드사·연도마다 다름. 서버에서 주는 값인지 미정. 미정이면 카드 1종 기준으로 고치게 됨
4 "+ 혜택 5건", "무료 혜택" 표시 바 눌러서 이동하는 화면 없음. 표시 바가 남은 이용 횟수인지 설명 없음
5 "최대 28%까지" 할인 기간·조건·종료 후 문구 미정
6 eSIM 값 4종(사용량, 만료, 확인 시점, 임박 표시) 전부 서버 값. "갱신" 동작과 "1GB 기준" 계산 위치 (서버/화면) TBD. 협의가 끝날 때까지 이 카드 개발이 불가능합니다
7 빈 박스 3개 의도적 빈칸인지 미제작인지 구분 불가

5. 서버 협의 대상 — 전부 미협의

아래 8개 항목이 TBD인 동안 화면에 값을 채울 방법이 없습니다.

# 화면 항목 필요로 하는 것
1 "10명 중 9명" 통계 값 또는 문구 사용 승인
2 카드 혜택 문장, "+ 혜택 5건" 카드별 혜택 정보
3 "무료 혜택" 표시 바 남은 이용 횟수
4 라운지 추천 라운지 목록, 평점, 혼잡도(데이터 존재 여부부터 확인)
5 eSIM 할인 배너 할인 기간·조건
6 eSIM 사용량 4개 값 값 목록, "1GB 기준" 계산 위치, "갱신" 버튼에 드는 값
7 여정 기반 추천 등록 여정 → 추천 결과 변환 방식
8 카테고리 3종, 빈 박스 3개 해당 자리 콘텐츠의 관리 방식

6. 리스크

번호 리스크 결과 조치
R1 (가장 큼) 통과 = 개발 승인까지로 읽힘 미결정 8개 항목이 개발 판단으로 전가. 화면은 만들어지지만 값을 채울 수 없고, "이미 승인받았다"는 이유로 수정이 어려워짐 통과 결정문에 "화면 디자인만 통과. 4·5절 항목은 TBD" 기록
R2 eSIM 카드, 협의 없으면 착수 불가 핵심 다이나믹 존이 정지. 나중에 서버 값이 정되면 재개발 통과 직후 서버 담당과 1회 협의: 값 목록, 계산 위치, 갱신 동작 (Figma를 연 채로)
R3 문구와 동작 불일치 "자동으로 떠요"를 인천 고정 값으로 개발하면, 다른 여정을 등록해도 인천이 나와 문구가 거짓이 됨 여정 완료 상태 화면 추가, 추천 적용 기준 정의, "혼잡도" 표시 자리 확정 또는 문구에서 삭제
R4 실패·불러오는 중·빈 화면 0개 값 8종을 한 화면에 모은 화면이 실패 시 어떻게 보일지 미정. 개발자가 영역마다 다르게 만듦 영역별 실패·빈 화면을 다이나믹 존 카드 기준으로 시안에 추가, 또는 공통 표기 규칙으로 결정
R5 미정 값을 고정 문구로 코딩 값이 바뀔 때마다 앱 수정·배포. 서버 또는 운영 화면에서 값을 주어야 함 "10명 중 9명", "28%"의 출처를 디자인·기획에 확인 요청
R6 표시 요소 ↔ 기존 컴포넌트 대응 미확인 대응 불가 항목이 통과 후에야 드러나면 토큰 수정 → Figma (Tokens Studio) 수정 사이클 발생. 카드 목록·남은 양 바는 Safari 15 하한 확인 필요 기존 컴포넌트·토큰과 대조한 목록(대응 가능/불가능/수정 필요)을 디자인에 선제 공유
R7 버튼·카드의 이동 화면 미정 이동할 화면을 모르면 개발 순서를 정할 수 없음 "누르면 어디로 가는가" 목록 1장 요청 (범위 밖 화면이라도 목록만)

7. 담당별 할 일

7.1 디자인 (질문)

  1. 빈 박스 3개: 의도적 빈칸인가, 미제작인가?
  2. 여정 등록 완료 상태 화면을 만들 것인가?
  3. 카드 여러 장의 위쪽 자리 배분 우선순위는?
  4. "10명 중 9명"의 출처는?
  5. 실패·빈 화면 표현을 이번 시안에 넣는가?
  6. "혼잡도"를 어디에 표시하는가, 아니면 문구에서 빼는가?

7.2 서버 (협의 대상)

  1. eSIM: 값 목록, 1GB 기준 계산 위치(서버/화면), 갱신 버튼 값
  2. 카드별 혜택 정보(문장, 제공 횟수) 형식
  3. 라운지 평점·혼잡도의 출처와 갱신 주기 — 혼잡도를 실제로 줄 수 있는가
  4. "10명 중 9명": 계산 값인가, 승인 문구인가
  5. eSIM 할인의 기간·조건 값
  6. 여정 데이터 → 추천 결과 변환 방식

7.3 프론트엔드 (자체 준비)

  1. 시안 표시 요소와 기존 컴포넌트·토큰 대조 결과
  2. 3절에서 빠져 있는 10개 상태의 화면 결정 규칙
  3. Safari 15에서 카드 목록 넘김·남은 양 바 동작 확인
  4. 영역별 실패·불러오는 중 표기 방식 합의
  5. 상태 조합 기준의 Storybook 스토리 설계

8. 통과 단계

단계 완료 기준
1. 디자인 통과 (현재) 화면 디자인 승인 + 4·5절 미결정 목록을 결정문에 기록
2. 데이터 계약 5절 8개 항목 전부 "어떤 값을 어느 쪽에서 주는지" 확정
3. 상태 목록 확정 3절의 없는 상태(여정 완료, 실패, 빈 화면 등) 표현 확정
4. 개발 시작 2·3단계 완료 후 eSIM 카드·라운지 추천 영역 개발 시작
