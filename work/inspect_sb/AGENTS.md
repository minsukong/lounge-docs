# 기획 검토 AI 작업 지침

이 폴더에서 기획 검토 문서를 작성·검수·갱신하기 전에 이 파일을 읽는다. README는 양식 참고이며, 기존 문서의 판단을 그대로 복사하지 않는다.

## 이 작업을 하는 이유

현재 더라운지 3.0 Figma 기획은 작성·수정 중이다. 화면·설명·IA가 서로 다르거나 비어 있을 수 있다. **조사 시점의 기획 상태와 근거를 보존하고, 미정의 내용·확인 필요 사항·예상 작업 영향을 객관적으로 기록하는 작업이다.** 기획 보완과 작업자 보호에 도움이 되도록 기록하며, A/B를 업무 지침의 결정·계약·작업 카드로 연결하는 절차는 두지 않는다.

- 화면·설명이 비어 있거나 임시 배치뿐이라 검토할 내용이 거의 없으면 **작성 중·검토 보류**로 넘겨도 된다. 대상 위치·확인 날짜·보류 이유만 짧게 남기고, 빈칸마다 질문을 만들지 않는다. 내용이 있는 화면·설명은 부분적으로 검토한다.
- 미완성이라는 이유만으로 모든 빈칸을 결함으로 만들지 않는다. 작업 결과·범위·연결에 영향을 주는 부분을 우선한다.
- 기록은 작업자의 판단 근거와 변경 이력도 보존한다. 책임 소재·기획자 평가·지연·재작업 발생을 AI가 단정하지 않는다.
- 검토할 내용이 있는 부분의 판단 기준은 “이 내용만 받은 작업자가 같은 조건에서 같은 결과를 만들 수 있는가?”다. 답이 불명확하면 정책을 대신 정하지 말고 질문으로 남긴다. 심하게 미완성인 부분은 이 기준으로 억지 평가하지 않는다.

## 주요 전제: Backend 협의가 충분히 이루어지지 않은 상태

2026-10-07 사용자 확인 기준, 현재 Backend 협의가 충분히 이루어지지 않은 상태다. API·인증·데이터·오류·세션·처리 주체의 FE/앱 합의 여부를 항목별로 확인한다. 모든 항목이 미합의이거나 협의가 전혀 없었다고 단정하지 않는다.

- 사용자에게 보이는 정책·흐름은 **기획 확인**, 요청·응답·인증·오류·세션 계약은 **Backend 협의 필요**로 구분한다. 함께 결정할 항목은 두 구분을 병기한다.
- Figma에 API 설명이 없다는 이유만으로 기획 누락을 만들지 않는다. Backend 협의 부족은 API·문서·구현이 존재하지 않는다는 뜻도 아니다. 실제 자료의 존재와 협의 상태를 별도로 확인한다.
- B에는 답에 따라 달라질 웹·앱 연동과 검증 범위만 적는다. endpoint·응답 필드·오류 코드·토큰 처리·담당·공수는 임의로 확정하지 않는다. 협의가 안 됐다는 이유만으로 모든 화면의 준비 작업을 중단으로 기록하지 않는다.
- 이후 A/B 작성·검수에서도 이 전제를 적용한다. 데이터·인증·상태·오류·연동 항목은 기획 확인과 Backend 협의 필요를 구분하고, 실제 합의가 확인된 부분만 합의 근거로 연결한다.
- 이후 협의하면 실제 답변·합의 날짜·근거를 같은 RC에 남기고 상태를 갱신한다. 요청하지 않은 Backend 연락이나 확인 요청은 보내지 않는다.

## Figma 조회 방식과 토큰

2026-10-07 사용자 확인 기준, 현재 Figma MCP를 사용할 수 없어 **Figma REST API로 원본을 읽는다.** 사용자는 원본 조회 작업을 요청할 때만 토큰을 전달한다.

- 토큰은 해당 작업의 인증에만 사용한다. 문서·저장소·설정·스크립트 파일에 저장하거나 응답·명령 출력·로그에 노출하지 않는다. 인증 헤더를 포함한 요청 전체를 기록하지 않는다.
- 토큰이 전달되지 않았으면 과거 대화·파일·환경에서 찾아 재사용하지 않는다. 새 원본 조회에 필요한 경우에만 사용자에게 요청하고, 기존 자료의 문서 검수는 가능한 범위에서 진행한다.
- REST API도 읽기 전용으로 사용한다. 먼저 섹션 이름·계층으로 OLD를 제외하고, 사용자 지정 범위의 화면·설명만 조회한다. 원본 수정·코멘트 등록은 별도 사용자 승인 전 하지 않는다.
- 근거에는 조회 방식·일시·파일 및 노드 ID·확인 범위를 남긴다. 원문·발췌를 보존할 때도 토큰·인증 헤더를 제외한다. 실제 조회하지 않았으면 원본 확인 완료로 표시하지 않는다.

## OLD 섹션 제외

- 섹션 이름이나 섹션 제목에 `OLD`로 표시된 영역은 대소문자와 관계없이 검토에서 제외한다. 상위 섹션이 OLD이면 하위 화면·설명·목업도 모두 제외한다.
- 먼저 섹션 이름·계층만 확인해 OLD를 걸러낸 뒤, 나머지 영역의 내용을 읽는다. OLD 하위 텍스트 추출·상세 조회·스크린샷 분석은 하지 않는다. 이미 받은 원본 데이터에 포함되어 있어도 분석에 사용하지 않는다.
- OLD 내용으로 질문·누락·상충 후보나 개발 영향을 만들지 않는다. 제외 기록이 필요하면 섹션 이름·ID와 “OLD 제외”만 남긴다.
- 기존 후보의 근거가 OLD에만 있다면 현재 기획의 문제로 재사용하지 않는다. 과거 이력은 보존하고 현재 영역의 근거를 확인한다. 사용자가 OLD를 지정해 별도로 검토하도록 요청한 경우에만 해당 범위를 읽는다.

## 진행 순서

1. **읽기:** 사용자 지정 페이지의 화면·설명을 함께 읽는다. 검토 가능한 부분과 작성 중·검토 보류 부분을 나누고, 필요한 IA·연관 화면만 확인한다.
2. **정리:** A에 관찰과 확인 질문, B에 같은 질문의 웹·앱 작업 영향을 작성한다.
3. **갱신:** 사용자 검토나 Figma 업데이트 후 기존 ID를 유지하며 바뀐 부분과 날짜·근거를 추가한다.

한 번에 전체 페이지를 조사하지 않는다. 대상은 01~12와 04-01·04-02이며, BO 전체 검토는 범위 밖이다. BO 관리 항목이 사용자 화면에 영향을 주면 그 연결 계약만 질문할 수 있다.

## 근거와 질문을 구분하기

- **관찰:** 실제로 읽은 문구·화면·노드 ID와 확인 날짜를 남긴다. 가능하면 해당 노드 링크와 추출 원문·발췌를 함께 보존한다. 요약을 직접 인용처럼 쓰지 않는다.
- **질문:** 관찰로부터 어떤 조건·흐름·담당 간 합의가 더 필요한지 적는다. 다른 자료에서 이미 정의했을 가능성을 확인한다.
- **영향:** 답에 따라 어느 화면·로직·연동·검증이 달라지는지 적는다. 예상 영향과 실제 발생을 구분한다.
- 다른 AI가 “원본 대조 완료”라고 썼다고 원본 확인으로 인정하지 않는다. 추출 원문이나 직접 조회로 검증한 범위를 명시하고, 못 확인했으면 “초안 보고 기준·독립 재검증 전”으로 남긴다.
- 텍스트 추출만으로 배치·시각 상태까지 검증했다고 쓰지 않는다. 화면 설명이 없거나 컴포넌트 이름이 MO라고 해서 PC 구현 불가로 판정하지 않는다.
- 화면 안의 Last Update는 **기재된 날짜**다. 실제 Figma 최종 수정 시점과 우리가 확인한 날짜를 구분한다.

## 질문을 만들 때 지킬 기준

- 설명·목업·IA가 다르면 “어느 기준을 적용하나요?”라고 묻는다. 플랫폼·로그인 상태·조회 범위에 따른 의도된 차이인지 먼저 확인한다.
- 기존에 정의된 내용은 인정한다. BO 관리가 명시됐다면 “정적/동적 여부”를 다시 묻기보다 관리 필드·고정 항목·전달 계약을 확인한다.
- 조회 기간과 보존 기간, 원본 부재와 아직 조회하지 않은 상태를 구분한다.
- 사용자에게 보이는 정책·흐름 질문과 개발 담당끼리 합의할 기술 계약을 구분한다. 모든 기술 세부사항을 기획자가 정의해야 한다고 요구하지 않는다.
- 내부 문서의 잘못된 참조는 내부 정정으로 기록한다. 이를 기획 누락으로 바꾸지 않는다.
- “개발 불가”, “하드코딩할 수밖에 없다”, “무조건 재작업” 같은 표현은 검증된 근거 없이 사용하지 않는다. SDK·저장소·Bridge·페이지네이션·공통화 방식을 임의로 결정하지 않는다.
- 없는 정책·예외·기능을 만들어 질문 수를 늘리지 않는다. 빈 페이지나 심하게 미완성인 영역은 보류 기록만 남기고 업데이트 후 다시 본다. 보지 못한 기능의 누락 목록이나 개발 영향 문서를 억지로 만들지 않는다.

## 웹·앱·IA 구분

- `01.FO_APP_IA.html`은 하이브리드 앱이다. Native와 앱 내부 WebView 배치를 구분한다.
- `01.FO_WEB_IA.html`은 회원·결제를 포함할 반응형 웹 과업의 참고 IA다. 시트의 `webview` 표기를 앱 내부 웹만이라는 의미로 해석하지 않는다.
- 화면은 **IA 시트 + 화면 코드**로 식별한다. 시트가 다르면 같은 코드도 다른 화면일 수 있다. 코드 차이 자체를 충돌로 단정하지 않고, Figma 노드와 대상 시트·코드의 대응을 확인한다.
- IA 배치만으로 정책·실제 담당·기술 계약이 확정됐다고 쓰지 않는다. IA 원본 HTML은 수정하지 않는다.

## 산출물과 업데이트

- A: `NN-주제-A-기획리뷰.md`. 관찰·질문·근거·상태를 기록하고 `RC-NN-###`를 부여한다. 분류는 [정책] [Flow] [화면/상태] [데이터/API] [Native/Web] [변경] 중 필요한 것만 붙인다.
- B: `NN-주제-B-개발영향.md`. A의 ID를 참조해 웹·앱 영향과 함께 확인할 내용을 적는다. 새 질문은 A에 먼저 등록한다. IA·계약·실제 작업 상태는 보조 근거로 연결할 수 있다.
- 페이지 전체가 작성 중·검토 보류라면 README 진행 현황에 위치·날짜·이유만 남겨도 된다. 질문이 없으면 빈 A/B 파일을 만들 필요가 없다. 검토 가능한 내용이 생기면 다시 읽는다.
- 기존 A/B 틀과 후보 ID를 유지한다. 반복 설명·의례적인 경고·불필요한 필드를 늘리지 않는다. PM을 별도 주체로 도입하지 않는다.
- Figma 업데이트는 자동 반영되지 않는다. 재조회 후 같은 질문은 해소·부분 해소·변경으로 갱신하고, 별개의 질문에만 새 ID를 부여한다. 이전 관찰·답변·결정은 보존한다.
- 질문이 해소되어도 개발·통합 완료로 처리하지 않는다. 실제 작업 상태를 모르면 미확인으로 둔다.
- 2026-10-16까지 기획 진행 상황을 보며 조금씩 검토한다. 이 날짜는 기획·검수·개발 전체 완료 기한이 아니다.
- Figma는 읽기 전용이다. 사용자 승인 전 코멘트·수정·외부 확인 요청을 하지 않는다.
