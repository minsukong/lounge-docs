# work/inspect_sb — 페이지별 기획 검수·개발 영향 검토 자료

**AI 작업 전 [기획 검토 지침](AGENTS.md)을 먼저 읽습니다.** 현재 작성 중인 기획에서 확인 질문을 찾는 작업입니다. 내용이 있는 부분은 검토하고, 비어 있거나 심하게 미완성인 부분은 **작성 중·검토 보류**로 짧게 기록한 뒤 업데이트 후 다시 봅니다. 빈칸마다 결함이나 질문을 만들지 않습니다. **OLD로 표시된 섹션과 모든 하위 화면·설명은 읽거나 검토하지 않습니다.**

이 폴더는 Figma 기획 페이지 단위의 검토 산출물과 프로젝트 현황 브리핑을 보관합니다. `docs/`의 운영 기준이나 실제 구현 명세가 아닙니다. [work 영역 규칙](../AGENTS.md)에 따라 이 폴더의 자료는 해당 검토 요청을 다룰 때만 읽습니다.

여기에 적힌 화면 ID, 후보 목록, 영향 서술은 확정된 정책·계약·담당·일정을 뜻하지 않습니다.

**주요 전제: 현재 Backend 협의가 충분히 이루어지지 않은 상태(2026-10-07 사용자 확인).** 기획의 정책·흐름 확인과 Backend의 API·인증·데이터 계약 협의를 구분합니다. 항목별 합의 여부와 기존 자료를 확인하며, API가 없거나 모든 항목이 미합의라고 단정하지 않습니다. 이후 페이지도 같은 기준으로 작성하고, 합의되면 기존 RC에 날짜·근거를 남깁니다.

**Figma 접근:** 현재 MCP를 사용할 수 없어 REST API로 읽기 전용 조회합니다. 토큰은 사용자가 원본 조회 작업을 요청할 때만 전달하며, 파일·문서·로그에 저장하거나 노출하지 않습니다. 새 조회에 토큰이 없으면 과거 토큰을 찾아 재사용하지 않습니다. 상세 기준은 [기획 검토 지침](AGENTS.md)의 “Figma 조회 방식과 토큰”을 따릅니다.

## 평소에는 간단히 기록하기

기본 기록은 **확인할 내용 / 작업 영향 / 현재 상태 / 날짜·근거** 네 가지로 작성합니다. 매번 모든 상세 필드를 채울 필요는 없습니다. 임시 가정·담당·공수·재작업은 실제로 확인하거나 결정한 경우에만 추가합니다.

- A는 무엇을 확인해야 하는지 짧게 적습니다. 상태는 `확인 필요 / 확인 중 / 해소` 정도로 요약하고, 요청·답변은 실제 발생했을 때 이력에 남깁니다.
- B는 같은 ID 옆에 웹·앱 작업에서 달라지는 부분을 적습니다. 영향이 달라지지 않았다면 매번 새로 작성하지 않습니다.
- 아래 상세 양식과 단계는 필요한 경우의 참고입니다. 기존 03 문서의 관찰과 이력은 보존합니다.

### Figma가 업데이트되면

Figma 변경은 이 문서에 자동으로 반영되지 않습니다. 사용자가 업데이트를 알려주거나 다음 검토를 요청하면 해당 페이지를 다시 읽고 이전 기록과 비교합니다.

| 확인 결과 | 문서 처리 |
|---|---|
| 기존 질문에 답이 생김 | 같은 RC를 해소로 요약하고, 날짜·근거를 추가. 실제 개발 완료 여부는 별도로 기록 |
| 일부만 정의됨 | 정의된 부분을 기록하고 남은 질문만 유지 |
| 이전 정의가 바뀜 | 같은 RC에 변경 전후와 작업 영향을 추가 |
| 별개의 새 질문이 생김 | A에 새 RC를 추가하고 필요한 경우 B에 영향 연결 |
| 변화가 없거나 확인 불가 | 기존 상태 유지. 실제 확인한 날짜·범위 또는 확인 불가 사유만 기록 |

원본의 정확한 수정 시점을 알 수 없다면 문서에는 **우리가 확인한 날짜**를 남깁니다. 과거 기록은 덮어쓰지 않고 짧은 이력을 추가합니다. Figma 코멘트는 별도 승인 전 등록하지 않습니다.

## 문서 유형 두 개

기획 페이지 하나를 검토할 때마다 **두 개의 파일**을 만듭니다. 페이지 번호는 Figma 페이지 번호(`work/기획figma구조.txt`)를 그대로 씁니다.

| 유형 | 파일명 패턴 | 후보 ID | 답하는 질문 |
|---|---|---|---|
| **A. 기획 검수·이력 원장** | `NN-<주제>-A-기획리뷰.md` | `RC-NN-###` 생성 | 무엇을 물어야 하는가 |
| **B. 개발 영향 환산** | `NN-<주제>-B-개발영향.md` | A의 `RC-NN-###` 참조 | 그 미확정이 작업에서 왜 문제인가 |

- `NN`은 페이지 번호입니다. 하위 페이지는 `04-01`처럼 원본 번호를 따릅니다.
- B는 새 이슈를 만들지 않습니다. 항상 A가 만든 `RC-NN-###`로만 참조하므로, 두 파일 사이에서 질문·결정·구현 변경이 같은 ID로 추적됩니다.
- A 없이 B를 먼저 쓰지 않습니다. B는 A의 후보를 입력으로 받는 파생 문서입니다.
- 페이지를 넘어선 공통 주제(예: `01. 공통`의 오류 정의)에는 새 ID를 만들지 않고, 각 페이지의 RC에서 해당 페이지의 RC를 참조합니다.

### 유형 A — 기획 검수·이력 원장

"현재 기획만 전달받은 작업자가 추가 질문 없이 동일한 결과를 만들 수 있는가"를 검증하고, 막힌 지점을 질문 → 답변 → 결정으로 추적하는 대장입니다.

- **1차 독자**: 기획자·작업자. 결정 대상은 "무엇을 묻고, 답이 왔을 때 무엇이 확정되는가"입니다.
- **상세 기록 참고 필드**: 이전 관찰 / 확인되지 않은 부분 / 확인 요청 초안 / 작업 영향 / 임시 가정 / 변경·재작업 가능성 / 대조할 근거
- **검수 분류 6개**: [정책] [Flow] [화면/상태] [데이터/API] [Native/Web] [변경]
- **필요할 때 확인할 상세 단계**: 후보 → 원본 대조 → 사용자 검토 → 확인 요청 → 답변 수신 → 반영 확인 → 종료
- **하지 않는 것**: 기획자 평가와 책임 판단, Ready 판정, Figma 수정·코멘트 등록, 실제 확인 요청 발송.

상세 문서가 필요할 때는 다음 구성을 참고합니다.

1. 목적과 읽는 방법(원본 대조 여부를 명시)
2. 범위와 검수 위치
3. 검수 분류와 상태
4. Review Candidate 목록과 항목별 상세
5. 기록 양식과 이력 예시
6. 다음 검토 범위

문서 제목은 두 유형 모두 같은 형식을 따릅니다.

- A: `NN. <페이지명> — A. 기획 검수·이력 원장`
- B: `NN. <페이지명> — B. 개발 영향 환산`

파일명의 `A`·`B` 접두는 문서 제목의 유형 표기와 같게 유지합니다. 같은 페이지의 두 파일이 목록에서 A → B 순으로 나란히 정렬되게 하기 위한 규칙입니다. `03-로그인-회원가입-A-기획리뷰.md`의 5절 양식이 **다른 페이지를 같은 방식으로 검수할 때의 형식 시연**이므로, 새 페이지를 시작할 때 그 골격을 본떠 만듭니다. 이후 페이지의 문서는 해당 페이지에서 실제로 확인한 내용으로 채워지므로 그대로 검수 원장이 됩니다.

### 유형 B — 개발 영향 환산과 협의 의제

A의 후보를 입력으로 받아 "왜 지금 물어야 하고 누가 함께 결정해야 하는가"로 번역합니다. 기획 질문을 담당별 구현 전제 차이로 환산합니다.

- **1차 독자**: 웹 FE·Flutter·BE·QA 담당과 협의 진행자. 결정 대상은 "어떤 기술 계약을 누가 합의할 것인가"입니다.
- **핵심 기능**: 여러 담당의 구현 전제를 함께 결정하는 RC를 **우선 협의 대상**으로 지목하고, 흩어진 후보를 실제 합의 문서 단위로 묶습니다.
- **후보와 근거**: 후보 ID는 A에서만 생성합니다. B는 A의 후보를 참조하고, 개발 영향 분석에는 IA·기술 계약·실제 작업 상태의 근거도 연결할 수 있습니다. 근거별 확인 시점과 확인 여부를 구분하며, B에서 새 질문이 발견되면 A에 등록한 뒤 참조합니다. 확인하지 않은 원본이나 기술 명세는 미확인으로 남깁니다.

상세 문서가 필요할 때는 다음 구성을 참고합니다.

1. 작업 관점에서의 핵심 문제와 우선 협의 대상
2. 항목별 웹·앱 개발 영향과 공동 확인 항목
3. 담당 간 전제가 갈리는 사례(가상 사례임을 명시)
4. 진행 가능한 준비 작업과 완료 조건 분리
5. 일정·공수·재작업에 미칠 수 있는 영향
6. 우선 협의할 산출물
7. 개발 영향 기록 양식

### 두 유형이 갈리는 이유

| 구분 | A. 기획 검수 원장 | B. 개발 영향 검토 |
|---|---|---|
| 산출물 성격 | 질문과 결정 이력 | 영향과 합의 의제 |
| 갱신 계기 | 원본 대조 결과, 기획 답변 수신 | 기술 계약 합의, 작업 상태 변화 |
| 상태 값 | 후보 → … → 종료 | 미착수 / 준비 / 임시 구현 / 연동 대기 / 통합 확인 |
| 근거 범위 | Figma 원본 + 이전 논의 + 연결된 확인 근거 | A의 후보 + IA·기술 계약·실제 작업 상태의 확인 근거 |

### 상태 값은 두 개의 축입니다

두 값은 서로 다른 진행을 관리하므로 한쪽으로 통합하지 않습니다. 같은 RC를 다룰 때는 아래 대응으로 함께 읽습니다.

| A의 검수 상태 | B에서 함께 관리할 내용 |
|---|---|
| 후보 / 원본 대조 | 영향은 예상으로 기록. 작업 상태는 실제 확인 결과를 기록하고, 확인하지 못했으면 미확인 |
| 확인 요청 → 답변 수신 | 실제 대기 중인 작업이 있으면 선행 조건·대기 사유를 기록. 목표 확인 시점은 합의된 경우만 기록 |
| 반영 확인 | 기획·계약 반영과 실제 구현·연동·검증 상태를 각각 확인하여 기록. 특정 개발 상태로 자동 전환하지 않음 |
| 종료 | A의 질문 해소 근거를 연결하고 B의 실제 작업·검증 상태는 별도 유지. A 종료만으로 개발·통합 완료를 표시하지 않음 |

A의 검수 상태와 B의 개발 상태는 독립적입니다. 검수 전에도 개발이 진행 중일 수 있고, 정책 질문이 해소된 뒤에도 구현·통합 검증이 남아 있을 수 있습니다.

## 2026-10-16까지의 점진 검토 운영

- 01~12와 마이페이지 하위 04-01·04-02를 대상으로, 기획 업데이트와 진행 상황을 보며 조금씩 검토합니다. BO 관련 페이지는 제외합니다.
- 10월 16일은 현재의 점진 검토 운영 기간입니다. 기획 확정일이나 전체 검수·개발 완료일로 간주하지 않습니다. 별도 자동 모니터링이나 정기 알림은 설정하지 않았습니다.
- 각 검토 시점의 원본 위치·조회 일시·확인 범위를 남깁니다. 업데이트되지 않았거나 확인하지 못한 부분은 그 상태를 기록하고, 프로젝트 전체의 미정의로 확대하지 않습니다.
- 같은 RC ID를 유지하면서 이전 관찰·질문·답변·결정을 보존하고 새 관찰을 이력으로 추가합니다. 최신 상태 요약은 갱신하되, 이전 기록을 새 사실로 덮어쓰지 않습니다.
- 변경을 확인한 경우 변경 전후·근거·작업 영향을 함께 기록합니다. 실제 재작업이나 일정 영향은 확인된 범위만 기록합니다.
- 12개 영역의 문서를 한 번에 만들거나 원본 전체를 매번 조회하지 않습니다. 그때 검토하는 페이지와 직접 연결되는 근거부터 확인합니다.
- Figma 원본은 읽기 전용으로 유지합니다. 코멘트 등록과 실제 확인 요청 발송은 사용자 승인 전 진행하지 않습니다.

## 새 페이지 검토를 시작할 때

1. [Figma 페이지 구조](../기획figma구조.txt)에서 대상 페이지의 번호와 node-id를 확인합니다.
2. A를 만듭니다. 원본을 아직 대조하지 않았다면 후보 단계로 시작하고, 그 사실을 문서 상단에 명시합니다.
3. A의 후보를 원본과 대조해 유지·수정·기정의 종료로 정리합니다.
4. 유지된 후보를 대상으로 B를 만듭니다. B는 A의 RC ID만 참조합니다.
5. 이후 답변·결정·구현 변경은 두 문서의 기록 양식에 같은 `RC-NN-###`로 남깁니다.

## 읽는 순서

1. A의 Review Candidate 목록에서 RC와 분류를 확인합니다.
2. B의 항목별 영향과 우선 협의 산출물에서 그 RC가 어떤 담당의 구현 전제를 바꾸는지 확인합니다.
3. A의 마지막 절 순서대로 진행합니다: 원본 대조 → 후보 정리 → 사용자 검토 → 확인 요청 → 답변 반영.
4. 결과가 생기면 A의 이력 표와 B의 기록 양식에 같은 RC ID로 남깁니다.

## 아직 적용되지 않은 것

03 문서 두 개는 **후보 단계**입니다. 원본 Figma 대조가 수행되지 않았고 확인 요청도 발송되지 않았습니다. 따라서 아래는 아직 사실로 읽지 않습니다.

- 8개 항목이 실제 기획의 누락이라는 판단
- 특정 담당의 책임, 일정 지연, 재작업 발생
- 회원가입 Ready 여부와 03 페이지 전체 Ready 여부(두 문서 모두 판정 보류로 명시)

원본 대조가 끝나면 A의 후보가 유지·수정·기정의 종료로 정리되고, B의 예상 영향과 우선 협의 목록도 함께 갱신됩니다.

01. 공통 문서는 그 단계까지 진행한 경우의 형태입니다. REST API로 원본 텍스트를 읽어 관찰을 확인했고, 확인 요청은 보내지 않았습니다. 이 과정에서 확인된 화면 코드 기준 미확정(RC-01-007)은 03-B 문서가 쓴 "IA 시트 + 화면 코드로 APP/WEB를 구분한다"는 전제와 관련됩니다. 두 시트의 코드 체계가 다르다는 것은 확인했지만, 이를 오류로 단정하지는 않는다. 03 문서의 해당 문장은 아직 수정하지 않았습니다.

02. 메인 문서 두 개도 같은 단계까지 진행했다. 화면 코드는 IA 원본에서 확인한 값으로 적었고, 어느 시트가 기준인지는 확인하지 않았다. 02에서 확인된 `FO-MAI-*` 코드의 화면구분·플랫폼 차이는 위와 같은 기준 미확정과 이어진다.

## 브리핑 문서군

`더라운지3.0_프로젝트현황*` 3개와 `project-status-briefing.js`는 한 세트입니다. 페이지 단위 검토와 성격이 다르므로 위 진행 현황 표에 포함하지 않습니다.

- `.md`가 내용 원본이고, `.html`은 같은 내용을 화면으로 발표한 것입니다. 필요한 스타일과 스크립트는 `docs/assets/`에 있습니다.
- HTML이 참조하는 자산 경로는 `../../assets/…` 형태라 이 폴더에서는 실제 파일과 연결되지 않습니다(저장소 루트에 `assets/`가 없음). 화면이 깨지거나 발표자 모드가 동작하지 않으면 이 경로를 먼저 확인합니다.
- `_브리핑진행안.md`는 HTML을 띄운 상태에서 발표자가 읽을 문장, 피해야 할 표현, 예상 질문과 답변을 담습니다.
- `project-status-briefing.js`는 HTML의 `window.LoungeBriefingPresenterConfig`에 주입되는 섹션별 노트입니다. HTML의 섹션 순서가 바뀌면 이 파일의 `key` 값도 함께 맞춰야 합니다.

이 브리핑의 결론은 "자료가 없다"가 아니라 "자료의 숫자·일정·목록이 공식 범위와 일정의 기준선인지 확인하기 어렵다"입니다. 페이지 단위 검토 문서는 그중 **기획과 인터페이스 항목을 실제 화면 단위로 내려보는 방식**입니다.
