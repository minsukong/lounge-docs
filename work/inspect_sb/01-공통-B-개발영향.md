## 1. 작업 관점에서의 핵심 문제

**Backend 협의 전제(2026-10-07 사용자 확인):** 현재 Backend 협의가 충분히 이루어지지 않아 연동 기준의 합의 여부를 확인해야 하는 상태다. 사용자에게 보이는 조건·흐름은 **기획 확인**, 데이터·인증·오류·상태 전달·처리 주체는 **Backend 협의 필요**로 구분한다. API·문서·구현 부재나 모든 항목의 미합의를 뜻하지 않으며, 기존 자료·합의 근거를 항목별로 확인한다.

RC-01-004·005·006의 오프라인·BO 관리 데이터·알림 연결은 기획 요구와 Backend·앱 전달 계약을 나눠 확인한다. 협의 결과에 따라 웹·앱 연동·검증 범위가 달라질 수 있으며, 실제 작업 중단·재작업 여부는 별도 확인한다.

공통 영역은 여러 화면에 영향을 준다. 헤더·바텀·푸터·플로팅 메뉴·알림의 적용 기준과 데이터 연결을 확인하면 화면별 구현 전제를 맞출 수 있다. 현 문서에서 확인되지 않은 부분을 질문으로 남기며, 프로젝트 전체가 미확정이라고 판단하지 않는다.

- **적용 기준을 확인해야 한다.** 같은 페이지 안에서 GNB·바텀·플로팅 메뉴의 항목 집합이 프레임마다 다르고(RC-01-001, RC-01-003), PC header·LNB에는 화면 설명이 없다(RC-01-002). 차이가 의도된 플랫폼·화면 상태별 구성인지 확인하면 공통 항목과 분기를 정리할 수 있다.
- **데이터 주체가 외부에 있다.** 푸터와 플로팅 메뉴는 BO 전시에서 관리한다고 적혀 있고(RC-01-005), 오프라인 QR은 기기 저장 데이터를 요구한다(RC-01-004). 관리 데이터의 전달 계약과 오프라인 처리 주체를 관련 담당과 확인할 필요가 있다.
- **Figma·IA 연결을 확인해야 한다.** APP·WEB은 시트와 코드를 함께 쓰면 구분할 수 있다. Figma 각 화면의 대상 플랫폼과 대응 시트·코드를 확인해 작업·테스트 근거로 연결한다(RC-01-007).

기획 확인은 **RC-01-001·003(내비게이션·플로팅 기준), RC-01-008(위치정보 약관 본문)**부터 제안한다. **RC-01-004·005·006(오프라인·BO·알림 계약)**은 관련 개발 담당과 함께 확인하고, RC-01-007은 Figma·IA 연결 근거를 보완한다.

이번 검수는 A·B 문서의 논리와 참조를 확인한 것으로, Figma 추출 원문·BO/BE 명세·실제 개발 상태는 재검증하지 않았다. 아래 영향은 **후보의 불확실성이 실제로 남아 있는 경우의 예상 결과**이며, 확정된 기획 누락·개발 장애·일정 지연·재작업 실적이 아니다.

### IA에서 확인한 공통 영역 배치

2026-10-07에 IA 원본을 조회했다는 초안의 기록을 유지한다. 공통 영역은 두 시트에서 코드 체계가 다르다.

| 화면 | [APP IA](../더라운지_IA%20FO_v0.2.xlsx/01.FO_APP_IA.html) | [WEB IA](../더라운지_IA%20FO_v0.2.xlsx/01.FO_WEB_IA.html) | Figma 01. 공통 |
|---|---|---|---|
| 알림 팝업 | `A010100` · **Native** | `B010100` · webview · 회원 | `B010100` |
| 알림 목록 | `A010200` · webview | `B010200` · webview · 회원 | `A010200` |
| 알림 상세 | `A010300` · webview | `B010300` · webview · 회원 | `A010300` |
| 검색 | `A020000` · webview | `B020000` · webview · **비회원** | 화면 없음 |
| 플로팅 메뉴 쿠폰북 | `B010000` · Link · webview | `C010000` · Link · webview | 버튼 목업만 |
| 플로팅 메뉴 내 월렛 | `B020000` · Link · webview | `C020000` · Link · webview | 버튼 목업만 |
| 다국어 설정 | `C000000` · page · webview | `D000000` · Layer · webview | IA 표만, 화면 없음 |
| GNB(전체메뉴) 로그인 전/후 | `D010000`·`D020000` · **Native** | `E000000` 계열 | 화면 설명 없음 |
| 풋터 제휴문의·정책 4종 | `E010000`~`E040000` · webview | `F010000`~`F040000` | `E010000`~`E040000` |
| 스플래시화면 | 코드 없음 | — | 없음 |

`FO-CMM-B020000`은 APP IA에서 플로팅 메뉴>내 월렛, WEB IA에서 검색이다. 코드만 보면 다르지만 `IA 시트 + 화면 코드`로 두 화면을 구분할 수 있다. Figma 각 화면이 어느 시트·코드와 대응하는지 확인해야 한다.

APP IA는 GNB(전체메뉴)와 알림 팝업을 Native로, 나머지를 webview로 배치한다. Figma는 MO 전체 메뉴와 알림 팝업을 화면·팝업으로만 정의하고 플랫폼을 적지 않는다. 이 배치만으로 실제 구현 주체가 확정되지는 않는다.

## 3. 담당 간 구현 전제가 달라질 수 있는 사례

아래는 실제 발생 보고가 아닌, 협의가 필요한 이유를 설명하는 가상 사례다.

| 전제가 갈리는 지점 | 서로 다른 구현 전제의 예 | 통합 시 발생할 수 있는 결과 | 먼저 합의할 내용 |
|---|---|---|---|
| 공통 헤더 소유 | 웹은 공통 헤더를 React 컴포넌트로, 앱은 Native 헤더로 각각 만든다고 생각함 | 헤더 항목·알림 카운트·검색 진입이 플랫폼마다 다르게 동작 | 플랫폼별 헤더 구현 주체와 공유 항목 |
| 푸터 데이터 | 웹은 푸터를 정적 마크업으로 확정하고, BO는 푸터 관리에서 링크를 바꿀 수 있다고 생각함 | BO에서 링크를 바꿔도 화면에 반영되지 않음 | BO 관리 대상 필드와 Front 수신 방식 |
| 오프라인 QR | 웹은 서버 응답 실패 시 빈 상태로, 앱은 저장된 이용권을 보여준다고 생각함 | 인터넷 없는 공항에서 사용자에게 아무것도 안 보임 | 저장 주체, 읽기 경로, 서버 상태와의 우선순위 |
| 알림 팝업 | IA는 Native, Figma는 화면으로만 정의. 앱은 웹 화면을 띄운다고 보고 웹은 앱이 팝업을 연다고 봄 | 알림 진입이 중복되거나 빠짐. 헤더 카운트 갱신 주체도 없음 | 알림 진입 주체와 카운트 반영 순서 |
| 화면 코드 | 작업 카드는 APP IA 코드로, 테스트 케이스는 WEB IA 코드로 작성됨 | 다른 화면이 같은 ID로 묶여 결함 추적이 섞임 | IA 시트·코드 병기와 Figma 대응 관계 |
| 카테고리 | 웹은 이용권 구매와 사용처 탐색이 같은 분류 API를 쓴다고 보고, BE는 분리한다고 생각함 | 메뉴와 목록 필터가 서로 다른 값을 표시 | 분류 체계 공용/분리 여부와 표기 기준 |

기획은 사용자에게 보이는 조건·행동을 확정하고, 개발 담당은 그 행동을 구현하는 기술 계약을 합의해야 한다. 화면 기획에 기술 세부사항이 없다는 이유만으로 기획 누락을 단정하지 않는다. 별도 BO·API 명세가 있으면 해당 근거를 연결한다.

## 4. 작업 진행과 완료 판단을 나누어 볼 부분

실제 코드·API·BO 준비 상태를 확인하지 않았으므로 아래는 작업 분리 제안이다. 전체 개발 중단을 의미하지 않는다.

| 작업 단계 | 진행할 수 있는 준비 작업 | 완료를 확정하려면 필요한 확인 |
|---|---|---|
| 공통 컴포넌트 골격 | Header·Footer·BottomNav·Floating의 인터페이스 초안, slot 구조 분리 | 항목 배열과 라벨, PC/MO 분기 기준 |
| 알림 화면 | Chips·목록 행·배지·빈 상태의 정적 마크업과 Story | 분류·조회 기간·읽음 요구와 실제 응답 |
| 정책 화면 | 약관·정책 레이아웃과 목차 내비게이션 구조 | 약관 본문, 동의 조건, 최종 경로 |
| 앱 연동 준비 | 오프라인 QR·알림 카운트에 필요한 이벤트 목록 정리 | 저장 주체, Bridge 계약, 갱신 순서 |
| BO 연동 준비 | 푸터·플로팅 메뉴에 필요한 필드 목록 정리 | BO 응답 형태와 관리/고정 항목 경계 |
| QA 기준 | 정상·빈 상태·오프라인·로그인 전후 검증 항목 초안 | 합의된 기대 결과와 실제 환경 |

목업 문구를 그대로 쓴 정적 마크업은 그 범위의 동작 확인이다. 공통 영역 구현이나 정책 확정까지 완료했다고 기록하지 않는다. 임시 구현을 선택한다면 가정·적용 범위·승인자·변경 시 영향을 함께 기록한다.

## 5. 일정·공수·재작업에 미칠 수 있는 영향

- **기반 작업의 선행성:** 적용 기준이 뒤늦게 바뀌면 연결된 화면을 수정할 수 있다. 기존 구성과 공유 범위에 따라 영향이 달라지므로 실제 변경을 확인해 기록한다.
- **BO·BE 의존:** 푸터·플로팅 메뉴(RC-01-005)와 알림(RC-01-006)은 Front 단독으로 완료할 수 없다. 담당별 구현 완료와 연동 완료는 별도 기록이 필요하다.
- **오프라인 요구의 테스트 비용:** RC-01-004는 네트워크 차단 환경 검증이 필요하다. 처리 범위와 계약에 따라 QA 준비 범위가 달라질 수 있다. 실제 지연은 확인 후 기록한다.
- **식별자 정합성:** 코드 단독 사용 시 혼동할 수 있으므로 IA 시트·코드를 병기한다. Figma 원본 노드와 화면명을 연결하면 추적 근거를 보완할 수 있다.
- **약관 대기의 파급:** RC-01-008의 본문·동의 조건이 회원가입에 적용되는지 확인한다. 확정 결과에 따라 동의 화면이 달라질 수 있다. RC-01-010은 다국어 항목이며 동의 흐름의 직접 근거가 아니다.
- **재작업 기록:** 기존 합의대로 구현했는지, 미확정 상태에서 어떤 가정으로 진행했는지에 따라 변경 원인을 구분한다. 현재 문서에서 재작업 발생이나 특정 담당의 책임을 확정하지 않는다.
