# 더라운지 3.0 프로젝트 현황 브리핑 진행안

## 1. 이 문서의 사용 목적

이 문서는 `더라운지3.0_프로젝트현황및정상화필요사항.html`을 화면에 띄워놓고 설명할 때 사용하는 발표자용 진행안이다.

HTML에서 `Ctrl + Shift + .`를 누르고 `/briefing`을 입력하면 오른쪽에 현재 섹션의 발표자 노트가 표시된다. `Esc`를 누르면 발표자 모드가 종료된다.

브리핑의 목적은 특정 개인이나 파트의 역량을 평가하는 것이 아니다. 현재 확인할 수 있는 자료의 상태, 일정에 미치는 영향과 필요한 결정을 공통으로 확인하는 것이 목적이다.

발표할 때는 모든 내용을 다음 순서로 말한다.

1. 현재 확인된 사실
2. 그 사실이 개발과 일정에 미치는 영향
3. 앞으로 필요한 확인 또는 결정

사람에 대한 평가, 과거 대응에 대한 감정과 책임 공방으로 확대하지 않는다.

## 2. 권장 브리핑 시간

| 구분 | 권장 시간 |
| --- | --- |
| 목적과 결론 | 1분 |
| 현재 자료 상태 | 3분 |
| 파트 간 의존관계와 WBS | 3분 |
| 주요 위험과 정상화 순서 | 3분 |
| 결정 요청 및 질의 | 5분 |

전체 설명은 약 10분, 질의를 포함해 15분 안팎으로 진행한다.

## 3. 시작 전에 기억할 원칙

- “누가 잘못했는가”보다 “현재 무엇이 확정됐는가”를 묻는다.
- “없다”라고 단정하기 전에 확인 가능한 문서, 버전과 승인 기록을 요청한다.
- 모호한 표현이 나오면 결정 내용, 담당, 목표일과 적용 버전으로 바꾼다.
- 이미 확정됐다는 답변에는 확정 문서, 승인자와 적용일을 요청한다.
- 회의 중 새로운 사실이 확인되면 반박하지 않고 문서에 반영할 확인사항으로 기록한다.
- 일정 답변을 요구받아도 검증되지 않은 숫자를 즉석에서 제시하지 않는다.

## 4. 브리핑 시작 문장

다음 문장은 그대로 읽어도 된다.

> 오늘 말씀드릴 내용은 특정 개인이나 파트의 책임을 지적하기 위한 것이 아닙니다. 현재 프로젝트의 범위와 일정을 판단할 수 있는 자료가 어떤 상태인지, 개발을 진행하려면 무엇을 확인해야 하는지를 공유드리려는 것입니다.
>
> 현재 자료가 전혀 없다는 뜻은 아닙니다. 다만 자료에 있는 화면 수, 일정과 목록이 최종 승인된 개발 기준인지 확인하기 어렵다는 것이 핵심입니다.
>
> 이미 확정된 내용이 있다면 해당 문서의 버전, 확인 담당과 적용 기준을 알려주시면 바로 반영하겠습니다. 오늘은 확인되지 않은 내용을 확정된 것으로 사용하지 않기 위한 기준을 맞추고자 합니다.

## 5. 화면별 설명 순서

### 5.1 `1. 결론`

핵심은 한 문장이다.

> 현재 IA, WBS, 기획, 디자인과 인터페이스 자료를 공식 범위와 일정의 기준선으로 사용하기 전에 담당 파트의 검증과 확정이 필요합니다.

이어서 다음과 같이 설명한다.

> 그래서 기존 WBS의 날짜만 다시 입력하는 방식으로는 신뢰할 수 있는 완료일을 만들기 어렵습니다. 범위, 선행조건과 파트별 제공 일정을 확인한 뒤 WBS를 다시 수립해야 합니다.

여기서는 과거 경위나 사람별 대응을 설명하지 않는다.

### 5.2 `2. 현재 상태`

표의 각 행을 길게 설명하지 않고 다음 세 가지로 묶는다.

> 첫째, IA와 WBS는 범위 집계 기준과 선후행 관계를 다시 확인해야 합니다.
>
> 둘째, 기획과 디자인은 화면의 모양뿐 아니라 업무 규칙, 데이터 출처와 예외 상태까지 연결돼야 개발 기준이 됩니다.
>
> 셋째, 인터페이스 자료는 v0.8.1 내부 확인용으로, Endpoint 목록을 파악할 수는 있지만 상세 요청·응답과 인증 기준이 부족해 구현 기준 명세로 사용할 수 없습니다.

반드시 덧붙일 문장:

> 각 자료의 일부 내용은 활용할 수 있습니다. 다만 활용 가능한 정보와 확정된 기준은 구분해야 합니다.

### 5.3 `3. 활용 가능한 자료와 한계`

> Front-end 구현, 품질, 보안, 접근성, WebView 책임 경계에 대한 가이드는 준비돼 있습니다. 이 자료는 개발 방식을 통일하는 데 사용할 수 있습니다.
>
> 그러나 기술 가이드가 화면별 업무 규칙, 최종 IA와 Backend API 명세를 대신할 수는 없습니다.

일정 산정 자료는 다음처럼 설명한다.

> 기존 planning 문서의 화면 수와 기간은 작성 당시 전달된 자료를 사용한 조건부 산정입니다. 현재 확정 범위나 공식 완료일이 아닙니다. 그래서 planning 문서에도 같은 안내를 반영했습니다.

인터페이스 자료는 다음처럼 설명한다.

> 인터페이스 자료는 API 영역과 확인 질문을 찾는 용도로는 가치가 있습니다. 다만 IN-APP API 66건의 상세 요청·응답이 기재되지 않았고 인증과 Token 처리도 확정되지 않아 실제 연동 기준으로는 부족합니다.

### 5.4 `4. 기능 개발 전에 확인할 내용`

> 개발 전에 모든 문서가 완벽해야 한다는 뜻은 아닙니다. 기능별로 실제 구현에 필요한 최소 정보가 확인돼야 한다는 뜻입니다.

최소 정보는 다음 다섯 가지로 줄여 말한다.

1. 사용자가 무엇을 하는 기능인지
2. 정상과 예외 상태가 무엇인지
3. 어떤 데이터를 어느 파트에서 제공하는지
4. API 또는 Native 연동이 필요한지
5. 무엇을 완료로 판단할지

> 이 다섯 가지가 확인된 기능은 진행하고, 확인되지 않은 기능은 대기 사유와 일정 영향을 WBS에 표시하자는 제안입니다.

### 5.5 `5. 파트 간 주요 의존관계`

> Front-end 작업은 기획, 디자인, Backend와 Native 작업이 모두 끝난 뒤 시작한다는 의미가 아닙니다. 기능별로 필요한 입력이 제공되는 순서에 따라 병렬로 진행할 수 있습니다.
>
> 다만 입력이 없는 기능까지 임의로 개발하면, 나중에 기준이 정해졌을 때 화면, Type, 오류 처리와 테스트를 다시 수정하게 됩니다.

강조할 문장:

> 현재 필요한 것은 전체 중단이 아니라, 진행 가능한 기능과 협의가 필요한 기능을 구분하는 것입니다.

### 5.6 `6. IA와 WBS 재수립`

> 현재 WBS의 문제는 날짜가 틀렸다는 한 가지 문제가 아닙니다. 날짜의 근거가 되는 범위, 선행조건과 확인 대기가 연결돼 있지 않다는 문제입니다.

WBS 재수립 순서는 다음 네 단계로 압축해 말한다.

1. IA의 분류 기준과 누락 범위를 검증한다.
2. 기능별 미확정 사항과 담당 파트를 연결한다.
3. 실제 제공 일정과 투입 인력을 반영한다.
4. 통합 QA와 안정화까지 포함해 완료일을 계산한다.

> 개발 인원을 늘리는 것은 구현 병렬화에는 도움이 됩니다. 하지만 기획, API와 Native 관련 확인이 늦어지는 문제까지 해결하지는 못합니다.

### 5.7 `7. 주요 리스크`

리스크를 모두 읽지 말고 우선순위 세 가지만 말한다.

> 가장 큰 위험은 검증되지 않은 IA와 WBS를 공식 기준으로 사용해 범위 누락과 잘못된 완료일이 반복되는 것입니다.
>
> 두 번째는 디자인이나 문서가 존재한다는 이유로 기능 개발이 가능한 상태라고 판단하는 것입니다.
>
> 세 번째는 미확정 업무 규칙과 연동 방식을 개발자가 개별적으로 결정하게 되는 것입니다.

> 나머지 위험은 이 세 가지가 해소되지 않을 때 발생하는 연동 지연, 재작업과 QA 대기입니다.

### 5.8 `8. 정상화 단계`

> 정상화는 새로운 문서를 많이 만드는 작업이 아닙니다. 기존 자료를 확정, 검토 중, 참고와 미작성으로 구분하는 것부터 시작합니다.

다이어그램을 따라 다음처럼 설명한다.

> 자료 상태를 구분한 뒤 IA와 범위를 검증합니다. 그리고 기획, 디자인, API와 Native의 미확정 사항에 담당과 목표일을 지정합니다. 이 결과를 바탕으로 WBS를 다시 만들고, 확정된 기능부터 개발과 통합 검증을 진행합니다.

### 5.9 `9. 역할과 책임 범위`

> 이 표는 책임을 떠넘기기 위한 표가 아닙니다. 각 파트가 최종 확인해야 할 영역을 구분하기 위한 표입니다.

> Front-end는 확정된 기준에 따라 화면과 상태를 구현하고 기술적 위험을 식별할 책임이 있습니다. 다만 업무 규칙, Backend의 최종 데이터 판단과 Native 플랫폼 동작을 단독으로 확정할 수는 없습니다.

> PM은 각 파트의 결정을 대신하는 역할이 아니라, 범위, 담당, 결정 일정과 전체 선후행 관계를 통합 관리하는 역할로 정리했습니다.

### 5.10 `10. 기능별 착수 및 완료 기준`

> 착수 기준은 개발을 막기 위한 조건이 아니라, 재작업을 줄이기 위한 최소 확인사항입니다.

> 완료도 화면이 보이는 것만으로 판단할 수 없습니다. API 오류, WebView·Native 연동, 실제 기기, QA와 운영 가능 상태까지 확인돼야 완료일을 판단할 수 있습니다.

### 5.11 `11. 최종 정리`

다음 문장으로 마무리한다.

> 오늘 요청드리는 것은 과거 책임에 대한 판단이 아닙니다. 현재 적용할 기준 버전, 미확정 사항의 담당과 목표일, 그리고 이를 반영한 WBS 재수립 일정을 정해달라는 것입니다.
>
> 이미 확정된 항목은 근거 문서와 함께 공유해 주시면 확정 상태로 반영하겠습니다. 확인되지 않은 항목은 담당과 목표일을 지정해 관리하겠습니다.
>
> 이 기준이 잡히면 개발 가능한 기능부터 순차적으로 진행하고, 전체 일정도 근거를 갖고 다시 제시할 수 있습니다.

## 6. 회의에서 요청할 결정사항

브리핑이 끝난 뒤 다음 항목의 담당과 목표일을 요청한다.

| 결정 요청 | 확인할 내용 | 필요한 결과 |
| --- | --- | --- |
| IA 기준선 | 적용할 버전, 분류 기준과 누락 검토 담당 | 기준 IA와 검토 완료일 |
| 기획 완료 기준 | 화면별 업무 규칙·상태·예외의 완료 판단 | 기능별 완료 확인표 |
| 디자인 확인 | 데이터, 상태와 이동 규칙의 검토 방식 | 디자인 미확정 목록 |
| API 명세 | 기능별 상세 명세 제공 순서와 검토 담당 | API 제공 일정 |
| WebView·Native | 세션, Bridge, 외부 앱 복귀와 실제 기기 | 연동 협의 일정 |
| WBS | 재수립 책임자, 참여 파트와 검토 일정 | 통합 WBS 작성일 |
| QA·UAT | 담당, 환경, 기기와 완료 기준 | 통합 검증 일정 |

담당과 목표일이 바로 정해지지 않으면 다음처럼 마무리한다.

> 오늘 결정하기 어려운 항목은 미확정 상태로 기록하고, 누가 언제까지 확인할지만 지정해 주시면 됩니다. 확인 전까지는 해당 항목을 일정상 확정으로 처리하지 않겠습니다.

## 7. 피해야 할 표현과 대체 문장

| 피해야 할 표현 | 대신 사용할 문장 |
| --- | --- |
| 기획이 아무것도 안 했다 | 개발 착수에 필요한 화면별 업무 규칙과 상태 정의의 확정 여부를 확인하기 어렵습니다. |
| 기획 PL이 무능하다 | 기획 완료 기준과 최종 확인 책임이 문서상 명확하지 않습니다. |
| 아는 사람이 없다 | 해당 업무의 최종 확인 담당과 적용 기준이 지정되지 않았습니다. |
| 갑측이 계속 말을 바꾼다 | 주요 결정의 변경 이력과 현재 적용 기준을 확인할 기록이 필요합니다. |
| PM들이 뒷짐지고 있다 | 미확정 사항의 담당, 결정 목표일과 후속 일정 영향이 통합 관리되지 않고 있습니다. |
| IA를 막 만들었다 | IA의 화면·상태 분류 기준과 누락 범위가 검증되지 않았습니다. |
| WBS가 가짜다 | 현재 WBS의 날짜가 검증된 범위와 선후행 관계를 근거로 하는지 확인하기 어렵습니다. |
| 인터페이스 문서가 엉망이다 | 현재 자료는 v0.8.1 내부 확인용이며 구현에 필요한 상세 명세가 부족합니다. |
| 이 프로젝트는 답이 없다 | 현재 방식으로는 신뢰할 수 있는 범위와 완료일을 제시하기 어렵습니다. |
| 개발을 할 수 없다 | 확정된 기능은 진행할 수 있고, 미확정 기능은 필요한 협의와 일정 영향의 구분이 필요합니다. |
| 다 내 책임으로 떠넘긴다 | 업무 규칙과 파트 간 연동 기준은 각 담당의 확인 결과가 필요합니다. |

감정적인 표현이 떠오르면 바로 말하지 말고 다음 문장으로 시작한다.

> 사람에 대한 평가가 아니라 현재 확인 가능한 자료를 기준으로 말씀드리겠습니다.

## 8. 예상 질문과 답변

### Q1. 그래서 개발을 못 한다는 이야기인가?

> 아닙니다. 확정된 기능은 진행할 수 있습니다. 다만 미확정 기능까지 임의로 구현하면 재작업 가능성이 크므로, 진행 가능 항목과 대기 항목을 구분하자는 것입니다.

### Q2. 일단 개발하고 나중에 고치면 되지 않는가?

> UI 일부는 가능하지만 업무 규칙, 인증, 결제와 Native 연동은 기준이 바뀌면 Type, 상태 처리, 테스트와 통합 검증까지 함께 수정됩니다. 변경 비용과 일정 영향을 먼저 공유하고 진행 여부를 결정해야 합니다.

### Q3. 그래서 완료일이 언제인가?

> 현재 자료만으로 확정일을 제시하면 다시 변경될 가능성이 큽니다. IA와 기능 범위, 파트별 제공 일정과 실제 투입 인력을 확인한 뒤 근거가 있는 완료일을 제시하겠습니다.

### Q4. 기존 planning 문서에 기간이 있지 않은가?

> 해당 기간은 작성 당시 IA와 특정 인력 및 선행조건을 적용한 산정 시나리오입니다. 확정 일정이 아니며 planning 문서에도 같은 안내를 반영했습니다.

### Q5. 이미 확정된 내용이다.

> 적용할 문서 버전, 확인 담당과 승인 또는 합의 일자를 알려주시면 확정 상태로 반영하겠습니다. 현재 자료와 차이가 있다면 최신 기준을 우선하겠습니다.

### Q6. 왜 이제 이 문제를 제기하는가?

> 개발과 일정에 사용할 자료를 구체적으로 대조하는 과정에서 범위, 상태와 연동 기준의 확인 필요사항이 드러났습니다. 지금 기준선을 정하지 않으면 구현 이후 재작업과 일정 변경이 더 커질 수 있어 현재 시점에 공유드리는 것입니다.

### Q7. 개발 인원을 추가하면 일정이 해결되지 않는가?

> 인력 추가는 확정된 기능의 병렬 구현에는 도움이 됩니다. 그러나 기획, 디자인, API와 Native 확인 대기는 인원만으로 줄어들지 않습니다. 인력과 함께 선행조건 및 제공 일정이 정리돼야 합니다.

### Q8. Front-end 쪽에는 문제가 없는가?

> Front-end도 구현, 검토, 협의와 통합에 필요한 실제 가동률을 일정에 반영해야 합니다. Front-end에서 확정할 기술 기준과 준비할 작업은 문서에 함께 포함했고, 지연이나 미완료가 확인되면 같은 기준으로 WBS에 반영하겠습니다.

### Q9. 문서가 너무 많고 복잡하다.

> 모든 문서를 다 읽어달라는 요청은 아닙니다. 오늘은 결정이 필요한 항목과 담당, 목표일만 확인하고, 상세 문서는 판단 근거로 사용하겠습니다.

### Q10. 누가 최종적으로 정리해야 하는가?

> 각 파트는 담당 영역을 확인하고, PM은 범위, 담당, 선후행 관계와 결정 일정을 하나의 WBS로 통합 관리해야 합니다.

## 9. 대화가 감정적으로 흐를 때

다음 문장 중 하나를 사용해 논점을 되돌린다.

> 과거 평가보다는 현재 적용할 기준을 먼저 확인하겠습니다.

> 해당 내용이 확정됐다면 적용 문서와 버전을 확인하겠습니다.

> 이 자리에서 책임을 판단하기보다 담당과 목표일을 정하는 것이 우선이라고 생각합니다.

> 의견 차이는 미확정으로 기록하고 최종 확인 담당을 지정하면 됩니다.

> 지금 말씀드리는 핵심은 개발 거부가 아니라 일정의 근거를 확인하자는 것입니다.

상대방의 설명이 길어지면 다음 세 가지만 다시 묻는다.

1. 현재 적용할 결정은 무엇인가?
2. 최종 확인 담당은 누구인가?
3. 언제까지 어떤 문서에 반영할 것인가?
